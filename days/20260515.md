## 二、样本一：AI生成Java并发代码的三大致命Bug

### 2.1 双重检查锁定陷阱 (S2168)

**问题代码**：
```java
public class ResourceFactory {
    private static Resource resource;

    public static Resource getInstance() {
        if (resource == null) {
            synchronized (ResourceFactory.class) {
                if (resource == null)
                    resource = new Resource();
            }
        }
        return resource;
    }
}
```

**🔴 危险**：
- 没有`volatile`修饰，`resource`字段赋值可能被JVM重排序
- 线程B可能拿到部分构造的Resource对象引用
- 编译通过，单线程测试通过，生产环境偶发性崩溃

**✅ 修复方案**：
```java
// 方案1：直接同步方法（简洁安全）
public static synchronized Resource getInstance() {
    if (resource == null)
        resource = new Resource();
    return resource;
}

// 方案2：静态内部类Holder（延迟加载+JLS保证线程安全）
private static class ResourceHolder {
    public static Resource resource = new Resource();
}
public static Resource getResource() {
    return ResourceHolder.resource;
}
```

### 2.2 基于值类的同步陷阱 (S1860)

**问题代码**：
```java
private static final Boolean bLock = Boolean.FALSE;

public void doSomething() {
    synchronized (bLock) {  // 🔴 危险！
        // critical section
    }
}
```

**🔴 危险**：
- `Boolean.FALSE`是**值类**，JVM会缓存所有`Boolean.FALSE`引用
- 全应用所有`synchronized(Boolean.FALSE)`共享同一把锁
- 与第三方库冲突 → 未知死锁，栈追踪毫无关联

**同样问题的类型**：
- `Integer.valueOf()` 在-128~127范围内
- `String`字面量
- `List.of()`结果
- `java.time`类型

**✅ 修复**：
```java
private static final Object lock = new Object();

public void doSomething() {
    synchronized (lock) {
        // critical section
    }
}
```

### 2.3 持有锁时调用Thread.sleep() (S2276)

**问题代码**：
```java
public void doSomething() {
    synchronized (monitor) {
        while (!ready()) {
            Thread.sleep(200);  // 🔴 持有锁时休眠！
        }
        process();
    }
}
```

**🔴 危险**：
- `Thread.sleep()` **不释放**monitor锁
- 所有等待该锁的线程被冻结，无法进入临界区
- 如果有线程需要该锁才能修改`ready()`状态 → 死锁

**✅ 修复**：
```java
public void doSomething() {
    synchronized (monitor) {
        while (!ready()) {
            monitor.wait(200);  // ✅ 释放锁，等待期间允许其他线程进入
        }
        process();
    }
}
```

## 三、样本二：Spring Boot生产级配置七大死亡陷阱

### 3.1 数据库连接池耗尽（438/500代码库中招）

**问题**：
- HikariCP默认只有**10个连接**
- 开发环境1-2个并发，永远不触发
- 生产环境并发请求 → 排队 → 超时 → 崩溃

**真实案例**：
- 20万用户SaaS应用，连接池默认10
- 每周一9点全员登录 → 系统准时崩溃
- 团队排查6周 → 我改连接池到50 → 4秒修复
- 损失：18万美元营收

**✅ 修复**：
```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 50  # 根据真实并发配置
      connection-timeout: 30000
      idle-timeout: 600000
```

### 3.2 @Transactional滥用（381/500代码库中招）

**问题代码**：
```java
@Service
public class PaymentService {
    @Transactional  // 🔴 给调用外部接口的方法加事务！
    public void processPayment(Order order) {
        callExternalAPI1();  // 耗时2-4秒
        callExternalAPI2();  // 耗时2-4秒
        callExternalAPI3();  // 耗时2-4秒
        // 整个事务占用连接长达22秒
    }
}
```

**🔴 危险**：
- 事务期间**不释放数据库连接**
- 10个连接 ÷ 2秒/请求 = 5个并发用户占满全连接池
- 其他业务全部阻塞

**真实案例**：
- 金融科技公司凌晨2:47支付崩溃
- 每分钟亏损4000美元
- 4年经验开发者加了@Transactional
- 删除注解 → 23分钟后恢复

**✅ 修复**：
```java
@Service
public class PaymentService {
    // ✅ 仅在真正需要事务的数据库操作上加注解
    @Transactional
    public void savePaymentRecord(Payment payment) {
        paymentRepository.save(payment);
    }
    
    // ✅ 外部接口调用不要加事务
    public void processPayment(Order order) {
        callExternalAPI1();
        callExternalAPI2();
        savePaymentRecord(...);  // 事务在子方法中
    }
}
```

### 3.3 N+1查询灾难（413/500代码库中招）

**问题代码**：
```java
@GetMapping("/orders")
public List<OrderDTO> getOrders() {
    List<Order> orders = orderRepository.findAll();  // 1次查询
    return orders.stream()
        .map(this::toDTO)  // 🔴 每条触发懒加载getUser() = +100次查询
        .collect(Collectors.toList());
}
```

**数据流**：
```
100条订单 = 1次查订单 + 100次查用户 = 101次数据库请求
```

**✅ 修复**：
```java
// 方案1：JOIN FETCH急加载
@Query("SELECT o FROM Order o JOIN FETCH o.user WHERE ...")
List<Order> findAllWithUser();

// 方案2：EntityGraph
@EntityGraph(attributePaths = {"user"})
List<Order> findAll();
```

### 3.4 异常静默吞噬（267/500代码库中招）

**问题代码**：
```java
try {
    paymentService.charge(user, amount);
} catch (PaymentException e) {
    log.error("支付失败", e);
    // 🔴 异常被吞掉，程序继续执行
}
orderService.complete(order);  // 用户被扣费，但订单继续处理
```

**🔴 危险**：
- 支付失败 → 用户扣费 → 商品不发货
- 6个月累积9000笔问题订单
- 损失34万美元退款 + 大量客诉

**✅ 修复**：
```java
try {
    paymentService.charge(user, amount);
} catch (PaymentException e) {
    log.error("支付失败，回滚订单", e);
    throw new OrderProcessingException("支付处理失败", e);  // ✅ 向上抛出
}
```

### 3.5 Jackson无限递归（229/500代码库中招）

**问题代码**：
```java
@Entity
public class Order {
    @OneToMany(mappedBy = "order")
    private List<OrderItem> items;  // 🔴 双向关联
}

@Entity
public class OrderItem {
    @ManyToOne
    private Order order;  // 🔴 反向引用
}
```

**数据流**：
```
Order → items → OrderItem → order → items → OrderItem → ... → StackOverflow!
```

**✅ 修复**：
```java
@Entity
public class Order {
    @OneToMany(mappedBy = "order")
    @JsonIgnore  // ✅ 忽略反向关联
    private List<OrderItem> items;
}
```

## 四、跨语言设计智慧对比

### Java vs 其他语言的并发安全

| 模式 | Java | Go | Rust | Swift |
|------|------|-----|------|-------|
| 单例懒加载 | volatile / synchronized / Holder | sync.Once | OnceCell | static + dispatch_once |
| 锁对象选择 | 避免Boolean/Integer缓存 | 原生无此问题 | borrow checker保护 | Actor隔离 |
| 等待模式 | wait() vs sleep() | channel阻塞 | await tokio::time::sleep | Task.sleep |
| 数据竞争 | JMM happens-before | channel传递 | 编译期保证 | @MainActor |

**跨语言教训**：
- **信任边界跨越**：Cross Before You Use（Hyrum's Law）
- **并发安全**：编译期保证 > 运行时检测 > 人工检查
- **默认值陷阱**：Spring默认10连接 vs Go默认无限制 channel

## 五、AI最可能隐瞒的弱点

1. **不提及性能影响**：@Transactional在调用外部接口时的连接占用
2. **不标注边界条件**：单例模式没有volatile的性能代价
3. **不解释隐藏行为**：Boolean.FALSE的JVM缓存导致锁共享
4. **不提醒默认值危险**：HikariCP默认10连接的生产风险
5. **不说明懒加载副作用**：N+1查询的指数级性能衰减

## 六、审查checklist更新

### 新增检查项

- [ ] **并发安全**：单例是否有volatile？锁对象是否为基础类型缓存？
- [ ] **连接池配置**：HikariCP是否超过默认10连接？
- [ ] **事务边界**：@Transactional是否用于外部接口调用？
- [ ] **查询策略**：关联查询是否N+1？是否用JOIN FETCH？
- [ ] **异常处理**：catch块是否有业务兜底还是静默吞噬？
- [ ] **JSON序列化**：实体是否有双向关联导致无限递归？
