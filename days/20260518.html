不要被“像样”的代码骗过去

今天练的是代码审美：识别 AI 生成代码里的薄、油、虚，以及真正稳、硬、有边界感的工程质地。

核心判断

AI 代码常见错觉

  • 看起来完整，但没有边界
  • 看起来现代，但没有资源预算
  • 看起来抽象，但没有真实需求
  • 看起来自信，但没有证据链

审查时真正要看

  • 契约是否被显式建模
  • 失败是否可恢复、可定位
  • 资源是否有上限
  • 依赖、API、结论是否有证据

契约错位

LiteLLM adapter

字段名相似不等于语义相同。provider 适配层要有 capability model，而不是把一套 payload 塞给所有后端。

payload = {
    "model": model,
    "messages": messages,
    "reasoning_effort": "low",
    "tools": tools,
}
教程感

Copilot security weaknesses

AI 代码常常流畅、安全感很低。最常见写法不等于生产安全写法。

query = f"SELECT * FROM users WHERE email = '{email}'"
依赖幻觉

Package hallucination

包名看起来像真的，可能正是风险所在。依赖不是修辞，是供应链债务。

import { sanitizePaymentMemo } from "secure-payment-utils";
证据链

curl AI vulnerability reports

差的审查意见像判词，好的审查意见像实验记录：版本、入口、复现、栈、修复、回归测试。

审美词典

薄

只有 happy path，缺少边界、异常、日志、回滚、限流。

油

抽象很多、命名漂亮，但没有真实复杂度支撑。

虚

解释比代码可靠，事实链断裂，结论没有文档、源码或测试证明。

硬

类型、约束、边界、状态机写进代码和数据库，不靠口头约定。

稳

失败可恢复，重试幂等，资源有上限，日志能定位。

像样

变量名合理、函数短、解释顺，但需要追问证据和异常路径。

五个审查动作
动作适用场景提问
向代码要证据AI 解释 API、框架、性能收益这个行为来自哪份官方文档、源码分支或测试？
查相似 API 误用跨 provider、跨云厂商、跨语言迁移同名字段在目标后端语义是否一致？
从异常路径读设计支付、任务、消息、文件、网络第 N 步成功、第 N+1 步失败后，系统是什么状态？
把新增依赖当 PR 主角AI 新增 import/package这个包是否真实、必要、可信？
看抽象有没有第二个调用者AI 过度设计这个接口、工厂、策略对象服务的变化点是什么？
高价值问题清单
这段代码是否只证明了 happy path？边界是类型保证、数据库保证，还是注释保证？失败后是否可重试、可恢复、可定位？审查意见是否能复现，还是只有严重性形容词？

代码层

  • Optional/null/空字符串是否被混为一谈？
  • 错误是否被整理成无信息的 false/null/默认值？
  • 安全动作是否使用安全 API，而不是手写字符串处理？

系统层

  • 并发、连接、内存、队列是否有预算？
  • 新增依赖是否真实存在并值得引入？
  • AI 是否把一个生态的 API 套到了另一个生态？
