🔴 A: synchronized集合的假安全感

银行支付网关 · 来源: markaicode.com

private List<PaymentTransaction> activeTransactions = 
    Collections.synchronizedList(new ArrayList<>());

private void cleanupCompleted() {
    // ❌ 对synchronizedList迭代+删除
    for (PaymentTransaction tx : activeTransactions) {
        if (tx.getStatus() == TransactionStatus.COMPLETED) {
            activeTransactions.remove(tx);  // 💥 ConcurrentModificationException!
        }
    }
}

🔑 synchronizedList 只保证单操作原子性，不保证复合操作（迭代+删除）

✅ A: 修复方案

// ✅ 使用专为并发设计的集合
private final ConcurrentLinkedQueue<PaymentTransaction> activeTransactions = 
    new ConcurrentLinkedQueue<>();

private void cleanupCompleted() {
    // ✅ ConcurrentLinkedQueue.removeIf 是线程安全的
    activeTransactions.removeIf(tx -> 
        tx.getStatus() == TransactionStatus.COMPLETED 
        || tx.getStatus() == TransactionStatus.REJECTED
    );
}

✅ ConcurrentLinkedQueue 迭代安全 · removeIf 原子操作 · 清理移出 finally

🔴 B: synchronized杀死Virtual Thread

银行账户转账 · markaicode.com · Sonar Blog

// ❌ synchronized方法 + IO操作 = Virtual Thread pinning
public synchronized TransferResult transfer(
        Long fromAccountId, Long toAccountId, BigDecimal amount) {
    Account from = accountRepository.findById(fromAccountId).orElseThrow();  // DB查询
    Account to = accountRepository.findById(toAccountId).orElseThrow();      // DB查询
    from.debit(amount);
    to.credit(amount);
    accountRepository.save(from);   // DB写入
    accountRepository.save(to);     // DB写入
    auditLogService.logTransfer();  // DB写入
    notificationService.notify();   // 网络调用!
    return TransferResult.success();
}

synchronized → pin住载体线程 → ForkJoinPool耗尽 → 所有Virtual Thread排队

实测：synchronized ~50 TPS vs ReentrantLock ~500 TPS（10倍差距）

✅ B: 细粒度锁 + 超时 + 锁排序

// ✅ 每个账户一把锁
private final ConcurrentHashMap<Long, ReentrantLock> accountLocks = new ConcurrentHashMap<>();

public TransferResult transfer(Long fromId, Long toId, BigDecimal amount) {
    // ✅ 按ID排序获取锁，防止死锁
    Long first = Math.min(fromId, toId);
    Long second = Math.max(fromId, toId);
    ReentrantLock lock1 = accountLocks.computeIfAbsent(first, k -> new ReentrantLock());
    ReentrantLock lock2 = accountLocks.computeIfAbsent(second, k -> new ReentrantLock());
    if (!lock1.tryLock(5, TimeUnit.SECONDS)) throw new TransferTimeoutException();
    try {
        if (!lock2.tryLock(5, TimeUnit.SECONDS)) throw new TransferTimeoutException();
        try { return doTransfer(fromId, toId, amount); }
        finally { lock2.unlock(); }
    } finally { lock1.unlock(); }
}

✅ 不pin载体 · ✅ 超时防无限等 · ✅ 排序防死锁 · ✅ IO移出锁范围

🔴 C: 双重检查锁定的幽灵

银行风控引擎 · Sonar S2168

// ❌ 缺少volatile！
private static RiskRuleChain ruleChain;

public RiskRuleChain getRuleChain() {
    if (ruleChain == null) {                   // 第1次检查
        synchronized (RiskRuleEngine.class) {
            if (ruleChain == null) {           // 第2次检查
                ruleChain = loadRuleChain();    // ❌ 指令重排序！
            }
        }
    }
    return ruleChain;  // 可能返回半构造对象！
}

JMM允许 new 的构造器初始化与引用赋值重排序 → 线程B看到非null但未初始化的对象

风控场景后果：规则链不完整 → 洗钱交易畅通无阻

✅ C: 修复 + 🔴 D: 价值类对象作锁

修复：Holder模式 + AtomicReference

// ✅ JVM类初始化天然线程安全
private static class RuleChainHolder {
  static final AtomicReference<RiskRuleChain> 
    INSTANCE = new AtomicReference<>();
}
// 或更简洁：@PostConstruct

🔴 Boolean/Integer作锁

private static final Boolean lock = Boolean.FALSE;
synchronized (lock) { ... }
// ❌ Boolean.FALSE全局唯一！

🔴 E: Structured Concurrency缺join

银行批量代发 · markaicode.com

try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    for (PaymentOrder order : orders) {
        scope.fork(() -> {
            results.add(processPayment(order));  // ❌ ArrayList非线程安全
            return null;
        });
    }
    // ❌ 没有scope.join()！try-with-resources关闭时子任务仍在运行

}

✅ 并发审查Checklist

  • Collections.synchronized*() 的迭代操作是否安全？
  • Virtual Thread 环境中是否用了 synchronized？能否改 ReentrantLock？
  • 双重检查锁定是否缺 volatile？能否改用 Holder 模式？
  • 锁对象是否为 Boolean/Integer/String 等价值类？
  • StructuredTaskScope 关闭前是否调了 join()？
  • CompletableFuture 链是否有 whenComplete/handle/orTimeout？
  • synchronized 块内是否有 Thread.sleep()？应改 wait()
  • 锁粒度是否合理？是否包含 IO/网络操作？
  • 多把锁获取顺序是否一致？是否可能死锁？
  • 并发集合选择是否匹配场景？

🏗️ 架构评估：好设计 vs 坏设计

✅ ReentrantLock + tryLock超时

· 不pin Virtual Thread
· 超时防无限等待
· 细粒度：每资源独立锁
· 支持可中断/尝试获取

✅ 静态内部类Holder模式

· JVM类初始化保证线程安全
· 零同步代码，零性能开销
· 惰性加载，代码极简

🔴 synchronized方法级锁定+IO

· 粒度过粗：整个方法持锁
· Virtual Thread pinning
· IO拖长锁持有时间
· 全局串行化，TPS极低

🔴 Collections.synchronized*()

· 虚假安全感，比显式不安全更危险
· 复合操作不原子
· 性能不如j.u.c集合
