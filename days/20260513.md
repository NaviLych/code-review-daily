## 一、数据流审查（第1轮）

### 1.1 Rust crossbeam-channel Double-Free Bug 🔴

**来源**：[Diagnosing a Double-Free Concurrency Bug in Rust's Unbounded Channels](https://materialize.com/blog/rust-concurrency-bug-unbounded-channels/)

**数据流分析**：
```
Sender线程 ──写入──► Channel.tail ──读取──► Receiver线程
                            ↑
                      Block链表管理
```

**问题识别**：
- **输入**：多线程同时调用 `send()` 和 `drop(receiver)`
- **中间状态**：Channel初始化时 head 和 tail 同时指向 null，存在半初始化状态的时间窗口
- **输出**：两个线程可能同时释放同一 Block 指针 → Double-Free

**根因**：
```rust
// channel 初始化是两步操作，存在竞态窗口
head = null;  // Step 1
tail = null;  // Step 2
// 此时 head==tail==null，但内部状态不一致
```

**🔴 关键弱点**：即使Rust的所有权系统能防止大多数内存问题，但并发初始化和析构的边界情况仍可能突破安全边界。

### 1.2 Go 错误处理中的重复检查 🔴

**来源**：[Error handling in Go: Common pitfalls - PVS-Studio](https://pvs-studio.com/en/blog/posts/go/1371/)

**问题代码**：
```go
resp, err := c.List(opts)
if err != nil {
    return resp, err
}
data := resp.Data
for next, err := resp.Next(); next != nil && err == nil; next, err = next.Next() {
    data = append(data, next.Data...)
    resp = next
    resp.Data = data
}
if err != nil {  // ⚠️ 这里检查的是外层 err，不是循环中的 err
    return resp, err
}
return resp, err  // ⚠️ 返回的是初始 err，永远不是循环终止的原因
```

**数据流问题**：
- 循环内部的 `err` 遮蔽了外层的 `err`
- 循环结束后检查的 `err` 仍是初始声明的 `nil`

## 二、边界条件审查（第2轮）

### 2.1 TypeScript `as any` 类型安全破坏 🔴

**来源**：[Development Anti-Patterns - GitHub Issue #466](https://github.com/code-yeongyu/oh-my-openagent/issues/466)

**典型案例**：
```typescript
// ❌ 滥用 as any
const tuiClient = this.client as any
const data = response as any
(part as any).thinking = true

// ✅ 正确做法：定义接口
interface TuiClient {
    connect(): Promise<void>;
    send(msg: string): Promise<Response>;
}
const tuiClient: TuiClient = this.client as TuiClient;
```

**边界条件**：
- API返回意外结构时，`as any` 导致运行时崩溃
- 隐藏了类型不匹配，测试覆盖无法发现

### 2.2 Rust async TOCTOU 竞态 🟡

**来源**：[Rust Security Vulnerabilities in 2025](https://markaicode.com/rust-security-vulnerabilities-2025-analysis-mitigation/)

**漏洞模式**：
```rust
// ❌ Time-of-Check-Time-of-Use
async fn verify_and_use_file(path: &Path) -> Result<(), Error> {
    let metadata = fs::metadata(path).await?;  // Check
    if metadata.permissions().readonly() {
        return Err(Error::PermissionDenied);
    }
    // ⚠️ Time Gap: 文件权限可能在此处被修改
    let content = fs::read_to_string(path).await?;  // Use
    process_content(&content)
}

// ✅ 修复：使用文件描述符
async fn verify_and_use_file_fd(fd: &File) -> Result<(), Error> {
    // 文件描述符在打开时锁定权限
    let content = fd.read_to_string().await?;
    process_content(&content)
}
```

**来源**：[AI Code Review Guide - techdebt.works](https://techdebt.works/ai-code-review/)

## 三、必要性审查（第3轮）

### 3.1 Go 中删除 `fmt.Errorf` 包装会怎样？

```go
// 原始代码
data, err := ioutil.ReadAll(r)
if err != nil {
    return nil, fmt.Errorf("failed to read all data from reader: %w", err)
}

// 删除 fmt.Errorf 包装后
if err != nil {
    return nil, err  // ❌ 丢失上下文，调用方无法定位问题
}
```

**结论**：`fmt.Errorf` 不可删，它提供错误溯源的上下文链路。

### 3.2 Rust 过度使用 Mutex 的必要性

```rust
// ❌ 不必要的锁持有
fn process_data(data: &Arc<Mutex<Data>>) {
    let mut locked = data.lock().unwrap();
    some_helper_function(&data);  // 内部又获取同一把锁 → 死锁风险
    locked.process();
}

// ✅ 重构：缩小锁的作用域
fn process_data(data: &Arc<Mutex<Data>>) {
    let result = {
        let locked = data.lock().unwrap();
        locked.get_result_copy()  // 复制需要的数据
    };  // 锁在这里释放
    some_helper_function(&data);  // 无锁调用
    process_result(result);
}
```

## 四、反向审查：AI 最可能隐瞒的弱点

### 4.1 AI 生成代码的 8 大模式（来源：techdebt.works）

| 模式 | AI 隐瞒的风险 | 审查重点 |
|------|---------------|----------|
| 1. 过度冗长的错误处理 | try/catch 吞掉异常，不向上游传播 | 检查 catch 块是否只 log |
| 2. 同一文件内命名不一致 | camelCase/snake_case 混用 | 搜索同一概念的不同命名 |
| 3. 未使用的导入/死代码 | 引入不存在/有漏洞的包 | 验证每个 import 实际使用 |
| 4. 函数职责过多 | 40+ 行，多层嵌套，违反 SRP | 检查函数名是否含 "and" |
| 5. 缺失边界条件处理 | 空数组、null、超大值 | 主动构造极端输入测试 |
| 6. 硬编码配置值 | 环境差异时失败 | 搜索字符串字面量 |
| 7. 通用变量名 | data/result/temp 无语义 | 检查变量名是否自解释 |
| 8. 注释重复代码 | 不解释 WHY，只说 WHAT | 检查注释是否冗余 |

## 五、审美与架构评估

### 5.1 跨语言错误处理模式对比

| 语言 | 错误传播机制 | 类型安全 | 典型反模式 |
|------|-------------|----------|-----------|
| Go | 多返回值 + error 接口 | ❌ 无 | 忽略错误 `_` |
| Rust | Result<T, E> 枚举 | ✅ 编译期检查 | `unwrap()` 滥用 |
| TypeScript | try/catch / null 检查 | 🟡 类型守卫 | `as any` |
| Swift | throws / Result | ✅ 可选类型 | 过度使用 `try?` |

### 5.2 架构智慧：统一错误响应

**Go 最佳实践**（来源：[errors.Is errors.As 指南](https://it-araiguma.com/go-error-handling-design-pattern-guide/)）：

```go
// ✅ 领域错误型
type AppError struct {
    Code    int    // HTTP 状态码
    Message string // 用户可见消息
    Err     error  // 内部错误
}

func (e *AppError) Unwrap() error { return e.Err }

// ✅ 调用方使用 errors.As
var appErr *AppError
if errors.As(err, &appErr) {
    http.Error(w, appErr.Message, appErr.Code)
}
```

**跨语言借鉴**：Swift 的 `Result` 类型 + `LocalizedError` 协议实现类似效果：
```swift
enum AppError: Error {
    case notFound(String)
    case unauthorized
}
```

## 六、今日审查模式积累

### 新增到模式库：

1. **空 Catch 块静默吞异常** (severity: HIGH)
   - 症状：catch 块为空或只有注释
   - 修复：至少记录 debug 级别日志

2. **循环变量遮蔽外层错误** (severity: HIGH, Go)
   - 症状：`for ... err := ...` 遮蔽外层 `err`
   - 修复：使用不同的变量名或在外层累积错误

3. **Rust async TOCTOU** (severity: MEDIUM)
   - 症状：权限检查和文件操作分离
   - 修复：使用文件描述符而非路径

4. **TypeScript as any 滥用** (severity: HIGH)
   - 症状：类型断言到 any 绕过检查
   - 修复：定义完整接口，使用类型守卫
