## 一、Java/Spring Boot 典型错误模式

### 1.1 Spring Security 配置错误 ⭐⭐⭐

#### 错误1: `withDefaultPasswordEncoder()` 陷阱

> 来源: SonarSource - GPT-5.5's biggest blind spot

```java
// ❌ AI 生成的有缺陷代码
@Bean
public UserDetailsService userDetailsService() {
    UserDetails user = User.withDefaultPasswordEncoder()  // ⚠️ 已废弃!
        .username("admin")
        .password("password")
        .roles("USER")
        .build();
    return new InMemoryUserDetailsManager(user);
}
```

**问题分析**:
- **数据流**: 输入是明文密码，输出是 UserDetails 对象
- **边界条件**: `withDefaultPasswordEncoder()` 内部创建新的 encoder，与 BCrypt bean 不一致
- **必要性**: 方法已废弃，会产生安全警告，且密码编码不一致

**修复方案**:
```java
@Bean
public UserDetailsService userDetailsService(PasswordEncoder passwordEncoder) {
    UserDetails user = User.builder()
        .username("admin")
        .password(passwordEncoder.encode("password"))  // 使用注入的 encoder
        .roles("USER")
        .build();
    return new InMemoryUserDetailsManager(user);
}
```

**架构评估**: 依赖注入是正确的做法，但 AI 往往忽略框架特性的演进

#### 错误2: CORS 配置缺失或不完整

```java
// ❌ AI 生成的残缺配置
@Configuration
@EnableWebSecurity
public class SecurityConfig {
    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http.cors().and()  // ⚠️ 没有实际的 CorsConfigurationSource
            .authorizeHttpRequests(auth -> auth
                .anyRequest().authenticated()
            );
        return http.build();
    }
}
```

**问题分析**:
- **数据流**: 前端请求经过 CORS 预检，但这里没有配置 `allowedOriginPatterns`
- **边界条件**: localhost 开发时端口是随机的，必须用 `allowedOriginPatterns`
- **必要性**: 前端会收到 CORS 错误，导致整个系统不可用

**修复方案**:
```java
@Bean
public CorsConfigurationSource corsConfigurationSource() {
    CorsConfiguration configuration = new CorsConfiguration();
    configuration.setAllowedOriginPatterns(List.of("http://localhost:*"));
    configuration.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE", "OPTIONS"));
    configuration.setAllowedHeaders(List.of("*"));
    configuration.setAllowCredentials(true);
    
    UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
    source.registerCorsConfiguration("/**", configuration);
    return source;
}
```

**审美评估**: 配置式风格比 XML 风格更清晰，但 AI 常遗漏完整的 Bean 配置

#### 错误3: Spring Boot 3+ 废弃语法 `WebSecurityConfigurerAdapter`

> 来源: SonarSource - GPT-5.5's biggest blind spot

```java
// ❌ AI 生成的已废弃代码 (无法编译)
@Configuration
@EnableWebSecurity
public class SecurityConfig extends WebSecurityConfigurerAdapter {  // ⚠️ 废弃!
    
    @Override
    protected void configure(HttpSecurity http) throws Exception {  // ⚠️ 废弃!
        http
            .authorizeRequests()  // ⚠️ 废弃!
            .antMatchers("/api/public/**").permitAll()  // ⚠️ 废弃!
            .anyRequest().authenticated();
    }
}
```

**问题分析**:
- **数据流**: 配置被完全重写，但基于旧 API
- **架构**: 继承 vs 组合，Spring Boot 3 鼓励使用 Bean 配置

**修复方案**:
```java
@Configuration
@EnableWebSecurity
public class SecurityConfig {
    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        return http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/public/**").permitAll()
                .anyRequest().authenticated()
            )
            .build();
    }
}
```

### 1.2 Java Stream API 错误模式

#### 错误4: 使用废弃的 `Collectors.toList()`

```java
// ⚠️ AI 生成的代码 (产生警告)
List<String> names = users.stream()
    .map(User::getName)
    .filter(name -> !name.isEmpty())
    .collect(Collectors.toList());  // ⚠️ Java 16+ 废弃
```

**问题分析**:
- **数据流**: Stream → 中间操作 → 终止操作，输出不可变 List
- **边界条件**: `collect(toList())` 返回可变 List，`toList()` 返回不可变 List
- **必要性**: 简单替代可以工作，但语义不同

**修复方案**:
```java
List<String> names = users.stream()
    .map(User::getName)
    .filter(name -> !name.isEmpty())
    .toList();  // Java 16+ 更简洁
```

#### 错误5: 盲目使用 `parallelStream()`

```java
// ❌ AI 生成的危险代码
public void processOrders(List<Order> orders) {
    orders.parallelStream()
        .forEach(order -> {
            orderRepository.save(order);  // ⚠️ 数据库连接池耗尽
        });
}
```

**问题分析**:
- **数据流**: 并行处理，每个线程都调用数据库
- **边界条件**: 连接池大小有限，并行度失控
- **必要性**: parallelStream 适合 CPU 密集型，不适合 IO 密集型

**修复方案**:
```java
public void processOrders(List<Order> orders) {
    orderRepository.saveAll(orders);  // 批量保存，让数据库处理优化
}
```

**架构评估**: AI 不理解硬件资源约束，倾向于用并行掩盖效率问题

### 1.3 并发安全问题

#### 错误6: Double-Checked Locking 缺少 `volatile`

> 来源: [SonarSource - GPT-5.5's biggest blind spot](https://www.sonarsource.com/blog/gpt-5-5-biggest-blind-spot)

```java
// ❌ AI 生成的错误单例
public class ResourceFactory {
    private static Resource resource;

    public static Resource getInstance() {
        if (resource == null) {
            synchronized (ResourceFactory.class) {
                if (resource == null)
                    resource = new Resource();  // ⚠️ 可能返回部分构造对象
            }
        }
        return resource;
    }
}
```

**问题分析**:
- **数据流**: 线程 A 在 `new Resource()`，线程 B 看到非 null 但未构造完成的对象
- **边界条件**: JVM 可能重排序，构造函数在字段赋值之后完成
- **必要性**: 现代 JVM 下 synchronized 开销已可接受

**修复方案1** (推荐):
```java
public static synchronized Resource getInstance() {
    if (resource == null)
        resource = new Resource();
    return resource;
}
```

**修复方案2** (Holder 模式):
```java
private static class ResourceHolder {
    public static Resource resource = new Resource();
}

public static Resource getInstance() {
    return ResourceHolder.resource;  // JVM 保证线程安全
}
```

#### 错误7: 在 Boolean/FInteger 等值类型上 `synchronized`

```java
private static final Boolean bLock = Boolean.FALSE;

public void doSomething() {
    synchronized (bLock) {  // ⚠️ Boolean.valueOf() 缓存 -128~127
        // 危险: 其他代码可能使用相同的 Boolean 对象作为锁
    }
}
```

**问题分析**:
- **数据流**: 锁对象可能被其他代码意外共享
- **边界条件**: Integer 等值类型有缓存池，锁可能冲突
- **必要性**: 应使用专用对象作为锁

**修复方案**:
```java
private final Object lock = new Object();

public void doSomething() {
    synchronized (lock) {
        // 安全: 专用锁对象
    }
}
```

**扩展**: `Integer`、`String`、`List.of()` 同样有缓存/不可变陷阱，切勿用作锁对象

## 二、Swift/iOS 典型错误模式

### 2.1 Optional 处理错误

#### 错误8: `nil` 返回值被替换为空字符串

```swift
// ❌ Objective-C 原代码被 AI"修复"
func getUserName() -> String {  // ⚠️ 错误: 应该是 String?
    if let user {
        return user.name
    }
    return ""  // ⚠️ AI"修复"了 nil
}
```

**问题分析**:
- **数据流**: nil 是"没有用户"的信号，空字符串是"有用户但没名字"
- **边界条件**: 调用方检查是否为 nil 来做决策，改为空字符串会破坏契约
- **必要性**: 语义变更导致下游代码行为异常

**修复方案**:
```swift
func getUserName() -> String? {
    return user?.name  // 正确保留 Optional 语义
}
```

**学习要点**: AI 不理解 nil 作为信号的意义，只做语法层面的"美化"

#### 错误9: 强制解包 Optional

```swift
// ❌ AI 生成的崩溃代码
let image = UIImage(named: "aMissingIcon")!  // ⚠️ 运行时崩溃
```

**问题分析**:
- **边界条件**: 资源可能不存在，强制解包不考虑失败情况

**修复方案**:
```swift
if let image = UIImage(named: "aMissingIcon") {

    // 处理缺失情况
}
```

```swift
// ❌ AI 转换的代码 (功能正确但非最佳实践)
```

### 2.3 Swift async/await 并发三大陷阱 ⭐⭐⭐

> 来源: [3 mistakes to avoid with async/await - Swift with Vincent](https://swiftwithvincent.squarespace.com/blog/three-mistakes-to-avoid-with-async-await-in-swift)

#### 陷阱1: 串行执行而非并行

**错误代码**:
```swift
// ❌ 串行执行：总耗时 = t1 + t2 + t3
let user = await getUser()           // 先等
let address = await getAddress(of: user)  // 再等
let payment = await getPayment(of: user) // 最后等
```

**问题分析**:
- **数据流**: 三个无依赖的调用被强制串行化
- **边界条件**: 如果每个调用耗时 1 秒，总耗时 3 秒而非 1 秒
- **必要性**: `await` 的位置决定了是否真正并行

**修复方案**:
```swift
// ✅ 并行执行：总耗时 = max(t1, t2, t3)
async let user = getUser()
async let address = getAddress(of: user)
async let payment = getPayment(of: user)

let (fetchedUser, fetchedAddress, fetchedPayment) = try await (user, address, payment)
```

**跨语言对比**: JavaScript 的 `Promise.all()`、Java 的 `CompletableFuture.allOf()` 异曲同工

#### 陷阱2: Task 隐式捕获 self 导致内存泄漏

**错误代码**:
```swift
@MainActor
class ViewModel {
    func listenToNotifications() {
        Task {
            // ⚠️ self 被隐式捕获，且永不释放
            let notifications = NotificationCenter.default.notifications(
                named: UIDevice.orientationDidChangeNotification
            )
            for await notification in notifications {
                self.handle(notification)  // Task 持有 self，强引用
            }
        }
    }
}
```

**问题分析**:
- **数据流**: Task 持有 ViewModel 的引用，而 Task 永远不会结束（监听无限序列）
- **边界条件**: 与 `@escaping` 闭包不同，Task 不强制显式捕获 `self`
- **必要性**: ViewController 释放后，整个对象树都无法释放

**修复方案**:
```swift
@MainActor
class ViewModel {
    func listenToNotifications() {
        Task { [weak self] in
            guard let self else { return }
            
            let notifications = NotificationCenter.default.notifications(
                named: UIDevice.orientationDidChangeNotification
            )
            
            for await notification in notifications {
                self.handle(notification)
            }
            // ✅ 循环内部 unwrap，确保 Task 可以正常结束
        }
    }
}
```

**关键点**: `weak self` 必须在 `for` 循环**内部** unwrap，而非外部

#### 陷阱3: 滥用 `Task.detached`

**错误代码**:
```swift
@MainActor
class ViewModel {
    func listenToNotifications() {
        Task.detached { [weak self] in  // ⚠️ 脱离 @MainActor 上下文
            let notifications = await NotificationCenter.default.notifications(
                named: UIDevice.orientationDidChangeNotification
            )
            
            for await notification in notifications {
                guard let self else { return }
                await self.handle(notification)  // 需要额外的 await
            }
        }
    }
}
```

**问题分析**:
- **数据流**: `Task.detached` 脱离父任务的 actor 上下文
- **边界条件**: 无法直接访问 `@MainActor` 标记的属性/方法，必须 `await`
- **必要性**: 增加了不必要的复杂性

**修复方案**: 优先使用普通 `Task`，只有确实需要时才用 `Task.detached`

## 三、Java 25 新特性陷阱 ⭐⭐⭐

> 来源: [Your AI can write Java 25 right with SonarQube](https://www.sonarsource.com/blog/ai-can-write-java-25-right-with-sonarqube/)

### 3.1 JEP 506: `ScopedValue` 与 `ExecutorService` 的误用

**错误代码**:
```java
static final ScopedValue<String> REQUEST_ID = ScopedValue.newInstance();

void handleRequest(String id) {
    ScopedValue.where(REQUEST_ID, id).run(() -> {
        executor.submit(() -> {  // ⚠️ 线程来自 ExecutorService
            String reqId = REQUEST_ID.get(); // NoSuchElementException!
            processAsync(reqId);
        });
    });
}
```

**问题分析**:
- **数据流**: ScopedValue 绑定到 Carrier 线程，但 `executor.submit()` 借用了线程池的线程
- **边界条件**: ScopedValue 绑定**不传播**到 `ExecutorService` 的工作线程
- **必要性**: 必须使用 `StructuredTaskScope` 才能继承绑定

**修复方案**:
```java
void handleRequest(String id) throws Exception {
    ScopedValue.where(REQUEST_ID, id).call(() -> {
        try (var scope = StructuredTaskScope.open(Joiner.allSuccessfulOrThrow())) {
            scope.fork(() -> {
                String reqId = REQUEST_ID.get(); // ✅ 正确继承
                processAsync(reqId);
                return null;
            });
            scope.join();
        }
        return null;
    });
}
```

### 3.2 `ScopedValue.where()` 结果被丢弃

**错误代码**:
```java
static final ScopedValue<String> THEME = ScopedValue.newInstance();

// ⚠️ Carrier 结果被丢弃，绑定从未激活
ScopedValue.where(THEME, "DARK");

// 下一行抛出 NoSuchElementException
String currentTheme = THEME.get();
```

**问题分析**:
- **数据流**: `.where()` 返回 Carrier，但未调用 `.run()` 或 `.call()`
- **必要性**: 必须消费 Carrier 对象

**修复方案**:
```java
// ✅ 正确消费 Carrier
ScopedValue.where(THEME, "DARK").run(this::renderUI);
```

## 四、跨语言设计智慧对比表

### 4.1 并发模式的语言差异

| 模式 | Java | Swift | Go | Python |
|------|------|-------|-----|--------|
| 轻量级并发 | Virtual Threads | async/await + Task | goroutine | asyncio |
| 共享状态 | synchronized/volatile | Actor / @MainActor | channel | GIL 限制 |
| 上下文传递 | ThreadLocal → ScopedValue | Task-local (iOS 17+) | context.Context | contextvars |
| 结构化并发 | StructuredTaskScope | TaskGroup | goroutine scope | - |
| 单例模式 | Holder / enum | static let | sync.Once | - |

### 4.2 关键洞察

**AI 最容易出错的并发场景**:
- Java: Double-checked locking 无 volatile、Boolean 上 synchronize
- Swift: Task 内存泄漏、串行 vs 并行混淆、Task.detached 滥用
- Python: asyncio 与同步代码混用

**跨语言通用原则**:
- 轻量级并发 ≠ 自动线程安全
- 上下文传递需要显式机制
- 结构化并发优于 ad-hoc 任务管理
- 永远不要用缓存对象（Boolean/Integer/List.of()）作为锁

- [ ] null/nil 处理

- [ ] 删除此代码会怎样？

- [ ] 过度设计了吗？
