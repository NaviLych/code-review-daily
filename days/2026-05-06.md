## 审查对象

### 样本A：React UserList 组件（AI生成）
**来源**：CSDN文章《拯救AI生成的烂代码》- 典型AI风格代码片段  
**背景**：用户使用提示词"帮我写一个用户列表页面，支持搜索和排序"生成

```javascript
function UserList({ users }) {
    const [searchTerm, setSearchTerm] = useState('');
    const [sortField, setSortField] = useState('name');
    
    // 性能陷阱:每次渲染都重新计算
    const filteredUsers = users.filter(user =>
        user.name.toLowerCase().includes(searchTerm.toLowerCase())
    );
    
    // 二次遍历:排序又一次全量遍历
    const sortedUsers = [...filteredUsers].sort((a, b) => {
        if (sortField === 'name') {
            return a.name.localeCompare(b.name);
        }
        return a.age - b.age;
    });
    
    return (
        <div>
            <input value={searchTerm} onChange={(e) => setSearchTerm(e.target.value)} />
            {sortedUsers.map(user => <UserCard key={user.id} user={user} />)}
        </div>
    );
}
```

### 样本B：Claude Code 生成的 LiteLLM Fallback 逻辑（真实生产Bug）
**来源**：GitHub Issue #54070 - Claude Code consistently delivers code with undetected logical errors  
**背景**：Claude Code实现LiteLLM fallback机制，声明任务完成

**AI生成的代码逻辑**：
```python
# Claude 实现的 fallback 配置
response = llm.chat(
    model="anthropic/claude-sonnet-4-20250514",
    messages=messages,
    fallbacks=[{"model": "anthropic/claude-sonnet-4-20250514", "reasoning_effort": "disable"}],
    drop_params=True  # AI认为这会解决问题
)
```

**问题描述**：Claude假设`drop_params=True`会删除不支持的参数，但实际上：
- LiteLLM在fallback中"drops unsupported parameter **NAMES**"
- Anthropic reasoning models接受参数名`reasoning_effort`
- 但拒绝参数值`"disable"`
- 结果`drop_params=True`是no-op，runtime仍然失败

## 分层审查

### 数据流分析

#### 样本A - React UserList

| 阶段 | 输入 | 变换 | 输出 |
|------|------|------|------|
| 1 | `users` prop | 无 | 数组 |
| 2 | `searchTerm` state | `toLowerCase()` | 小写字符串 |
| 3 | users + searchTerm | `filter()` + `toLowerCase()` | 过滤后数组 |
| 4 | filteredUsers | `[...filteredUsers]`拷贝 | 新数组引用 |
| 5 | 新数组 | `sort()` | 已排序数组 |
| 6 | sortedUsers | `map()` | JSX元素 |

**问题**：
- ❌ 每次`searchTerm`变化，`users.filter()`对每项执行`toLowerCase()`，重复计算
- ❌ `[...filteredUsers]`创建不必要的新数组，增加GC压力
- ❌ 拷贝后排序是就地算法，外层拷贝毫无意义

#### 样本B - LiteLLM Fallback

| 阶段 | 输入 | 假设 | 实际行为 |
|------|------|------|----------|
| API调用 | model + fallbacks配置 | drop_params会删除"reasoning_effort" | 只删除不支持的参数**名** |
| 参数传递 | reasoning_effort="disable" | 被drop | 值被拒绝，参数**名**被保留 |
| Runtime | 完整参数对象 | 正常工作 | 抛出异常 |

**问题**：
- ❌ **假设外部库行为与实际不符**
- ❌ **未验证关键常量的实际值**（MINIMUM_PROMPT_CACHE_TOKEN_COUNT）
- ❌ **依赖"看起来合理"的API行为**

### 边界条件分析

#### 样本A - React UserList

| 边界情况 | AI代码处理 | 实际风险 |
|----------|------------|----------|
| 空数组 `users=[]` | filter返回[]，sort返回[] | ✅ 安全 |
| `users` prop 频繁变化 | 每次变化重新计算 | ⚠️ 性能问题 |
| 超长字符串搜索 | toLowerCase正常 | ✅ 安全 |
| 大量数据(10000+) | 每次输入触发双遍历 | ❌ **严重性能问题** |
| 特殊字符/Unicode | 可能存在localeCompare问题 | ⚠️ locale依赖 |

**遗漏的边界检查**：
- ❌ 没有`useMemo`缓存计算结果
- ❌ 没有分页/虚拟列表支持
- ❌ 没有防抖(debounce)优化输入响应

#### 样本B - LiteLLM Fallback

| 边界情况 | AI代码处理 | 实际风险 |
|----------|------------|----------|
| fallback被触发 | 假设参数被正确处理 | ❌ **假设错误** |
| reasoning_effort值合法 | 正常 | ✅ 安全 |
| reasoning_effort值="disable" | drop_params会处理 | ❌ **运行时失败** |
| 网络错误 | 未考虑 | ❌ **缺少错误处理** |

### 必要性审查（每行代码删掉会怎样？）

#### 样本A - React UserList

```javascript
const filteredUsers = users.filter(...)  // 删除？搜索功能失效
    user.name.toLowerCase()             // 删除？不区分大小写，可接受
        .includes(searchTerm.toLowerCase())

```

**不必要的代码**：
- `drop_params=True` - 在这个场景下不起作用

### 反向审（假设这是AI生成的，它最可能隐瞒的3个弱点）

#### AI代码的典型隐瞒弱点

**弱点1：未验证的外部依赖假设**
```
AI不会说："我不确定MINIMUM_PROMPT_CACHE_TOKEN_COUNT的实际值"
AI会说："根据缓存策略，预计节省40%成本"
```
- 问题：AI基于假设而非验证做出结论
- 后果：边界条件导致假设失效时无人知晓

**弱点2：过于自信的"完成"声明**
```
AI说："任务完成"、"测试通过"、"build成功"
但从未说："我没有验证的前提假设是..."
```
- 问题：缺乏不确定性表达
- 后果：用户信任AI的声明而跳过人工审查

**弱点3：隐蔽的复杂度引入**
```
AI生成代码可能：
- 引入不必要的抽象层
- 添加看似有用实则冗余的适配器
- 在简单问题上使用复杂模式
```
- 案例：Claude Code在8小时会话中创建MQTTServiceAdapter、consumerWrapper等
- 后果：代码膨胀，维护困难

## 发现总结

### 关键问题

1. **性能陷阱**（样本A）
   - 每次渲染触发O(n*logn)复杂度的完整计算
   - 1000条数据下每次输入耗时5-8ms，用户感知卡顿

2. **假设未验证**（样本B）
   - AI假设外部库行为，未验证关键常量
   - "drop_params=True"在特定场景是no-op
   - 导致生产环境runtime失败

3. **内存泄漏**（React WebSocket示例）
   - useEffect缺少清理函数
   - roomId变化时旧连接未关闭

4. **安全漏洞**（搜索结果案例）
   - SQL拼接而非参数化查询
   - 前端隐藏入口不保护后端API

### 改进建议

1. **添加AI生成代码审查清单**
   - [ ] 性能：是否有重复计算？
   - [ ] 边界：空输入、极端值测试过吗？
   - [ ] 依赖：外部库行为假设验证过吗？
   - [ ] 安全：输入验证了吗？SQL参数化了吗？
   - [ ] 清理：副作用有清理函数吗？

2. **建立团队AI代码规范**
   - 所有AI生成代码必须经过人工审查
   - 关键业务逻辑禁止依赖AI独立完成
   - 必须进行单元测试和安全扫描

3. **AI审查的AI（对抗性审查）**
   - 使用第二个AI模型进行对抗性审查
   - 验证前提假设和边界条件
   - 检查外部依赖的实际行为
