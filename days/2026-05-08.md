# 代码审查练习 - 2026-05-08

## 审查概览

今日聚焦：**Spring Boot @Transactional 静默失败**——5个在银行后端（支付/转账/风控）场景中致命的事务Bug。核心线索：**你的事务真的生效了吗？**

> 关键发现：所有5个Bug共享同一本质——**绕过了代理**。自调用走this、private方法无法被拦截、checked异常默认提交、REQUIRES_NEW在连接池耗尽时死锁、readOnly静默丢弃写入。在银行场景下，这些Bug意味着**钱可以无声地消失**。

## 样本A：银行转账服务——Checked异常导致资金丢失

**来源**：Dominik Paszek《Spring Boot @Transactional: 5 Bugs That Are Probably in Your Production Code》(2026.03) + 银行支付场景适配
**背景**：银行跨行转账，需调用外部合规API进行反洗钱校验，该调用抛出IOException

### 原始代码（AI典型生成）

```java
@Service
public class TransferService {

    @Autowired
    private AccountRepository accountRepository;
    @Autowired
    private ComplianceClient complianceClient;
    @Autowired
    private TransferLogRepository transferLogRepository;

    @Transactional
    public TransferResult transfer(Long fromId, Long toId, BigDecimal amount)
            throws IOException {
        // 1. 扣款
        Account from = accountRepository.findById(fromId).orElseThrow();
        from.debit(amount);
        accountRepository.save(from);  // ← 已持久化

        // 2. 合规校验（外部API调用）
        complianceClient.checkAntiMoneyLaundering(from, amount);  // ← 抛IOException

        // 3. 入账
        Account to = accountRepository.findById(toId).orElseThrow();
        to.credit(amount);
        accountRepository.save(to);

        // 4. 记录转账日志
        transferLogRepository.save(new TransferLog(fromId, toId, amount));

        return TransferResult.success();
    }
}
```

### Step 2：四层审查

**第1轮：数据流**
- 输入：fromId, toId, amount → Account查找 → 扣款 → 合规校验 → 入账 → 日志
- 中间变更：from余额减少（已flush到DB）、to余额增加（未执行）
- 输出：TransferResult 或 IOException
- **致命断裂**：`complianceClient`抛出IOException时，from.debit已经持久化，但to.credit从未执行。Spring默认对checked异常不回滚，**事务提交**。

**第2轮：边界条件**
- ❌ **Checked异常不回滚**：IOException是checked exception，Spring默认提交事务。from账户扣了钱，to账户没收到——资金凭空消失
- ❌ **外部调用无超时保护**：complianceClient如果长时间无响应，事务一直挂起，占用数据库连接
- ❌ **账户不存在时**：`orElseThrow()`抛NoSuchElementException(RuntimeException)，这反而会回滚——但错误信息对用户不友好
- ❌ **金额为0或负数**：无校验，debit可能接受非法金额
- ❌ **并发重复转账**：同一账户并发转账，余额可能被覆盖（缺少乐观锁或SELECT FOR UPDATE）
- ❌ **事务内远程调用**：complianceClient是网络IO，放在事务内会导致长事务，锁住数据库资源

**第3轮：必要性**
- `throws IOException` —— 如果改为内部捕获并抛RuntimeException，则可避免checked异常问题
- 合规校验放在事务内 —— 可否提前到事务外执行？如果校验不通过就不开启事务
- TransferLog —— 是否必须和转账在同一事务？日志丢失可否接受？

**反向审——AI最不确定的3个地方**
1. `complianceClient`的异常类型不确定——如果它抛的是RuntimeException呢？（那反而会回滚，但不可控）
2. `accountRepository.save()`是否立即flush？取决于JPA实现，可能在commit时才flush
3. 余额校验逻辑在`debit()`内部——如果debit允许透支呢？

### 修复方案

```java
@Service
public class TransferService {

    @Autowired private AccountRepository accountRepository;
    @Autowired private ComplianceClient complianceClient;
    @Autowired private TransferLogRepository transferLogRepository;
    @Autowired private ApplicationEventPublisher eventPublisher;

    // 先校验，再开事务——缩短事务范围
    public TransferResult transfer(Long fromId, Long toId, BigDecimal amount) throws IOException {
        // 1. 合规校验（事务外，失败则直接返回，不浪费事务资源）
        Account from = accountRepository.findById(fromId).orElseThrow();
        complianceClient.checkAntiMoneyLaundering(from, amount);
        
        // 2. 事务内只做DB操作
        return doTransfer(fromId, toId, amount);
    }

    @Transactional(rollbackFor = Exception.class)  // ← 关键修复
    public TransferResult doTransfer(Long fromId, Long toId, BigDecimal amount) {
        Account from = accountRepository.findById(fromId)
                .orElseThrow(() -> new BusinessException("转出账户不存在"));
        Account to = accountRepository.findById(toId)
                .orElseThrow(() -> new BusinessException("转入账户不存在"));

        if (amount.compareTo(BigDecimal.ZERO) <= 0) {
            throw new BusinessException("转账金额必须大于0");
        }

        from.debit(amount);
        to.credit(amount);
        accountRepository.save(from);
        accountRepository.save(to);

        // 异步记录日志，不阻塞主事务
        eventPublisher.publishEvent(new TransferCompletedEvent(fromId, toId, amount));

        return TransferResult.success();
    }
}
```

**审查要点提炼**：
| 检查项 | 风险等级 | 说明 |
|--------|---------|------|
| @Transactional无rollbackFor | 🔴 Critical | checked异常默认提交，银行场景必加rollbackFor=Exception.class |
| 事务内远程调用 | 🔴 Critical | 网络IO导致长事务，应前置到事务外 |
| 账户余额并发安全 | 🔴 Critical | 缺少乐观锁/悲观锁，需@Version或SELECT FOR UPDATE |
| 异常信息可读性 | 🟡 Important | orElseThrow默认异常对用户无意义 |
| 转账日志与主事务耦合 | 🟢 Suggestion | 可用事件解耦，避免日志失败影响转账 |

## 样本B：订单服务——自调用导致事务失效 + REQUIRES_NEW死锁

**来源**：同上文章，结合订单+审计场景
**背景**：银行支付订单创建后需要写审计日志，开发者用REQUIRES_NEW确保审计独立事务

### 原始代码（AI典型生成）

```java
@Service
public class PaymentOrderService {

    @Autowired private OrderRepository orderRepository;
    @Autowired private AuditService auditService;
    @Autowired private RiskCheckService riskCheckService;

    public void createPaymentOrder(PaymentOrder order) {
        // 风控校验
        riskCheckService.validate(order);
        // 创建订单
        saveOrder(order);  // ← this.saveOrder()，绕过代理！
        // 审计日志
        auditService.logAudit("Order created: " + order.getId());
    }

    @Transactional
    public void saveOrder(PaymentOrder order) {
        orderRepository.save(order);
        order.getItems().forEach(item -> {
            item.setOrderId(order.getId());
            // 其他业务逻辑
        });
        // 如果此处抛异常 → 不回滚！因为事务从未开启
    }
}

@Service
public class AuditService {

    @Autowired private AuditLogRepository auditRepository;

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void logAudit(String message) {
        auditRepository.save(new AuditLog(message));
    }
}
```

### Step 2：四层审查

**第1轮：数据流**
- 输入：PaymentOrder → 风控校验 → saveOrder(自调用) → 审计日志
- 中间：saveOrder内orderRepository.save → item关联设置
- 输出：无返回值（void）
- **致命断裂**：`saveOrder`通过`this`调用，代理未拦截，@Transactional无效

**第2轮：边界条件**
- ❌ **自调用绕过代理**：saveOrder标注了@Transactional但实际不走代理，异常不会触发回滚
- ❌ **REQUIRES_NEW死锁**：10个并发请求各占1个连接（HikariCP默认10），再请求第2个连接用于审计→连接池耗尽→死锁
- ❌ **审计失败影响主流程**：auditService.logAudit如果抛异常，会在外层事务中传播
- ❌ **order.getItems()可能为null**：缺少空判断
- ❌ **审计日志内容简单拼接**：敏感信息可能泄露到日志

**第3轮：必要性**
- `saveOrder`不需要单独一个方法——可以直接内联到createPaymentOrder并标注@Transactional
- REQUIRES_NEW——审计日志真需要独立事务吗？如果审计失败，是否可以接受丢日志？
- 风控校验放在createPaymentOrder内——可否更早执行，避免浪费事务资源？

**反向审——AI最不确定的3个地方**
1. `riskCheckService.validate`是否是远程调用？如果是，不应该放在事务内
2. `order.getItems()`返回的是Lazy Collection还是已加载的？如果在事务外调用会LazyInitializationException
3. REQUIRES_NEW获取新连接失败时，是抛异常还是阻塞等待？——阻塞等待，无超时

### 修复方案

```java
@Service
public class PaymentOrderService {

    @Autowired private OrderRepository orderRepository;
    @Autowired private ApplicationEventPublisher eventPublisher;
    @Autowired private RiskCheckService riskCheckService;

    // 风控前置，事务内只做DB操作
    @Transactional(rollbackFor = Exception.class)
    public void createPaymentOrder(PaymentOrder order) {
        // 1. 风控校验（放在事务内因为需要DB数据，但应尽量快）
        riskCheckService.validate(order);
        
        // 2. 保存订单（已在代理方法内，事务生效）
        orderRepository.save(order);
        
        if (order.getItems() != null) {
            order.getItems().forEach(item -> item.setOrderId(order.getId()));
        }

        // 3. 发布事件，而非直接调用审计
        eventPublisher.publishEvent(new OrderCreatedEvent(order.getId()));
    }
}

@Component
public class AuditEventHandler {

    @Autowired private AuditLogRepository auditRepository;

    // 事务提交后执行，不占用主事务连接
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void handleOrderCreated(OrderCreatedEvent event) {
        auditRepository.save(new AuditLog("Order created: " + event.getOrderId()));
    }
}
```

**审查要点提炼**：
| 检查项 | 风险等级 | 说明 |
|--------|---------|------|
| 自调用绕过代理 | 🔴 Critical | this.method()不走代理，@Transactional无效 |
| REQUIRES_NEW连接池死锁 | 🔴 Critical | 并发下连接池耗尽，应用冻结无异常 |
| 审计与业务事务耦合 | 🟡 Important | 用@TransactionalEventListener(AFTER_COMMIT)解耦 |
| 集合空指针 | 🟡 Important | getItems()可能返回null |

## 样本C：支付服务——private方法+readOnly陷阱

**来源**：同上文章Bug#3+#5，银行场景适配
**背景**：银行产品服务类，类级别标注readOnly=true，个别方法需要写入

### 原始代码（AI典型生成）

```java
@Service
@Transactional(readOnly = true)
public class ProductRateService {

    @Autowired private ProductRepository productRepository;
    @Autowired private RateChangeLogRepository rateChangeLogRepository;

    // 更新产品利率——需要写入！
    @Transactional  // ← 想覆盖readOnly，但...
    private void updateRate(Long productId, BigDecimal newRate) {  // ← private!
        Product p = productRepository.findById(productId).orElseThrow();
        p.setRate(newRate);
        // Hibernate不会flush — readOnly=true生效，且private方法代理无法拦截
        // 双重静默失败！
    }

    // 查询产品列表——纯读取，OK
    public List<Product> listProducts(String category) {
        return productRepository.findByCategory(category);
    }

    // 批量更新利率
    public void batchUpdateRates(Map<Long, BigDecimal> rateMap) {
        rateMap.forEach((productId, newRate) -> {
            updateRate(productId, newRate);  // ← this.updateRate，双重问题
        });
    }
}
```

### Step 2：四层审查

**第1轮：数据流**
- 输入：rateMap → 逐个updateRate → 修改Product.rate
- 中间：p.setRate(newRate) 修改了托管实体
- 输出：void（无返回值确认）
- **双重静默失败**：①private方法代理不拦截→事务未开启→readOnly标注也无效→但Hibernate默认flush模式仍受类级readOnly影响；②即使改为public，类级readOnly=true会禁用dirty checking→修改不被flush

**第2轮：边界条件**
- ❌ **private + @Transactional**：CGLIB无法override private方法，注解完全无效
- ❌ **readOnly=true禁用flush**：即使事务开启，Hibernate也不flush托管实体的修改
- ❌ **双重静默**：不抛异常、不写日志、数据就是丢了
- ❌ **批量操作无事务边界**：batchUpdateRates本身无@Transactional，逐个updateRate（即使生效）也是独立事务
- ❌ **rateMap遍历顺序不确定**：如果产品间有依赖关系（如联动利率），顺序可能影响结果
- ❌ **newRate无范围校验**：负利率？超过100%？

**第3轮：必要性**
- `private`修饰——改为public即可修复代理问题
- 方法级@Transactional——覆盖类级readOnly=true，如果方法改为public则生效
- rateMap.forEach——如果批量更新需要原子性，应该用@Transactional包裹batchUpdateRates

**反向审——AI最不确定的3个地方**
1. `p.setRate()`是否会触发dirty checking？——在readOnly=true下不会，readOnly=false下会
2. batchUpdateRates中部分成功部分失败怎么办？——当前无原子性保证
3. rateMap为空时是否有问题？——不会，forEach跳过空集合

### 修复方案

```java
@Service
@Transactional(readOnly = true)
public class ProductRateService {

    @Autowired private ProductRepository productRepository;
    @Autowired private RateChangeLogRepository rateChangeLogRepository;

    // ✅ public + @Transactional 覆盖 readOnly
    @Transactional(rollbackFor = Exception.class)  // readOnly=false + rollbackFor
    public void updateRate(Long productId, BigDecimal newRate) {
        if (newRate.compareTo(BigDecimal.ZERO) < 0) {
            throw new BusinessException("利率不能为负数");
        }
        Product p = productRepository.findById(productId)
                .orElseThrow(() -> new BusinessException("产品不存在"));
        BigDecimal oldRate = p.getRate();
        p.setRate(newRate);
        // dirty checking now active, will flush at commit ✓
        rateChangeLogRepository.save(
            new RateChangeLog(productId, oldRate, newRate, LocalDateTime.now()));
    }

    // ✅ 批量更新包裹在事务内
    @Transactional(rollbackFor = Exception.class)
    public void batchUpdateRates(Map<Long, BigDecimal> rateMap) {
        rateMap.forEach(this::updateRate);  // 通过代理调用，事务传播为REQUIRED
    }

    public List<Product> listProducts(String category) {
        return productRepository.findByCategory(category);
    }
}
```

**审查要点提炼**：
| 检查项 | 风险等级 | 说明 |
|--------|---------|------|
| private + @Transactional | 🔴 Critical | 代理无法拦截，注解完全无效 |
| readOnly=true静默丢弃写入 | 🔴 Critical | 无异常无警告，数据丢失 |
| 批量操作无事务 | 🟡 Important | 部分成功部分失败，数据不一致 |
| 利率无范围校验 | 🟡 Important | 负利率、超限利率 |

## 样本D：Java 22并发——Virtual Thread + synchronized + 连接泄漏

**来源**：Mark AI Code《Fix AI-Generated Java v22 Concurrency Bugs》+ 银行账户转账场景适配
**背景**：银行使用Java 22 Virtual Threads处理高并发转账请求，AI生成的代码使用synchronized保护转账操作

### 原始代码（AI典型生成）

```java
@Service
public class AccountTransferService {

    // AI认为synchronized可以保证线程安全
    public synchronized TransferResult transfer(
            Account from, Account to, BigDecimal amount) {
        from.withdraw(amount);
        to.deposit(amount);
        auditLog.record(from.getId(), to.getId(), amount);
        return TransferResult.success();
    }

    // AI生成的"线程安全"活跃用户追踪
    private List<Account> activeAccounts = Collections.synchronizedList(new ArrayList<>());

    public void trackActive(Account account) {
        activeAccounts.add(account);
    }

    public void cleanInactive() {
        for (Account acc : activeAccounts) {  // ← 遍历
            if (acc.isInactive()) {
                activeAccounts.remove(acc);   // ← ConcurrentModificationException!
            }
        }
    }

    // AI生成的懒加载连接池
    private volatile Connection poolConnection;

    public Connection getPoolConnection() {
        if (poolConnection == null) {
            synchronized (this) {
                if (poolConnection == null) {
                    poolConnection = createConnection();  // ← double-checked locking
                }
            }
        }
        return poolConnection;
    }
}
```

### Step 2：四层审查

**第1轮：数据流**
- 输入：from, to, amount → synchronized转账 → 返回结果
- 中间：withdraw → deposit → audit
- 输出：TransferResult
- **问题**：synchronized锁住了整个this对象，所有转账串行执行——高并发下吞吐量极低

**第2轮：边界条件**
- ❌ **synchronized阻塞Virtual Thread载体线程**：Virtual Thread挂载在载体线程(carrier thread)上，synchronized会pin住载体线程，导致载体线程无法调度其他Virtual Thread。并发量大时，所有载体线程被pin住，系统假死
- ❌ **synchronized粒度太粗**：A→B和C→D本可以并行，但被同一个锁串行化
- ❌ **Collections.synchronizedList遍历删除**：迭代中删除触发ConcurrentModificationException（即使在单线程下！）
- ❌ **double-checked locking不安全**：在Java 22中虽然volatile语义正确，但模式本身容易出错，且connection不是可重入的——多个线程共享同一个Connection！
- ❌ **共享单一Connection**：这不是连接池，是连接共享——并发请求会争抢同一个Connection，导致事务交叉
- ❌ **转账无事务**：withdraw和deposit在不同时刻，中间失败无法回滚

**第3轮：必要性**
- `synchronized`——完全可以去掉，由数据库事务保证原子性（SELECT FOR UPDATE）
- `Collections.synchronizedList`——用ConcurrentHashMap或ConcurrentLinkedQueue替代
- `double-checked locking`——用Initialization-on-demand holder pattern替代
- `共享单一Connection`——使用真正的连接池（HikariCP）

**反向审——AI最不确定的3个地方**
1. `auditLog.record`是同步还是异步？如果是远程调用，不应该放在synchronized块内
2. `Account`对象是JPA托管实体吗？如果是，synchronized无法防止数据库层面的并发问题
3. `createConnection()`创建的是什么类型的Connection？如果是JDBC Connection，它不是线程安全的

### 修复方案

```java
@Service
public class AccountTransferService {

    @Autowired private AccountRepository accountRepository;
    @Autowired private AuditEventPublisher auditPublisher;
    @Autowired private DataSource dataSource;  // HikariCP连接池

    // ✅ 用数据库事务+行锁替代synchronized
    @Transactional(rollbackFor = Exception.class)
    public TransferResult transfer(Long fromId, Long toId, BigDecimal amount) {
        // 按ID排序加锁，防止死锁（A→B和B→A同时执行）
        Long firstId = Math.min(fromId, toId);
        Long secondId = Math.max(fromId, toId);
        
        Account first = accountRepository.findByIdForUpdate(firstId);  // SELECT FOR UPDATE
        Account second = accountRepository.findByIdForUpdate(secondId);
        
        Account from = firstId.equals(fromId) ? first : second;
        Account to = firstId.equals(toId) ? first : second;
        
        from.withdraw(amount);
        to.deposit(amount);
        
        // 异步审计，不占用事务时间
        auditPublisher.publishAsync(new TransferAuditEvent(fromId, toId, amount));
        
        return TransferResult.success();
    }

    // ✅ 使用ConcurrentHashMap追踪活跃账户
    private final ConcurrentHashMap<Long, Account> activeAccounts = new ConcurrentHashMap<>();

    public void trackActive(Account account) {
        activeAccounts.put(account.getId(), account);
    }

    public void cleanInactive() {
        activeAccounts.entrySet().removeIf(e -> e.getValue().isInactive());
    }

    // ✅ 使用holder pattern懒加载（如果确实需要）
    private static class ConnectionHolder {
        // 实际项目应使用DataSource连接池，而非单连接
        static final DataSource INSTANCE = createDataSource();
        
        private static DataSource createDataSource() {
            HikariConfig config = new HikariConfig();
            config.setJdbcUrl("jdbc:postgresql://localhost/bank");
            config.setMaximumPoolSize(20);
            return new HikariDataSource(config);
        }
    }
    
    public DataSource getDataSource() {
        return ConnectionHolder.INSTANCE;
    }
}
```

**审查要点提炼**：
| 检查项 | 风险等级 | 说明 |
|--------|---------|------|
| synchronized阻塞Virtual Thread | 🔴 Critical | 载体线程被pin，高并发下系统假死 |
| Collections.synchronizedList遍历删除 | 🔴 Critical | ConcurrentModificationException |
| 共享单一JDBC Connection | 🔴 Critical | 多线程共享导致事务交叉 |
| double-checked locking反模式 | 🟡 Important | 用holder pattern替代 |
| 转账无数据库事务 | 🔴 Critical | withdraw/deposit不原子 |
| 锁粒度太粗 | 🟡 Important | 应使用行级锁，按ID排序防死锁 |

## Step 3：审美与架构评估

### 代码可读性

| 维度 | 评价 | 说明 |
|------|------|------|
| 命名 | 🟡 | transfer/saveOrder/updateRate尚可，但缺乏业务语义（如crossBankTransfer） |
| 函数粒度 | 🔴 | transfer方法混合了校验、持久化、远程调用，职责不清 |
| 异常处理 | 🔴 | 大量静默失败——private方法注解无效、readOnly丢弃写入、checked异常提交 |
| 防御性编程 | 🔴 | 几乎没有输入校验，orElseThrow使用默认异常 |

### 设计模式评估

**过度设计**：无——反而是设计不足
**设计不足**：
1. **事务边界模糊**：业务逻辑、远程调用、审计日志混在同一事务内
2. **缺少事件驱动**：审计、通知等副作用应通过事件解耦
3. **缺少Repository的查询方法**：findByIdForUpdate等行级锁查询未定义

### 架构层面

**核心架构问题——事务边界与连接管理**

```
❌ 当前架构：
Controller → Service(事务+远程调用+审计) → Repository
                  ↓
              资源浪费：事务持有连接期间做网络IO

✅ 应有架构：
Controller → Service(编排层) → ComplianceService(校验，事务外)
              ↓
          TransactionalService(纯DB操作，事务内) → Repository
              ↓
          AuditEventHandler(@TransactionalEventListener AFTER_COMMIT)
```

**关键原则**：
1. **事务越短越好**——事务内只做数据库操作
2. **远程调用前置**——校验通过后再开事务
3. **副作用后置**——审计、通知等用事件异步处理
4. **连接池容量规划**——REQUIRES_NEW需要额外连接，必须确保连接池足够大

### Java特有审查积累

| 模式 | 陷阱 | 审查Checklist |
|------|------|---------------|
| @Transactional | self-invocation绕过代理 | [ ] 是否有this.xxx()调用@Transactional方法？ |
| @Transactional | checked异常默认提交 | [ ] 是否显式声明rollbackFor=Exception.class？ |
| @Transactional | private/final方法无效 | [ ] @Transactional方法是否为public？ |
| @Transactional | REQUIRES_NEW连接池耗尽 | [ ] REQUIRES_NEW是否用AFTER_COMMIT解耦？ |

## Step 4：今日模式积累

### 新增审查模式

**模式：静默失败三连击（Silent Failure Triple）**
- 自调用 + checked异常 + readOnly陷阱
- 这三个Bug的共同特征：**代码看起来正确、编译通过、测试可能通过、生产中静默出错**
- 在银行场景中特别危险：资金变动无声地出错

**模式：事务范围膨胀（Transaction Scope Bloat）**
- 事务内包含远程调用、复杂计算、审计写入
- 导致长事务、连接占用、锁等待
- 修复：事务前置校验 + 事务内纯DB + 事件驱动后置

**模式：连接池饥饿死锁（Connection Pool Starvation Deadlock）**
- REQUIRES_NEW在并发下需要2倍连接
- 死锁时无异常、无日志、应用冻结
- 修复：AFTER_COMMIT事件 + 连接池容量 = 并发量 × 1.5

### Cheat Sheet更新

```
@Transactional审查速查（银行场景版）：
1. rollbackFor=Exception.class → 必加，不讨论
2. 事务内只做DB操作 → 远程调用前置或异步
3. 方法必须是public → private/final注解无效
4. this.xxx()是陷阱 → 分离Bean或@Lazy自注入
5. readOnly类上的写方法 → 显式@Transactional覆盖
6. REQUIRES_NEW → 只在AFTER_COMMIT后使用
7. 连接池容量 → 并发量 × (1 + REQUIRES_NEW方法数)
```
