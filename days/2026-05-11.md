## 样本一：Swift VIPER 架构 - 好设计 ✅

**来源**: [SwiftfulThinking/SwiftfulStarterProject](https://github.com/SwiftfulThinking/SwiftfulStarterProject)

### 数据流分析
```
输入: 用户交互事件
    ↓
View (SwiftUI) → Presenter (ViewModel) → Interactor (业务逻辑)
    ↓
Router (导航) ← Entity (数据模型)
    ↓
输出: UI状态更新 + 导航指令
```

### 关键设计亮点

**1. 协议抽象实现依赖解耦**
```swift
// ✅ 好的设计：数据层抽象为协议
protocol UserRepositoryProtocol {
    func fetchUser(id: String) async throws -> User
    func updateUser(_ user: User) async throws
}

// 具体实现可以随时替换（Firebase/Local/CoreData）
struct FirebaseUserRepository: UserRepositoryProtocol { ... }
```

**跨语言借鉴**:
- Java: 使用 Interface + Dependency Injection
- JavaScript: 使用 Protocol/TypeScript interface
- Go: 使用 Interface (隐式实现)

**2. 职责边界清晰**
```
View:       仅负责UI渲染，0业务逻辑
Presenter:  格式化数据，触发Interactor
Interactor: 纯业务逻辑，不触碰UI
Router:     导航逻辑独立
Entity:     数据模型，无行为
```

**3. 测试友好设计**
```swift
// ✅ Mock实现可以完全替换真实实现
class MockUserRepository: UserRepositoryProtocol {
    func fetchUser(id: String) async throws -> User {
        return User(id: "mock", name: "Test User")
    }
}
```

### 审查结论
| 维度 | 评分 | 说明 |
|------|------|------|
| 可读性 | ⭐⭐⭐⭐⭐ | 职责单一，命名清晰 |
| 可测试性 | ⭐⭐⭐⭐⭐ | 依赖注入使Mock轻而易举 |
| 扩展性 | ⭐⭐⭐⭐⭐ | 新增功能只需新增Module |
| 过度设计 | ⚠️ 需警惕 | 小型App可能显得冗余 |

## 样本二：JavaScript/React 性能反模式 🔴

**来源**: [拯救 AI 生成的烂代码 - Vibe Coding 重构指南](http://m.toutiao.com/group/7631767146644701759/)

### 第1轮：数据流分析

```javascript
// ❌ 反模式代码
function UserList({ users }) {
  const [searchTerm, setSearchTerm] = useState('');
  const [sortField, setSortField] = useState('name');
  
  // 🔴 每次渲染都重新计算！
  const filteredUsers = users.filter(user =>
    user.name.toLowerCase().includes(searchTerm.toLowerCase())
  );
  
  // 🔴 二次遍历 + 每次创建新数组
  const sortedUsers = [...filteredUsers].sort((a, b) => {
    if (sortField === 'name') {
      return a.name.localeCompare(b.name);
    }
    return a.age - b.age;
  });
  
  return (
    <div>
      <input value={searchTerm} onChange={(e) => setSearchTerm(e.target.value)} />
      {sortedUsers.map(user => <UserCard key={user.id} user={user} />)}
    </div>
  );
}
```

### 问题诊断

**第1轮 - 数据流问题**:
- 输入: `users` 数组、用户键盘输入
- 中间状态: `filteredUsers`, `sortedUsers` 每次渲染重建
- 输出: 渲染列表
- 🔴 **问题**: filter+sort 双遍历，用户输入触发完整重算

**第2轮 - 边界条件**:
- 🔴 空数组未处理
- 🔴 超长数组(1000+)性能崩溃
- 🔴 搜索词为空的边界情况未优化

**第3轮 - 必要性审查**:
```javascript
// ❓ [...filteredUsers] 是否必要？
// 答案: filter返回新数组，sort会修改原数组
// 但在React中直接sort可能引发原数组被修改的问题
// 所以spread是必要的，但可以与filter合并减少遍历
```

**反向审查 - AI可能隐瞒的弱点**:
1. 🔴 不会提醒你用 `useMemo` 缓存计算结果
2. 🔴 不会提醒你用 `useDeferredValue` 优化输入响应
3. 🔴 不会主动考虑虚拟列表(1000条数据时)

### 修复方案

```javascript
// ✅ 优化后代码
function UserList({ users }) {
  const [searchTerm, setSearchTerm] = useState('');
  const [sortField, setSortField] = useState('name');
  
  // ✅ 使用 useMemo 缓存计算结果
  const normalizedSearchTerm = useMemo(
    () => searchTerm.toLowerCase(),
    [searchTerm]
  );
  
  const processedUsers = useMemo(() => {
    // ✅ 一次遍历完成过滤
    const filtered = users.filter(user =>
      user.name.toLowerCase().includes(normalizedSearchTerm)
    );
    
    // ✅ 使用 Intl.Collator 提升排序性能
    const collator = new Intl.Collator('zh-CN');
    return filtered.sort((a, b) => {
      if (sortField === 'name') {
        return collator.compare(a.name, b.name);
      }
      return a.age - b.age;
    });
  }, [users, normalizedSearchTerm, sortField]);
  
  // ✅ 使用 useDeferredValue 优化输入响应
  const deferredUsers = useDeferredValue(processedUsers);
  
  return (
    <div>
      <input value={searchTerm} onChange={(e) => setSearchTerm(e.target.value)} />
      {deferredUsers.map(user => <UserCard key={user.id} user={user} />)}
    </div>
  );
}
```

## 样本三：WebSocket 内存泄漏 🔴

**来源**: 同上

```javascript
// ❌ 内存泄漏代码
function ChatRoom({ roomId }) {
  const [messages, setMessages] = useState([]);
  
  useEffect(() => {
    const ws = new WebSocket(`wss://api.example.com/chat/${roomId}`);
    
    ws.onmessage = (event) => {
      const newMessage = JSON.parse(event.data);
      setMessages(prev => [...prev, newMessage]);
    };
    
    // 🔴 没有清理函数！连接永不关闭
    // 🔴 roomId 变化时旧连接未关闭
  }, [roomId]);
  
  return <MessageList messages={messages} />;
}
```

### 问题诊断

**第1轮 - 数据流**:
- 输入: WebSocket消息流、`roomId` 变化
- 中间状态: `messages` 数组持续增长
- 输出: 渲染消息列表
- 🔴 **泄漏点**: 组件卸载时 `ws` 连接未关闭

**第2轮 - 边界条件**:
- 🔴 网络断线无重连机制
- 🔴 `roomId` 变化时多个连接同时存活
- 🔴 消息数组无限增长(无分页/限制)

**反向审查 - AI可能隐瞒**:
1. 🔴 不提 cleanup 函数
2. 🔴 不提重连逻辑
3. 🔴 不考虑消息数量上限

### 修复方案

```javascript
// ✅ 修复后
function ChatRoom({ roomId }) {
  const [messages, setMessages] = useState([]);
  const wsRef = useRef(null);
  
  useEffect(() => {
    let isMounted = true;
    let reconnectTimer = null;
    
    const connect = () => {
      const ws = new WebSocket(`wss://api.example.com/chat/${roomId}`);
      wsRef.current = ws;
      
      ws.onmessage = (event) => {
        if (isMounted) {
          const newMessage = JSON.parse(event.data);
          setMessages(prev => [...prev, newMessage]);
        }
      };
      
      ws.onclose = () => {
        if (isMounted) {
          reconnectTimer = setTimeout(connect, 3000);
        }
      };
    };
    
    connect();
    
    // ✅ 清理函数：关闭连接、取消重连
    return () => {
      isMounted = false;
      clearTimeout(reconnectTimer);
      if (wsRef.current?.readyState === WebSocket.OPEN) {
        wsRef.current.close();
      }
    };
  }, [roomId]);
  
  return <MessageList messages={messages} />;
}
```

## 跨语言模式对比

### 内存管理模式对比

| 语言 | 资源管理 | 自动GC | 手动清理 |
|------|----------|--------|----------|
| JavaScript | GC自动，但需要显式清理订阅/WebSocket | ✅ | ⚠️ 必需 |
| Swift | ARC自动引用计数 | ✅ | ✅ 闭包捕获需注意 |
| Go | GC + defer模式 | ✅ | ✅ defer确保清理 |
| Rust | 所有权系统 + 生命周期 | ✅ | ✅ Drop trait |

### Swift vs JavaScript 响应式模式

**Swift (Combine) - 推荐写法**:
```swift
// ✅ 响应式数据流 + 自动取消
class ViewModel: ObservableObject {
    @Published var users: [User] = []
    private var cancellables = Set<AnyCancellable>()
    
    func fetchUsers() {
        repository.fetchUsers()
            .receive(on: DispatchQueue.main)
            .sink(
                receiveCompletion: { _ in },
                receiveValue: { [weak self] users in
                    self?.users = users
                }
            )
            .store(in: &cancellables) // ✅ 自动取消
    }
}
```

**JavaScript - 对应模式**:
```javascript
// ✅ 清理函数对应 Swift 的 cancellables
useEffect(() => {
    const subscription = data$.subscribe(users => setUsers(users));
    return () => subscription.unsubscribe(); // ✅ 等价于 store(in:)
}, []);
```

## 今日模式库更新

### 新增反模式

| 反模式名称 | 特征 | 影响 | 修复方案 |
|-----------|------|------|----------|
| 渲染内重复计算 | 循环/filter/sort在render内 | 性能崩溃 | useMemo/useCallback |
| 资源未清理泄漏 | useEffect无return | 内存泄漏 | 添加cleanup函数 |
| 状态闭包捕获 | 闭包持有旧state引用 | 数据陈旧 | useRef + isMounted标志 |
| 无重连机制 | WebSocket断开无恢复 | 可用性降级 | 指数退避重连 |

### 新增设计模式

| 模式名称 | 适用场景 | Swift实现 | JS实现 |
|---------|---------|-----------|--------|
| 协议依赖注入 | 需要Mock测试 | `protocol X {}` | `interface X {}` |
| 响应式自动取消 | 订阅管理 | `cancellables.store(in:)` | `subscription.unsubscribe()` |
| 副作用清理 | 资源管理 | `defer` / cleanup | `useEffect return` |

## 关键发现总结

1. **AI生成代码的常见隐瞒点**:
   - 不提性能优化（useMemo等）
   - 不提资源清理
   - 不提边界条件

2. **跨语言通用智慧**:
   - 资源获取必有释放
   - 计算结果尽量缓存
   - 依赖变化要追踪

3. **架构设计原则**:
   - 单一职责 > 过度抽象
   - 显式优于隐式
   - 可测试性驱动设计
