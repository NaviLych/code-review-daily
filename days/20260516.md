## 一、主题：支付回调幂等、事务边界与外部副作用

**来源**：
- [Stripe API: Idempotent requests](https://docs.stripe.com/api/idempotent_requests?api-version=2024-11-20.acacia)
- [Spring Framework: Transaction Propagation](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/tx-propagation.html)

> 今日样本是模拟 AI 生成的银行支付回调处理器。它看起来完整：验签、查订单、更新状态、发积分、发短信。但审查重点不是代码是否“能跑”，而是它在重复回调、网络超时、并发请求、事务回滚和外部副作用下是否仍然保持资金一致性。

## 二、样本：AI 生成的支付回调处理器

### 2.1 问题代码

```java
@RestController
@RequestMapping("/api/payments")
public class PaymentCallbackController {
    private final OrderRepository orderRepository;
    private final PaymentRepository paymentRepository;
    private final PointClient pointClient;
    private final SmsClient smsClient;

    @PostMapping("/callback")
    @Transactional
    public ResponseEntity<String> handle(@RequestBody PaymentCallback callback) {
        if (!callback.verify()) {
            return ResponseEntity.status(401).body("invalid signature");
        }

        Order order = orderRepository.findByOrderNo(callback.getOrderNo()).orElseThrow();
        if ("PAID".equals(order.getStatus())) {
            return ResponseEntity.ok("success");
        }

        Payment payment = new Payment();
        payment.setOrderNo(callback.getOrderNo());
        payment.setTradeNo(callback.getTradeNo());
        payment.setAmount(callback.getAmount());
        payment.setStatus("SUCCESS");
        paymentRepository.save(payment);

        order.setStatus("PAID");
        order.setPaidAt(LocalDateTime.now());
        orderRepository.save(order);

        pointClient.addPoints(order.getUserId(), order.getAmount().intValue());
        smsClient.send(order.getPhone(), "支付成功");

        return ResponseEntity.ok("success");
    }
}
```

### 2.2 AI 最可能给出的解释

```text
该方法使用 @Transactional 保证订单和支付记录一起提交。
如果订单已经支付，直接返回 success，可以避免重复处理。
验签失败返回 401，成功后保存支付记录并通知用户。
```

**审查提醒**：这段解释把“数据库原子性”和“业务幂等性”混为一谈，也把外部接口调用当成了事务的一部分。AI 的话术很顺，但真正危险的地方恰好藏在它说得最自信的位置。

## 三、四层审查

## 第1轮：数据流

### 输入从哪来

- `PaymentCallback` 来自支付渠道 HTTP 回调，属于外部不可信输入。
- `orderNo`、`tradeNo`、`amount`、`status`、签名字段都来自外部。
- 回调天然可能重复、乱序、延迟到达。

### 中间变了什么

```text
callback
  -> verify()
  -> find order by orderNo
  -> if order.status == PAID return
  -> insert payment
  -> update order
  -> call point service
  -> call sms service
  -> return success
```

### 输出到哪去

- 写入 `payment` 表。
- 修改 `order` 表状态。
- 调用积分系统产生外部副作用。
- 调用短信系统产生外部副作用。
- 返回支付渠道 `success`。

### 数据流红旗

1. `amount` 没有与本地订单金额比对。
2. `tradeNo` 没有唯一约束语义。
3. “订单已支付”只能防重复订单状态，不能防重复支付流水。
4. 外部副作用发生在数据库事务尚未提交之前。

## 第2轮：边界条件

### 3.1 重复回调导致重复支付流水

**并发场景**：

```text
T1: 查询订单 status = WAIT_PAY
T2: 查询订单 status = WAIT_PAY
T1: insert payment(tradeNo=T20260516001)
T2: insert payment(tradeNo=T20260516001)
T1: update order = PAID
T2: update order = PAID
```

如果 `payment.trade_no` 没有唯一索引，重复流水会直接落库。即使有唯一索引，也会在第二次 `save` 抛异常，而方法当前没有把“重复回调”转成渠道期望的成功响应。

**审查问题**：

- [ ] `trade_no` 是否有数据库唯一索引？
- [ ] 幂等判断是否基于支付渠道唯一事件号或交易号，而不是只看订单状态？
- [ ] 唯一约束冲突是否被识别为幂等成功？

### 3.2 金额未校验

```java
payment.setAmount(callback.getAmount());
```

这行代码把外部金额当成事实。银行/支付场景必须用本地订单金额做强校验：

```java
if (order.getAmount().compareTo(callback.getAmount()) != 0) {
    throw new PaymentAmountMismatchException(order.getOrderNo());
}
```

**危险后果**：

- 小额回调把大额订单标记为已支付。
- 币种、精度、分转元处理错误。
- 测试环境金额绕过被带入生产。

### 3.3 事务里调用外部系统

```java
@Transactional
public ResponseEntity<String> handle(...) {
    ...
    pointClient.addPoints(...);
    smsClient.send(...);
}
```

Spring 官方文档说明 `REQUIRES_NEW` 会获取独立物理事务，资源仍可能受外层事务占用影响；这类传播语义会影响连接池消耗。更基本的问题是：HTTP 外部调用不受本地数据库事务控制。

**失败矩阵**：

| 场景 | 数据库 | 积分 | 短信 | 结果 |
|---|---|---|---|---|
| 积分成功，短信失败，事务回滚 | 未支付 | 已加积分 | 可能未发 | 资金状态与权益状态不一致 |
| 数据库提交成功，HTTP 响应超时 | 已支付 | 已加积分 | 已发 | 渠道重试，重复副作用 |
| 外部接口慢 | 连接长时间占用 | 未知 | 未知 | 连接池被支付回调拖垮 |

### 3.4 `orElseThrow()` 变成 500

```java
Order order = orderRepository.findByOrderNo(callback.getOrderNo()).orElseThrow();
```

外部回调引用不存在订单，不应让 `NoSuchElementException` 漏成 500。需要明确审计日志、告警、响应策略：

```java
Order order = orderRepository.findByOrderNo(callback.getOrderNo())
    .orElseThrow(() -> new UnknownPaymentOrderException(callback.getOrderNo()));
```

### 3.5 NPE 与字段合法性

`callback.verify()` 之前没有保证字段非空。常见边界：

- `callback == null`
- `orderNo == null`
- `tradeNo == null`
- `amount == null`
- `status` 不是成功态
- 签名时间戳过期

## 第3轮：必要性

### 每行代码删掉会怎样

```java
@Transactional
```

不能简单删，但应该缩小范围。外部调用不应放进事务。推荐把“确认支付”做成短事务，把通知和积分通过 outbox 异步执行。

```java
if ("PAID".equals(order.getStatus())) {
    return ResponseEntity.ok("success");
}
```

不能作为唯一幂等条件。它最多是快速路径，不是并发安全保证。

```java
paymentRepository.save(payment);
orderRepository.save(order);
```

必要，但顺序需要配合唯一约束、状态机和乐观锁/条件更新。

```java
pointClient.addPoints(...);
smsClient.send(...);
```

不应在主交易链路同步执行。短信可异步，积分要有幂等事件号。

### 能不能不写

- Controller 不应直接承载支付业务流程，应委托 `PaymentCallbackService`。
- 短信不是支付成功的必要条件，可以拆到事件订阅者。
- 积分也不是支付事务的一部分，应使用 outbox 保证“支付提交后至少投递一次，消费者幂等”。

## 第4轮：反向审查

让 AI 交代它最不确定的 3 个地方：

1. **我不确定支付渠道是否保证只回调一次。**
   实际上多数支付回调应按至少一次投递处理，业务侧必须幂等。

2. **我不确定 `@Transactional` 是否能覆盖积分和短信。**
   不能。它只管理本地事务资源，不能让远程 HTTP 副作用跟随数据库回滚。

3. **我不确定 `order.status == PAID` 是否足够防重。**
   不够。并发请求会同时看到旧状态，必须依赖数据库唯一约束、条件更新或锁。

## 四、建议修复版本

### 4.1 数据库约束

```sql
alter table payment add constraint uk_payment_trade_no unique (trade_no);
alter table payment add constraint uk_payment_event_id unique (event_id);
alter table orders add column version bigint not null default 0;
```

### 4.2 应用服务

```java
@Service
public class PaymentCallbackService {
    private final OrderRepository orderRepository;
    private final PaymentRepository paymentRepository;
    private final OutboxRepository outboxRepository;

    @Transactional
    public PaymentCallbackResult confirm(PaymentCallback callback) {
        validateCallback(callback);

        Order order = orderRepository.findByOrderNoForUpdate(callback.getOrderNo())
            .orElseThrow(() -> new UnknownPaymentOrderException(callback.getOrderNo()));

        if (order.isPaid()) {
            return PaymentCallbackResult.duplicateSuccess();
        }

        if (order.amountNotEquals(callback.getAmount())) {
            throw new PaymentAmountMismatchException(order.getOrderNo());
        }

        try {
            paymentRepository.save(Payment.successFrom(callback));
        } catch (DataIntegrityViolationException duplicate) {
            return PaymentCallbackResult.duplicateSuccess();
        }

        order.markPaid(callback.getTradeNo(), callback.getPaidAt());
        orderRepository.save(order);

        outboxRepository.save(OutboxEvent.paymentSucceeded(order));
        return PaymentCallbackResult.success();
    }
}
```

### 4.3 Controller 只做协议适配

```java
@PostMapping("/callback")
public ResponseEntity<String> handle(@RequestBody PaymentCallback callback) {
    PaymentCallbackResult result = callbackService.confirm(callback);
    return ResponseEntity.ok(result.channelResponse());
}
```

### 4.4 Outbox 消费者

```java
@Component
public class PaymentSucceededConsumer {
    public void handle(PaymentSucceededEvent event) {
        pointClient.addPoints(event.userId(), event.points(), event.eventId());
        smsClient.sendPaymentSuccess(event.phone(), event.orderNo());
    }
}
```

**关键点**：

- 主事务只处理本地一致性。
- 外部副作用由 outbox 驱动。
- 消费方必须使用 `eventId` 幂等。
- 支付回调返回成功不代表所有附属权益都同步完成。

## 五、审美与架构评估

### 可读性

**问题**：

- Controller 过胖，混合协议、校验、领域状态、外部调用。
- 字符串状态 `"PAID"`、`"SUCCESS"` 缺少枚举。
- `orElseThrow()` 语义贫血，不利于问题定位。

**改进**：

- `PaymentStatus`、`OrderStatus` 使用枚举。
- 异常类型表达业务原因。
- 领域方法使用 `order.markPaid(...)`，避免散落 setter。

### 设计模式

**过度设计风险**：

- 小系统不一定一开始就引入完整消息中间件。

**设计不足风险**：

- 支付链路没有幂等键、唯一索引、状态机、outbox，是明显设计不足。

**平衡方案**：

- 先用数据库 outbox 表，不急着引入 Kafka。
- 先把支付确认与外部通知拆开，再扩展异步消费者。

### 架构层面

推荐职责划分：

```text
PaymentCallbackController
  -> PaymentCallbackService
      -> PaymentVerifier
      -> OrderRepository
      -> PaymentRepository
      -> OutboxRepository
  -> OutboxDispatcher
      -> PointClient
      -> SmsClient
```

依赖方向：

- Controller 依赖应用服务。
- 应用服务依赖领域对象和仓储接口。
- 外部 HTTP Client 不进入领域对象。

### Java / Spring 特有审查点

- `@Transactional` 放在 public service 方法上，而不是 Controller。
- 同类自调用不会触发代理事务，事务方法不要藏在 private 方法里。
- 不在事务内执行慢 HTTP 调用。
- `REQUIRES_NEW` 可能额外占用连接池，不能拿它当万能补丁。
- 通过数据库唯一索引兜底幂等，而不是只依赖 Java if 判断。

## 六、今日沉淀

### 新增审查模式

#### 模式：状态判断不是幂等

**识别特征**：

- `if (status == DONE) return success`
- 缺少唯一索引或幂等表
- 没有处理并发双写

**审查句式**：

> 这个 if 能挡住串行重复请求，但挡不住并发重复请求。最终幂等必须落到数据库约束或原子条件更新。

#### 模式：事务里夹外部副作用

**识别特征**：

- `@Transactional` 方法中调用 HTTP、RPC、消息发送、短信、邮件
- catch 后继续提交或远程成功后本地回滚

**审查句式**：

> 本地事务不能回滚远程世界。先提交事实，再通过 outbox 投递副作用。

### 新增架构模式

#### 模式：支付确认 + Outbox

```text
短事务确认支付
  -> 插入支付流水
  -> 更新订单状态
  -> 写 outbox 事件
提交后异步分发
  -> 积分
  -> 短信
  -> 对账
```

**适用场景**：

- 支付回调
- 交易完成事件
- 账户权益发放
- 需要本地一致性与外部最终一致性的链路

## 七、今日一句话

支付代码里最危险的不是异常，而是“成功了一半”。审查 AI 生成的银行后端代码时，先问三件事：重复请求会怎样、外部副作用会怎样、数据库提交前后失败会怎样。
