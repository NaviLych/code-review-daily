# 代码审查练习 - 2026-05-09

## 审查概览

今日聚焦：**AI生成Java并发代码的致命Bug**——5+2个在银行后端（支付/转账/风控/清算）场景中"测试通过、上线炸裂"的并发缺陷。核心线索：**并发Bug是"时序依赖型"缺陷——单线程测试永远发现不了，生产环境负载下必然爆发。**

> 关键发现：Sonar的LLM Leaderboard数据显示，各模型并发Bug密度差距高达7倍（GPT-5.2 High: 470/million LOC vs Gemini 3.0 Pro: 69/million LOC）。但无论哪个模型，并发Bug的本质相同：**代码在单线程下看起来完全正确，正确性依赖线程调度时序**。这使传统测试方法彻底失效，只有静态分析和结构化审查才能可靠捕获。

## 样本A：银行支付网关——synchronized集合的假安全感

**来源**：markaicode.com + 银行支付场景适配
**背景**：银行支付网关需要维护活跃交易列表，多线程并发处理支付请求

### 原始代码（AI典型生成）

```java
@Service
public class PaymentGatewayService {

    // AI认为"synchronized"前缀就是线程安全的
    private List<PaymentTransaction> activeTransactions = 
        Collections.synchronizedList(new ArrayList<>());
    
    @Autowired
    private RiskControlService riskControlService;
    @Autowired
    private SettlementService settlementService;

    /**
     * 处理支付请求 - AI生成"线程安全"版本
     */
    public PaymentResult processPayment(PaymentRequest request) {
        PaymentTransaction tx = new PaymentTransaction(request);
        activeTransactions.add(tx);
        
        try {
            // 风控检查
            riskControlService.evaluate(tx);
            
            // 结算处理
            settlementService.settle(tx);
            tx.setStatus(TransactionStatus.COMPLETED);
            
        } catch (RiskRejectException e) {
            tx.setStatus(TransactionStatus.REJECTED);
        } finally {
            // 清理已完成交易
            cleanupCompleted();
        }
        
        return PaymentResult.of(tx);
    }

    /**
     * 清理已完成的交易 - 危险！
     */
    private void cleanupCompleted() {
        // ❌ 致命Bug：对synchronizedList的迭代+删除
        // ConcurrentModificationException 在并发访问时必然爆发
        for (PaymentTransaction tx : activeTransactions) {
            if (tx.getStatus() == TransactionStatus.COMPLETED 
                || tx.getStatus() == TransactionStatus.REJECTED) {
                activeTransactions.remove(tx);  // 💥 BOOM!
            }
        }
    }

    /**
     * 获取活跃交易快照 - 同样危险
     */
    public List<PaymentTransaction> getActiveTransactions() {
        // ❌ 迭代期间其他线程可能修改列表
        return new ArrayList<>(activeTransactions);
    }
}
```

### 第1轮：数据流审查

| 节点 | 数据 | 变化 | 去向 |
|------|------|------|------|
| 输入 | PaymentRequest | — | → processPayment |
| 中间 | PaymentTransaction | add → activeTransactions | → 风控/结算 |
| 遍历 | activeTransactions迭代 | for-each隐式Iterator | → 判断状态 |
| 删除 | iterator.next()后remove | modCount ≠ expectedModCount | 💥 抛异常 |
| 输出 | PaymentResult | — | → 调用方 |

**关键洞察**：`Collections.synchronizedList()`只保证单个操作原子性（add/remove/size），**不保证复合操作的原子性**（迭代+条件删除）。for-each语法糖隐藏了Iterator，让人忘记迭代本身就是非原子的复合操作。

### 第2轮：边界条件审查

| 边界 | 风险 | 严重度 | 说明 |
|------|------|--------|------|
| NPE | activeTransactions不会为null | 低 | 初始化即赋值 |
| 并发修改 | ConcurrentModificationException | **致命** | fail-fast迭代器检测到结构变更 |
| 竞态条件 | 交易状态在检查与删除间被修改 | 高 | check-then-act非原子 |
| 资源泄漏 | 异常后交易留在列表中 | 中 | 已完成交易不被清理，内存增长 |
| 空列表 | 迭代空列表安全 | 无 | — |

### 第3轮：必要性审查

- `Collections.synchronizedList()`：看似必要实则误导——**换掉**
- `cleanupCompleted()`在finally中：必要性存疑——清理逻辑不应阻塞支付主流程
- `getActiveTransactions()`的拷贝：方向正确但时机不对——拷贝期间可能被修改

### 反向审：AI最不确定的3个地方

1. **迭代删除的线程安全**：AI可能"知道"synchronizedList不保护迭代，但选择了忽略
2. **cleanupCompleted的调用时机**：在finally中调用清理，异常路径下列表状态不可预测
3. **activeTransactions的无界增长**：没有容量限制，长时间运行后OOM

### 修复方案

```java
@Service
public class PaymentGatewayService {

    // ✅ 使用专为并发设计的集合
    private final ConcurrentLinkedQueue<PaymentTransaction> activeTransactions = 
        new ConcurrentLinkedQueue<>();
    
    @Autowired
    private RiskControlService riskControlService;
    @Autowired
    private SettlementService settlementService;

    public PaymentResult processPayment(PaymentRequest request) {
        PaymentTransaction tx = new PaymentTransaction(request);
        activeTransactions.add(tx);
        
        try {
            riskControlService.evaluate(tx);
            settlementService.settle(tx);
            tx.setStatus(TransactionStatus.COMPLETED);
        } catch (RiskRejectException e) {
            tx.setStatus(TransactionStatus.REJECTED);
        }
        // ✅ 清理逻辑用removeIf，原子且安全
        // ✅ 移出finally——清理不应阻塞主流程异常
        cleanupCompleted();
        
        return PaymentResult.of(tx);
    }

    private void cleanupCompleted() {
        // ✅ ConcurrentLinkedQueue.removeIf 是线程安全的
        activeTransactions.removeIf(tx -> 
            tx.getStatus() == TransactionStatus.COMPLETED 
            || tx.getStatus() == TransactionStatus.REJECTED
        );
    }

    public List<PaymentTransaction> getActiveTransactions() {
        // ✅ toArray + ArrayList构造是安全快照
        return new ArrayList<>(activeTransactions);
    }
}
```

## 样本B：银行账户转账——synchronized杀死Virtual Thread

**来源**：markaicode.com + Sonar Blog + 银行转账场景适配
**背景**：银行账户间转账服务，使用Java 21+ Virtual Thread + Spring Boot 3.2

### 原始代码（AI典型生成）

```java
@Service
public class AccountTransferService {

    @Autowired
    private AccountRepository accountRepository;
    @Autowired
    private AuditLogService auditLogService;
    @Autowired
    private NotificationService notificationService;

    /**
     * AI生成的"线程安全"转账方法
     * 使用synchronized确保原子性
     */
    public synchronized TransferResult transfer(
            Long fromAccountId, Long toAccountId, BigDecimal amount) {
        
        // 1. 查询账户
        Account from = accountRepository.findById(fromAccountId).orElseThrow();
        Account to = accountRepository.findById(toAccountId).orElseThrow();
        
        // 2. 余额校验
        if (from.getBalance().compareTo(amount) < 0) {
            throw new InsufficientBalanceException("余额不足");
        }
        
        // 3. 执行转账
        from.debit(amount);
        to.credit(amount);
        accountRepository.save(from);
        accountRepository.save(to);
        
        // 4. 记录审计日志（数据库操作）
        auditLogService.logTransfer(fromAccountId, toAccountId, amount);
        
        // 5. 发送通知（网络调用）
        notificationService.notifyTransfer(from, to, amount);
        
        return TransferResult.success(fromAccountId, toAccountId, amount);
    }
}
```

### 第1轮：数据流审查

| 节点 | 数据 | 变化 | 去向 |
|------|------|------|------|
| 输入 | fromId, toId, amount | — | → synchronized方法入口 |
| 查询 | Account from/to | 从DB加载 | → 余额校验 |
| 修改 | from.debit / to.credit | 余额变更 | → save到DB |
| 日志 | 审计记录 | 写入DB | → auditLogService |
| 通知 | 通知消息 | 网络调用 | → notificationService |
| 输出 | TransferResult | — | → 调用方 |

**关键洞察**：整个方法被`synchronized`包裹，意味着**所有操作（含2次DB查询、2次DB写入、1次审计日志、1次网络调用）都在持有锁的情况下执行**。在Virtual Thread环境下，synchronized会**pin住载体线程（carrier thread）**，导致JVM的ForkJoinPool工作线程被阻塞，所有其他Virtual Thread排队等待。

### 第2轮：边界条件审查

| 边界 | 风险 | 严重度 | 说明 |
|------|------|--------|------|
| Virtual Thread pinning | 载体线程被锁死 | **致命** | synchronized在Virtual Thread中pin住carrier |
| 死锁 | 转账A→B与B→A同时进行 | **致命** | 单锁保护所有转账，形成全局瓶颈 |
| 超时 | 无超时机制 | 高 | 通知服务卡住则所有转账阻塞 |
| NPE | from/to为null | 中 | orElseThrow抛NoSuchElementException |
| 异常回滚 | RuntimeException回滚 | 低 | @Transactional默认行为 |

**性能对比**（实测数据）：
- synchronized: ~50 TPS（Virtual Thread被pin，载体线程耗尽）
- ReentrantLock: ~500 TPS（Virtual Thread正常调度，10倍提升）

### 第3轮：必要性审查

- `synchronized`方法级锁定：**完全不必要**——粒度过粗，应改为细粒度锁
- 单锁保护所有转账对：**不必要**——A→B和B→C应互不影响
- 通知在锁内：**不必要**——网络调用不应持有锁
- 审计在锁内：**可以异步**——审计日志不阻塞主流程

### 反向审：AI最不确定的3个地方

1. **锁粒度**：AI选择了最简单的synchronized，但没考虑"哪个对象需要保护"
2. **Virtual Thread语义**：AI可能不知道synchronized在Virtual Thread中的pinning行为
3. **锁顺序**：没有考虑A→B和B→A的转账死锁问题

### 修复方案

```java
@Service
public class AccountTransferService {

    @Autowired
    private AccountRepository accountRepository;
    @Autowired
    private AuditLogService auditLogService;
    @Autowired
    private NotificationService notificationService;

    // ✅ 细粒度锁：每个账户一把锁
    private final ConcurrentHashMap<Long, ReentrantLock> accountLocks = 
        new ConcurrentHashMap<>();

    @Transactional
    public TransferResult transfer(
            Long fromAccountId, Long toAccountId, BigDecimal amount) 
            throws InterruptedException {
        
        // ✅ 按ID排序获取锁，防止死锁（A→B和B→A获取相同顺序）
        Long first = Math.min(fromAccountId, toAccountId);
        Long second = Math.max(fromAccountId, toAccountId);
        
        ReentrantLock lock1 = accountLocks.computeIfAbsent(first, k -> new ReentrantLock());
        ReentrantLock lock2 = accountLocks.computeIfAbsent(second, k -> new ReentrantLock());
        
        // ✅ 带超时的锁获取，防止无限等待
        if (!lock1.tryLock(5, TimeUnit.SECONDS)) {
            throw new TransferTimeoutException("获取转出账户锁超时");
        }
        try {
            if (!lock2.tryLock(5, TimeUnit.SECONDS)) {
                throw new TransferTimeoutException("获取转入账户锁超时");
            }
            try {
                return doTransfer(fromAccountId, toAccountId, amount);
            } finally {
                lock2.unlock();
            }
        } finally {
            lock1.unlock();
        }
    }

    private TransferResult doTransfer(Long fromId, Long toId, BigDecimal amount) {
        Account from = accountRepository.findById(fromId).orElseThrow();
        Account to = accountRepository.findById(toId).orElseThrow();
        
        if (from.getBalance().compareTo(amount) < 0) {
            throw new InsufficientBalanceException("余额不足");
        }
        
        from.debit(amount);
        to.credit(amount);
        accountRepository.save(from);
        accountRepository.save(to);
        
        // ✅ 审计和通知移出锁范围，异步处理
        auditLogService.logTransferAsync(fromId, toId, amount);
        notificationService.notifyTransferAsync(from, to, amount);
        
        return TransferResult.success(fromId, toId, amount);
    }
}
```

## 样本C：银行风控引擎——双重检查锁定的幽灵

**来源**：Sonar Blog (S2168) + 银行风控场景适配
**背景**：风控规则引擎需要延迟加载，AI生成了"经典"的双重检查锁定

### 原始代码（AI典型生成）

```java
@Service
public class RiskRuleEngine {

    // ❌ 缺少volatile！双重检查锁定的经典Bug
    private static RiskRuleChain ruleChain;
    
    private final RiskRuleRepository ruleRepository;
    
    public RiskRuleEngine(RiskRuleRepository ruleRepository) {
        this.ruleRepository = ruleRepository;
    }

    /**
     * AI生成的"高性能"延迟加载
     * 看起来完美，实际上在JMM下可能返回半构造对象
     */
    public RiskRuleChain getRuleChain() {
        if (ruleChain == null) {                    // 第1次检查（无锁）
            synchronized (RiskRuleEngine.class) {
                if (ruleChain == null) {            // 第2次检查（有锁）
                    ruleChain = loadRuleChain();     // ❌ 危险！
                    // 问题：new RiskRuleChain()的构造可能被重排序
                    // 线程B可能看到 ruleChain != null 但对象未完全初始化
                }
            }
        }
        return ruleChain;
    }

    private RiskRuleChain loadRuleChain() {
        List<RiskRule> rules = ruleRepository.findAllActiveRules();
        RiskRuleChain chain = new RiskRuleChain(rules);  // 构造器内可能很复杂
        chain.initialize();                               // 初始化内部状态
        chain.validate();                                 // 校验规则完整性
        return chain;
    }
}
```

### 第1轮：数据流审查

| 节点 | 数据 | 变化 | 去向 |
|------|------|------|------|
| 读取 | ruleChain (static) | null检查 | → 决定是否加载 |
| 加载 | RiskRuleChain | new + init + validate | → 赋值给static字段 |
| 返回 | ruleChain引用 | — | → 风控评估调用方 |

**关键洞察**：JMM（Java内存模型）允许编译器/CPU对`ruleChain = loadRuleChain()`进行**指令重排序**。分解为3个子步骤：
1. 分配内存空间
2. 调用构造器初始化
3. 将引用指向分配的内存

JMM允许2和3重排序。线程A执行了1→3（引用非null但对象未初始化），线程B在第1次检查时看到非null，返回了**半构造的对象**。在银行风控场景下，这意味着**风控规则可能完全不生效**。

### 第2轮：边界条件审查

| 边界 | 风险 | 严重度 | 说明 |
|------|------|--------|------|
| 指令重排序 | 返回半构造对象 | **致命** | 风控规则链不完整，交易绕过风控 |
| volatile缺失 | 可见性无保证 | **致命** | 线程可能永远看不到更新 |
| static字段 | 类级别共享 | 高 | 所有实例共享，生命周期与类相同 |
| loadRuleChain异常 | ruleChain为null | 中 | 初始化失败后后续调用会重试，但期间所有风控跳过 |
| 规则更新 | 无法热更新 | 中 | static字段只初始化一次 |

**风控场景的恐怖后果**：如果`RiskRuleChain`半构造，`evaluate()`方法可能：
- 返回null → NPE → 交易失败（最好的情况）
- 返回空规则列表 → 所有交易通过风控 → **洗钱交易畅通无阻**（最坏的情况）

### 第3轮：必要性审查

- 双重检查锁定：**完全不必**——JVM的类初始化机制天然线程安全
- synchronized块：**不必**——静态内部类方案更优
- 延迟加载本身：**需要**——风控规则加载昂贵，但实现方式要换

### 修复方案

```java
@Service
public class RiskRuleEngine {
    
    private final RiskRuleRepository ruleRepository;
    
    public RiskRuleEngine(RiskRuleRepository ruleRepository) {
        this.ruleRepository = ruleRepository;
    }

    // ✅ 方案1：静态内部类持有者模式（推荐）
    // JVM保证类初始化的线程安全性（JLS §12.4）
    // 延迟加载：RuleChainHolder直到getRuleChain()首次调用才初始化
    private static class RuleChainHolder {
        // 这里需要Spring Bean，所以用Supplier方式
        static final AtomicReference<RiskRuleChain> INSTANCE = new AtomicReference<>();
    }
    
    public RiskRuleChain getRuleChain() {
        RiskRuleChain chain = RuleChainHolder.INSTANCE.get();
        if (chain == null) {
            synchronized (RiskRuleEngine.class) {
                chain = RuleChainHolder.INSTANCE.get();
                if (chain == null) {
                    chain = loadRuleChain();
                    // ✅ AtomicReference + volatile语义保证可见性
                    RuleChainHolder.INSTANCE.set(chain);
                }
            }
        }
        return chain;
    }
    
    // ✅ 方案2（更简洁）：如果不需要延迟加载，直接@PostConstruct
    // Spring保证@PostConstruct在Bean完全初始化后执行
    private RiskRuleChain ruleChain;
    
    @PostConstruct
    public void init() {
        this.ruleChain = loadRuleChain();
    }
    
    public RiskRuleChain getRuleChainInitialized() {
        return this.ruleChain;  // Spring保证所有依赖注入完成后的可见性
    }
}
```

## 样本D：价值类对象上的锁——Boolean陷阱

**来源**：Sonar Blog (S1860) + 银行清算场景适配
**背景**：银行日终清算批处理，需要对不同清算批次加锁

### 原始代码（AI典型生成）

```java
@Service
public class BatchSettlementService {

    // ❌ 用Boolean作为锁对象——看起来无害，实则致命
    private static final Boolean settlementLock = Boolean.FALSE;
    
    // ❌ 同样危险：Integer缓存范围内（-128~127）的锁
    private static final Integer retryLock = Integer.valueOf(0);
    
    @Autowired
    private SettlementRepository settlementRepository;
    @Autowired
    private AccountService accountService;

    /**
     * 执行清算批次
     */
    public SettlementResult settleBatch(BatchSettlementRequest request) {
        synchronized (settlementLock) {  // ❌ 看似是私有锁，实则全局共享！
            // 执行清算逻辑...
            List<SettlementItem> items = settlementRepository
                .findByBatchId(request.getBatchId());
            
            for (SettlementItem item : items) {
                accountService.settle(item);
            }
            
            return SettlementResult.completed(request.getBatchId());
        }
    }

    /**
     * 重试失败的清算
     */
    public RetryResult retryFailed(String batchId) {
        synchronized (retryLock) {  // ❌ Integer(0) 在整个JVM中共享！
            List<SettlementItem> failedItems = settlementRepository
                .findFailedByBatchId(batchId);
            
            for (SettlementItem item : failedItems) {
                accountService.settle(item);
            }
            
            return RetryResult.completed(batchId);
        }
    }
}
```

### 第1轮：数据流审查

| 节点 | 数据 | 变化 | 去向 |
|------|------|------|------|
| 锁对象 | Boolean.FALSE | JVM全局缓存 | → synchronized获取monitor |
| 清算数据 | SettlementItem | 从DB加载 | → accountService.settle |
| 锁对象 | Integer(0) | JVM缓存范围-128~127 | → synchronized获取monitor |

**关键洞察**：`Boolean.FALSE`在整个JVM中只有一个实例。不仅是你的代码，**所有第三方库中任何使用`Boolean.FALSE`作为锁的代码**都在竞争同一个monitor。这意味着：
- 你的清算服务可能在等待一个完全无关的第三方库释放`Boolean.FALSE`的锁
- 死锁的堆栈跟踪中，两个线程看起来毫无关联——极难诊断

同理，`Integer.valueOf(0)`返回的是缓存的实例（-128~127范围内），整个JVM中所有值为0的Integer共享同一对象。

### 第2轮：边界条件审查

| 边界 | 风险 | 严重度 | 说明 |
|------|------|--------|------|
| 全局锁竞争 | 与第三方库死锁 | **致命** | Boolean.FALSE全局唯一 |
| Integer缓存 | -128~127范围共享 | **致命** | 同值Integer是同一对象 |
| 诊断困难 | 堆栈无逻辑关联 | 高 | 死锁两线程看起来完全不相关 |
| 性能影响 | 无关代码互等 | 高 | 清算被不相关的锁阻塞 |

### 第3轮：必要性审查

- Boolean作为锁：**完全不必要**——应该用`new Object()`
- Integer作为锁：**完全不必要**——应该用`new Object()`
- static final锁：如果意图是"每个服务实例一把锁"，则应改为实例字段

### 修复方案

```java
@Service
public class BatchSettlementService {

    // ✅ 使用专用Object实例作为锁——保证唯一性和独占性
    private final Object settlementLock = new Object();
    private final Object retryLock = new Object();
    
    @Autowired
    private SettlementRepository settlementRepository;
    @Autowired
    private AccountService accountService;

    // 或者更好：如果需要按批次ID加锁
    private final ConcurrentHashMap<String, ReentrantLock> batchLocks = new ConcurrentHashMap<>();

    public SettlementResult settleBatch(BatchSettlementRequest request) {
        // ✅ 按批次ID粒度加锁
        ReentrantLock lock = batchLocks.computeIfAbsent(
            request.getBatchId(), k -> new ReentrantLock());
        
        lock.lock();
        try {
            List<SettlementItem> items = settlementRepository
                .findByBatchId(request.getBatchId());
            for (SettlementItem item : items) {
                accountService.settle(item);
            }
            return SettlementResult.completed(request.getBatchId());
        } finally {
            lock.unlock();
        }
    }
}
```

## 样本E：Structured Concurrency范围泄漏——订单处理

**来源**：markaicode.com + 银行批量代发场景适配
**背景**：银行批量代发工资服务，使用Java 21+ Structured Concurrency并行处理

### 原始代码（AI典型生成）

```java
@Service
public class BatchPaymentService {

    /**
     * 批量代发 - AI生成"使用结构化并发"版本
     * 但漏掉了关键的scope.join()调用
     */
    public BatchPaymentResult batchPay(List<PaymentOrder> orders) 
            throws InterruptedException {
        
        List<PaymentResult> results = new ArrayList<>();
        
        try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
            for (PaymentOrder order : orders) {
                scope.fork(() -> {
                    PaymentResult result = processPayment(order);
                    results.add(result);  // ❌ ArrayList非线程安全！
                    return result;
                });
            }
            // ❌ 致命遗漏：没有 scope.join()！
            // try-with-resources关闭scope时，子任务仍在运行
            // 这些"僵尸线程"会持续消耗资源
        }
        
        return new BatchPaymentResult(results);
    }

    private PaymentResult processPayment(PaymentOrder order) {
        // 模拟支付处理（含数据库操作）
        // ...
        return PaymentResult.success(order.getId());
    }
}
```

### 第1轮：数据流审查

| 节点 | 数据 | 变化 | 去向 |
|------|------|------|------|
| 输入 | List<PaymentOrder> | — | → fork子任务 |
| 并行 | 每个order | fork为Virtual Thread | → processPayment |
| 收集 | results (ArrayList) | 多线程add | ❌ 非线程安全 |
| 关闭 | try-with-resources | 关闭scope | ❌ 子任务可能未完成 |

**关键洞察**：两个严重问题叠加：
1. **缺少`scope.join()`**：try-with-resources关闭scope时，未完成的子任务被取消但并非立即终止，可能变成"僵尸线程"消耗载体线程和内存
2. **ArrayList非线程安全**：多线程同时add会丢失数据或抛ArrayIndexOutOfBoundsException

### 第2轮：边界条件审查

| 边界 | 风险 | 严重度 | 说明 |
|------|------|--------|------|
| 范围泄漏 | 僵尸Virtual Thread | **致命** | 线程数持续增长直到OOM |
| ArrayList并发写 | 数据丢失/异常 | **致命** | 多线程add不安全 |
| 任务取消 | 部分代发丢失 | 高 | 未处理的任务被静默取消 |
| 异常传播 | 某个子任务失败不影响其他 | 中 | ShutdownOnFailure语义未生效 |
| 大批量 | 一次性fork上千任务 | 中 | 可能超出载体线程池容量 |

### 修复方案

```java
@Service
public class BatchPaymentService {

    public BatchPaymentResult batchPay(List<PaymentOrder> orders) 
            throws InterruptedException, ExecutionException {
        
        try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
            // ✅ 收集所有Subtask引用
            List<StructuredTaskScope.Subtask<PaymentResult>> tasks = orders.stream()
                .map(order -> scope.fork(() -> processPayment(order)))
                .toList();
            
            // ✅ 关键！等待所有任务完成
            scope.join();
            
            // ✅ 如果任何任务失败，抛出异常（取消其他任务）
            scope.throwIfFailed();
            
            // ✅ 安全收集结果——此时所有任务已完成
            List<PaymentResult> results = tasks.stream()
                .map(StructuredTaskScope.Subtask::get)
                .toList();
            
            return new BatchPaymentResult(results);
        }
    }

    private PaymentResult processPayment(PaymentOrder order) {
        // 支付处理逻辑
        return PaymentResult.success(order.getId());
    }
}
```

## 样本F：CompletableFuture异常吞噬——交易查询

**来源**：markaicode.com + 银行交易查询场景适配
**背景**：银行交易查询需要聚合多个下游系统的数据

### 原始代码（AI典型生成）

```java
@Service
public class TransactionQueryService {

    @Autowired
    private AccountServiceClient accountClient;
    @Autowired
    private TradeServiceClient tradeClient;
    @Autowired
    private RiskServiceClient riskClient;

    /**
     * 聚合查询交易详情 - AI生成的"异步"版本
     */
    public CompletableFuture<TransactionDetail> queryDetail(String transactionId) {
        return CompletableFuture
            .supplyAsync(() -> accountClient.queryAccount(transactionId))
            .thenCompose(account -> 
                tradeClient.queryTrade(transactionId)
                    .thenApply(trade -> buildDetail(account, trade)))
            .thenCompose(detail ->
                riskClient.queryRiskScore(detail.getAccountId())
                    .thenApply(score -> {
                        detail.setRiskScore(score);
                        return detail;
                    }));
        // ❌ 任何一步失败，异常被静默吞噬！
        // accountClient超时？静默失败
        // tradeClient返回null？NPE被吞掉
        // riskClient不可用？查询永远pending
    }
}
```

### 4层审查要点

**数据流**：account → trade → risk，链式组合，任一环节失败则整条链断裂。

**边界条件**：
| 边界 | 风险 | 严重度 |
|------|------|--------|
| 异常静默 | 调用方永远收不到结果 | **致命** |
| 超时 | 无超时控制 | **致命** |
| null返回 | NPE被吞掉 | 高 |
| 部分失败 | 无法感知哪些步骤成功 | 高 |

**必要性**：链式调用本身合理，但缺少异常处理是不完整的。

**反向审**：AI不确定的地方——thenCompose中的异常是否应该中断后续步骤？如何给异步链加超时？

### 修复方案

```java
@Service
public class TransactionQueryService {

    private static final Duration QUERY_TIMEOUT = Duration.ofSeconds(5);

    @Autowired private AccountServiceClient accountClient;
    @Autowired private TradeServiceClient tradeClient;
    @Autowired private RiskServiceClient riskClient;

    public CompletableFuture<TransactionDetail> queryDetail(String transactionId) {
        return CompletableFuture
            .supplyAsync(() -> accountClient.queryAccount(transactionId))
            .thenCompose(account -> 
                tradeClient.queryTrade(transactionId)
                    .thenApply(trade -> buildDetail(account, trade)))
            .thenCompose(detail ->
                riskClient.queryRiskScore(detail.getAccountId())
                    .thenApply(score -> {
                        detail.setRiskScore(score);
                        return detail;
                    }))
            // ✅ 超时控制
            .orTimeout(QUERY_TIMEOUT.toMillis(), TimeUnit.MILLISECONDS)
            // ✅ 日志记录（无论成功失败）
            .whenComplete((result, ex) -> {
                if (ex != null) {
                    log.error("交易查询失败, txId={}, error={}", transactionId, ex.getMessage(), ex);
                    metrics.counter("query.detail.errors").increment();
                } else {
                    log.debug("交易查询成功, txId={}", transactionId);
                }
            })
            // ✅ 降级处理
            .handle((result, ex) -> {
                if (ex != null) {
                    return TransactionDetail.fallback(transactionId, ex.getMessage());
                }
                return result;
            });
    }
}
```

## 样本G：锁内Sleep——轮询式清算状态检查

**来源**：Sonar Blog (S2276) + 银行清算场景适配
**背景**：银行清算后需要等待上游系统确认，AI生成了轮询等待逻辑

### 原始代码（AI典型生成）

```java
@Service
public class SettlementConfirmService {

    private final Object monitor = new Object();
    
    @Autowired
    private UpstreamSettlementClient upstreamClient;

    /**
     * 等待清算确认 - AI生成的轮询版本
     */
    public SettlementConfirmResult waitForConfirmation(String settlementId) 
            throws InterruptedException {
        synchronized (monitor) {
            while (!upstreamClient.isConfirmed(settlementId)) {
                Thread.sleep(200);  // ❌ 持有锁时sleep！
                // sleep不释放monitor锁
                // 其他需要这个锁的线程全部阻塞
                // 如果确认逻辑也需要这个锁 → 死锁！
            }
            return SettlementConfirmResult.confirmed(settlementId);
        }
    }

    /**
     * 更新清算状态 - 另一个需要同一锁的方法
     */
    public void updateSettlementStatus(String settlementId, Status status) {
        synchronized (monitor) {  // ❌ 被上面的sleep阻塞！
            // 如果这个方法负责设置确认状态...
            // 而上面的轮询在等待确认状态...
            // → 永远死锁！
            upstreamClient.updateStatus(settlementId, status);
        }
    }
}
```

### 4层审查要点

**数据流**：waitForConfirmation轮询 → sleep持有锁 → updateSettlementStatus无法获取锁 → 确认状态永远不会更新 → 死锁。

**核心问题**：`Thread.sleep()` vs `Object.wait()`的本质区别：
- `sleep()`：当前线程休眠，**不释放任何锁**
- `wait()`：当前线程等待，**释放monitor锁**，允许其他线程进入synchronized块

### 修复方案

```java
@Service
public class SettlementConfirmService {

    private final Object monitor = new Object();
    @Autowired
    private UpstreamSettlementClient upstreamClient;

    public SettlementConfirmResult waitForConfirmation(String settlementId) 
            throws InterruptedException {
        synchronized (monitor) {
            while (!upstreamClient.isConfirmed(settlementId)) {
                // ✅ wait释放锁，其他线程可以更新状态
                monitor.wait(200);  
            }
            return SettlementConfirmResult.confirmed(settlementId);
        }
    }

    public void updateSettlementStatus(String settlementId, Status status) {
        synchronized (monitor) {
            upstreamClient.updateStatus(settlementId, status);
            // ✅ 状态更新后唤醒等待线程
            monitor.notifyAll();
        }
    }
}
```

## 审查模式积累

### 新增模式

| 模式编号 | 模式名称 | 识别关键词 | 严重度 | 场景 |
|----------|----------|------------|--------|------|
| CONC-001 | synchronized集合迭代删除 | `Collections.synchronized*()` + for-each + remove | 致命 | 列表遍历删除 |
| CONC-002 | Virtual Thread synchronized pinning | `synchronized`方法 + Virtual Thread + IO操作 | 致命 | 支付/转账 |
| CONC-003 | 双重检查锁定缺少volatile | `if(x==null) synchronized if(x==null)` 无volatile | 致命 | 延迟初始化 |
| CONC-004 | 价值类对象作锁 | `synchronized(Boolean/Integer/String)` | 致命 | 任何加锁场景 |
| CONC-005 | Structured Concurrency缺join | `scope.fork()` 无 `scope.join()` | 致命 | 批量并行 |
| CONC-006 | CompletableFuture异常吞噬 | 链式调用无 whenComplete/handle | 致命 | 异步聚合 |
| CONC-007 | 锁内Thread.sleep | `synchronized { Thread.sleep() }` | 致命 | 轮询/重试 |

### 通用审查Checklist（并发专题）

- [ ] `Collections.synchronized*()` 的所有迭代操作是否安全？
- [ ] `synchronized` 是否在 Virtual Thread 环境中使用？是否有 ReentrantLock 替代？
- [ ] 双重检查锁定是否缺少 `volatile`？能否改用 Holder 模式？
- [ ] 锁对象是否为 Boolean/Integer/String 等价值类？
- [ ] StructuredTaskScope 是否在关闭前调用了 `join()`？
- [ ] CompletableFuture 链是否有 `whenComplete`/`handle`/`orTimeout`？
- [ ] synchronized 块内是否有 `Thread.sleep()`？应改为 `wait()`
- [ ] 锁的粒度是否合理？是否包含 IO/网络操作？
- [ ] 多把锁的获取顺序是否一致？是否可能死锁？
- [ ] 并发集合的选择是否匹配场景（读多写少 → CopyOnWrite；队列 → ConcurrentLinkedQueue）？

## 架构评估

### 好设计 ✅

**ReentrantLock + tryLock超时模式**：适用于银行转账场景，优势——
1. 不pin Virtual Thread的载体线程
2. 超时机制防止无限等待
3. 支持尝试获取、可中断
4. 细粒度控制——每个账户/资源独立锁

**静态内部类Holder模式**：适用于延迟加载，优势——
1. JVM类初始化保证线程安全（JLS §12.4）
2. 无显式同步代码，零性能开销
3. 惰性加载——首次访问才初始化
4. 代码极简，无可读性负担

### 坏设计 ❌

**synchronized方法级锁定 + IO操作**：这是AI最常生成的模式——
1. 粒度过粗：整个方法持有锁
2. Virtual Thread pinning：synchronized在虚拟线程中阻塞载体
3. IO在锁内：网络调用/DB操作拖长锁持有时间
4. 全局串行化：所有调用排队，TPS极低

**Collections.synchronized*()包装器**：AI的"线程安全"默认选择——
1. 只保证单操作原子性，复合操作不安全
2. 给人虚假安全感，比显式不安全更危险
3. 性能不如java.util.concurrent集合
4. 应该直接使用ConcurrentHashMap/ConcurrentLinkedQueue等

## 今日关键结论

> **并发Bug的本质是"时序依赖"**——它们在单线程测试中100%通过，在生产环境的线程竞争下100%爆发。传统测试无法捕获，只有结构化代码审查和静态分析才能可靠识别。
> 
> **银行后端的并发Bug = 钱可以无声地消失**。synchronized集合迭代删除丢交易、双重检查锁定返回半构造风控引擎、价值类锁导致清算死锁——每一个都是"测试绿灯、上线炸裂"的典型案例。
> 
> **审查心态**：看到任何synchronized/锁/并发集合，默认假设它有问题，直到证明安全。
