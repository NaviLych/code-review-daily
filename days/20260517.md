## 一、主题：风控批处理、动态 SQL 与线程池资源治理

**来源**：
- [OWASP: SQL Injection](https://owasp.org/www-community/attacks/SQL_Injection)
- [OWASP Cheat Sheet: SQL Injection Prevention](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html)
- [Spring Boot Reference: Task Execution and Scheduling](https://docs.spring.io/spring-boot/3.3/reference/features/task-execution-and-scheduling.html)
- [Spring Framework API: ThreadPoolTaskExecutor](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/scheduling/concurrent/ThreadPoolTaskExecutor.html)

> 今日样本是模拟 AI 生成的“交易风控批量重算任务”。它符合 AI 常见风格：Stream + CompletableFuture + 动态 SQL + 默认线程池，代码看起来现代，但在银行后端场景里有 SQL 注入、连接池挤爆、异常吞噬、批处理不可恢复等问题。

## 二、样本：AI 生成的风控重算任务

### 2.1 问题代码

```java
@Service
public class RiskRebuildService {
    private final JdbcTemplate jdbcTemplate;
    private final RiskScoreClient riskScoreClient;

    public void rebuild(String startDate, String endDate, String productType) {
        String sql = "select id, user_id, amount, merchant_id from transactions "
            + "where created_at >= '" + startDate + "' "
            + "and created_at < '" + endDate + "' "
            + "and product_type = '" + productType + "'";

        List<TransactionRow> rows = jdbcTemplate.query(sql, this::mapRow);

        List<CompletableFuture<Void>> futures = rows.stream()
            .map(row -> CompletableFuture.runAsync(() -> {
                RiskScore score = riskScoreClient.calculate(row);
                jdbcTemplate.update(
                    "update transactions set risk_score = ?, risk_level = ? where id = ?",
                    score.value(), score.level(), row.id()
                );
            }))
            .toList();

        futures.forEach(CompletableFuture::join);
    }

    private TransactionRow mapRow(ResultSet rs, int rowNum) throws SQLException {
        return new TransactionRow(
            rs.getLong("id"),
            rs.getLong("user_id"),
            rs.getBigDecimal("amount"),
            rs.getLong("merchant_id")
        );
    }
}
```

### 2.2 AI 最可能给出的解释

```text
使用 CompletableFuture 并行计算风控分，可以显著提升性能。
JdbcTemplate 自动管理资源，查询和更新都比较简洁。
最后 join 等待所有任务完成，保证批处理结束时数据已更新。
```

**审查提醒**：这段解释只看到了“并行”这个表层优势，没有交代线程池、连接池、外部服务限流、异常恢复、SQL 注入和批量处理的可观测性。

## 三、四层审查

## 第1轮：数据流

### 输入从哪来

- `startDate`、`endDate`、`productType` 可能来自运维后台、调度参数或人工补偿脚本。
- 在银行后端，调度参数也不能默认可信，尤其是能拼进 SQL 的字段。

### 中间变了什么

```text
startDate/endDate/productType
  -> 拼接 SQL
  -> 查询交易列表
  -> 每条交易调用风控评分服务
  -> 回写 transactions.risk_score/risk_level
  -> join 等待任务结束
```

### 输出到哪去

- 写回交易表风控字段。
- 调用外部风控评分服务。
- 没有生成批次记录、进度记录、失败明细或可重试游标。

### 数据流红旗

1. 输入参数直接拼 SQL。
2. 一次性把所有交易加载到内存。
3. 每条记录一个异步任务，没有并发上限。
4. 风控结果直接覆盖交易主表，没有批次维度。
5. 失败记录不可追踪，无法断点续跑。

## 第2轮：边界条件

### 3.1 SQL 注入

```java
"and product_type = '" + productType + "'"
```

OWASP 对 SQL 注入的定义很直接：不可信输入被用于动态构造 SQL，攻击者就可能改变查询意图。这里即使入口是内部后台，也可能被误操作或越权调用触发。

**攻击样例**：

```text
productType = LOAN' or '1'='1
```

生成的 SQL 会扩大重算范围，可能把全量交易都刷一遍。

**修复**：

```java
String sql = """
    select id, user_id, amount, merchant_id
    from transactions
    where created_at >= ?
      and created_at < ?
      and product_type = ?
    order by id
    limit ?
    """;

List<TransactionRow> rows = jdbcTemplate.query(
    sql,
    this::mapRow,
    startDateTime,
    endDateTime,
    productType,
    pageSize
);
```

### 3.2 日期字符串不校验

```java
public void rebuild(String startDate, String endDate, String productType)
```

问题：

- 日期格式错误到运行时才暴露。
- `startDate >= endDate` 没有阻止。
- 时区不明确，跨日统计容易偏移。
- 字符串拼接还会绕过索引使用方式。

**修复方向**：

```java
public void rebuild(LocalDate startDate, LocalDate endDate, ProductType productType) {
    if (!startDate.isBefore(endDate)) {
        throw new IllegalArgumentException("startDate must be before endDate");
    }
}
```

### 3.3 `CompletableFuture.runAsync` 默认使用 commonPool

```java
CompletableFuture.runAsync(() -> { ... })
```

不传 executor 时，任务会使用默认公共线程池。对于包含 HTTP 调用和数据库更新的阻塞任务，这是典型风险：

- 与应用其他异步任务抢线程。
- 阻塞 commonPool，导致无关功能变慢。
- 并发数量无法按风控服务限流配置。

Spring Boot 文档说明，在没有自定义 Executor 时会自动配置异步执行器；Spring 的 `ThreadPoolTaskExecutor` 暴露了 `corePoolSize`、`maxPoolSize`、`queueCapacity` 等配置项。审查重点是：批处理必须有自己的、有名字的、有上限的执行器。

### 3.4 一次性加载全量交易

```java
List<TransactionRow> rows = jdbcTemplate.query(sql, this::mapRow);
```

如果一天 300 万笔交易：

- 内存暴涨。
- 查询时间长。
- 事务快照/数据库资源压力大。
- 任务失败后不知道已经处理到哪里。

**修复方向**：

- 分页按 `id > lastId` 游标推进。
- 每页固定大小，例如 500 或 1000。
- 每页记录批次进度。
- 对失败明细建表，支持重跑。

### 3.5 异常路径不可控

```java
futures.forEach(CompletableFuture::join);
```

`join()` 会抛出 `CompletionException`，但这里没有：

- 记录是哪笔交易失败。
- 区分可重试和不可重试错误。
- 取消剩余任务。
- 更新批次状态。

更糟的是，前面已经有部分交易更新成功，最后抛异常只会让调用方知道“批次失败”，但不知道失败边界。

### 3.6 风控结果覆盖主表缺少审计

```java
update transactions set risk_score = ?, risk_level = ? where id = ?
```

问题：

- 没有 `risk_version`。
- 没有 `risk_batch_id`。
- 没有 `updated_at`。
- 没有保留旧评分。
- 不能回答“这个分数是哪个模型、哪次批处理写的”。

银行后端通常需要可解释、可追溯、可回放。

## 第3轮：必要性

### 每行代码删掉会怎样

```java
String sql = "... " + startDate + ...
```

必须删掉拼接方式，改为参数化查询。SQL 本身必要，字符串拼接不必要。

```java
List<TransactionRow> rows = jdbcTemplate.query(...)
```

查询必要，但一次性全量不必要。应该分页或流式处理。

```java
CompletableFuture.runAsync(...)
```

并行不一定必要。风控服务如果有 QPS 限制，盲目并行会把下游打挂。需要先定义吞吐目标，再配置并发上限。

```java
jdbcTemplate.update("update transactions ...")
```

更新必要，但直接覆盖主表不够。更好的方式是写 `transaction_risk_result`，再由受控流程汇总到主表。

### 能不能不写

- 如果这是离线重算，不一定要在业务应用内跑，可以放到独立 batch worker。
- 如果需要在线修复，至少隔离线程池、限流和批次状态。
- 如果风控评分可重复计算，主表可以只存结果引用，明细进入审计表。

## 第4轮：反向审查

让 AI 交代它最不确定的 3 个地方：

1. **我不确定 `productType` 是否可信。**
   不能默认可信。后台参数也属于输入边界，必须参数化。

2. **我不确定并发数是否安全。**
   `runAsync` 没有业务并发上限，既可能打爆风控服务，也可能耗尽数据库连接。

3. **我不确定失败后如何恢复。**
   当前没有批次表、游标、失败明细或幂等更新，不能可靠重跑。

## 四、建议修复版本

### 4.1 线程池隔离

```java
@Configuration
public class RiskBatchExecutorConfig {
    @Bean
    public ThreadPoolTaskExecutor riskBatchExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setThreadNamePrefix("risk-batch-");
        executor.setCorePoolSize(8);
        executor.setMaxPoolSize(16);
        executor.setQueueCapacity(500);
        executor.setWaitForTasksToCompleteOnShutdown(true);
        executor.initialize();
        return executor;
    }
}
```

### 4.2 批次化处理

```java
@Service
public class RiskRebuildService {
    private static final int PAGE_SIZE = 500;

    private final JdbcTemplate jdbcTemplate;
    private final RiskScoreClient riskScoreClient;
    private final ThreadPoolTaskExecutor riskBatchExecutor;
    private final RiskBatchRepository riskBatchRepository;

    public void rebuild(RiskRebuildCommand command) {
        command.validate();

        RiskBatch batch = riskBatchRepository.start(command);
        long lastId = 0L;

        while (true) {
            List<TransactionRow> rows = loadPage(command, lastId);
            if (rows.isEmpty()) {
                riskBatchRepository.markSuccess(batch.id());
                return;
            }

            processPage(batch.id(), rows);
            lastId = rows.get(rows.size() - 1).id();
            riskBatchRepository.saveProgress(batch.id(), lastId);
        }
    }

    private List<TransactionRow> loadPage(RiskRebuildCommand command, long lastId) {
        String sql = """
            select id, user_id, amount, merchant_id
            from transactions
            where id > ?
              and created_at >= ?
              and created_at < ?
              and product_type = ?
            order by id
            limit ?
            """;

        return jdbcTemplate.query(
            sql,
            this::mapRow,
            lastId,
            command.startAt(),
            command.endAt(),
            command.productType().name(),
            PAGE_SIZE
        );
    }

    private void processPage(long batchId, List<TransactionRow> rows) {
        List<CompletableFuture<RiskResult>> futures = rows.stream()
            .map(row -> CompletableFuture.supplyAsync(
                () -> calculateRisk(batchId, row),
                riskBatchExecutor
            ))
            .toList();

        List<RiskResult> results = futures.stream()
            .map(CompletableFuture::join)
            .toList();

        saveResults(batchId, results);
    }
}
```

### 4.3 结果表与幂等写入

```sql
create table transaction_risk_result (
    id bigint primary key,
    batch_id bigint not null,
    transaction_id bigint not null,
    risk_version varchar(64) not null,
    risk_score decimal(10, 4) not null,
    risk_level varchar(32) not null,
    created_at timestamp not null,
    unique (batch_id, transaction_id)
);
```

```java
private void saveResults(long batchId, List<RiskResult> results) {
    jdbcTemplate.batchUpdate("""
        insert into transaction_risk_result
            (batch_id, transaction_id, risk_version, risk_score, risk_level, created_at)
        values (?, ?, ?, ?, ?, ?)
        on conflict (batch_id, transaction_id) do nothing
        """,
        results,
        500,
        (ps, result) -> {
            ps.setLong(1, batchId);
            ps.setLong(2, result.transactionId());
            ps.setString(3, result.version());
            ps.setBigDecimal(4, result.score());
            ps.setString(5, result.level());
            ps.setTimestamp(6, Timestamp.from(Instant.now()));
        }
    );
}
```

### 4.4 失败明细

```java
private RiskResult calculateRisk(long batchId, TransactionRow row) {
    try {
        RiskScore score = riskScoreClient.calculate(row);
        return RiskResult.success(batchId, row.id(), score);
    } catch (RetryableRiskException ex) {
        riskBatchRepository.recordFailure(batchId, row.id(), "RETRYABLE", ex.getMessage());
        throw ex;
    } catch (Exception ex) {
        riskBatchRepository.recordFailure(batchId, row.id(), "FATAL", ex.getMessage());
        throw ex;
    }
}
```

## 五、审美与架构评估

### 可读性

**问题**：

- `rebuild(String, String, String)` 参数语义弱。
- SQL 拼接让业务意图和安全风险混在一起。
- Lambda 内同时做远程调用和数据库写入，异常定位困难。

**改进**：

- 引入 `RiskRebuildCommand` 表达输入契约。
- 方法拆成 `loadPage`、`processPage`、`saveResults`。
- 每个批次有 `batchId` 贯穿日志与结果表。

### 设计模式

**过度设计风险**：

- 对小数据量一次性引入分布式任务平台可能过重。

**设计不足风险**：

- 无批次、无幂等、无失败明细的风控重算，在银行场景不可接受。

**平衡方案**：

- 先用单应用 batch worker + 数据库批次表。
- 当数据量、耗时和 SLA 上来后，再迁移到调度平台或分片执行。

### 架构层面

推荐职责划分：

```text
RiskRebuildController / Scheduler
  -> RiskRebuildService
      -> RiskBatchRepository
      -> TransactionReader
      -> RiskScoreClient
      -> RiskResultWriter
```

依赖方向：

- 调度层只发命令。
- 应用服务控制批次生命周期。
- 读取交易与写风险结果分离。
- 外部风控服务通过可限流 client 访问。

### Java / Spring 特有审查点

- `CompletableFuture.runAsync` 必须显式传 executor。
- 批处理线程池要和 Web 请求线程池、通用 async executor 隔离。
- `ThreadPoolTaskExecutor` 的 `queueCapacity` 不是越大越好，过大队列会掩盖下游过载。
- JdbcTemplate 防资源泄漏，但不替你防 SQL 注入。
- 批量任务要有 `batch_id`、进度、失败明细和重跑策略。

## 六、今日沉淀

### 新增审查模式

#### 模式：默认线程池误用

**识别特征**：

- `CompletableFuture.runAsync(...)` 不传 executor
- `parallelStream()` 跑阻塞 IO
- 批量任务和 Web 请求共享线程池

**审查句式**：

> 看到默认并行，先问线程从哪来、并发上限是多少、阻塞时影响谁。

#### 模式：批处理不可恢复

**识别特征**：

- 一次性查询全量数据
- 没有批次表和游标
- 失败后只能全量重跑
- 无失败明细

**审查句式**：

> 批处理的正确性不只在成功路径，关键是失败后能否知道停在哪、坏在哪、如何重来。

#### 模式：动态 SQL 伪内部安全

**识别特征**：

- “这个接口只有内部用”作为拼接 SQL 的理由
- 日期、枚举、排序字段直接拼接
- 运维后台参数未校验

**审查句式**：

> 内部入口也是输入边界。只要能改变 SQL 结构，就必须参数化或白名单。

### 新增架构模式

#### 模式：可恢复批处理

```text
batch table
  -> batch_id
  -> status
  -> last_processed_id
  -> started_at / finished_at

failure table
  -> batch_id
  -> item_id
  -> error_type
  -> error_message
  -> retry_count
```

**适用场景**：

- 风控重算
- 数据迁移
- 历史交易补偿
- 对账修复

## 七、今日一句话

AI 很爱把“并行”当作性能答案，但银行后端先要回答的是资源边界：线程从哪来、连接够不够、下游扛不扛、失败能不能恢复。
