## 一、今日核心发现：Rust的"安全边界"之外

### 🔴 发现1：TOCTOU竞态条件（最大漏洞集群）

**来源**：[Bugs Rust Won't Catch - Corrode](https://corrode.dev/blog/bugs-rust-wont-catch/)

uutils/coreutils审计发现44个CVE，其中最大集群是**TOCTOU (Time-of-Check to Time-of-Use)** 竞态条件。

**典型Bug模式 - CVE-2026-35355**：

```rust
// ❌ 危险代码 - 两次syscall之间可被攻击
fs::remove_file(to)?;                    // 第1次：检查
// <-- 攻击者可在此时植入symlink到/etc/shadow
let mut dest = File::create(to)?;        // 第2次：使用（重新解析路径！）
copy(from, &mut dest)?;
```

**问题本质**：
- Rust的`std::fs` API每次都重新解析路径
- 两次syscall之间，攻击者可以修改文件系统状态
- `File::create`会跟随symlink

**修复方案**：

```rust
// ✅ 安全代码 - 使用create_new防止symlink攻击
let mut dest = OpenOptions::new()
    .write(true)
    .create_new(true)  // 确保不存在（包括symlink）
    .open(to)?;
copy(from, &mut dest)?;
```

**跨语言对比**：
| 语言 | 默认行为 | 安全API |
|------|----------|---------|
| Rust | 路径重解析 | `OpenOptions::create_new()` |
| C | 依赖具体API | `openat()` 系列 |
| Go | 路径重解析 | `os.OpenFile()` + `O_CREATE\|O_EXCL` |

**审查规则**：
> ⚠️ **如果同一个路径执行两次操作，假设这是TOCTOU Bug直到被证明安全**

### 🔴 发现2：Ghost Bits类型截断漏洞

**来源**：[Rust #155912](https://github.com/rust-lang/rust/issues/155912)

**漏洞机制**：

```rust
let ch: char = '\u{2F58}';  // char是32位Unicode
let b: u8 = ch as u8;       // 只保留低8位！

// ħ (U+0127) → 0x27 = '\'' (单引号)
```

**攻击向量**：WAF/IDS绕过

```
WAF看到: "ħ OR ħ1ħ=ħ1" (无害的Unicode字符)
Rust处理: ħ → 0x27 → '\'' (还原为攻击payload)
```

**Rust为何相对安全**：
- 编译器发出**显式警告**
- 需要显式添加`#[allow(trivial_casts)]`
- 不像Go/Java完全没有警告

**缓解方案**：

```rust
// ❌ 危险 - 需要#[allow(trivial_casts)]
#[allow(trivial_casts)]
for ch in s.chars() {
    bytes.push(ch as u8);
}

// ✅ 安全 - 使用bytes()迭代器
for b in s.bytes() {
    // b已经是u8，无需转换
}

// ✅ 安全 - 输入验证
fn is_valid_ascii(s: &str) -> bool {
    s.chars().all(|ch| ch.is_ascii())
}
```

### 🟡 发现3：权限设置时序问题

```rust
// ❌ 危险 - 临时暴露窗口
fs::create_dir(&path)?;
fs::set_permissions(&path, Permissions::from_mode(0o700))?;
// 其他用户在create和set_permissions之间可以访问
```

**修复**：

```rust
// ✅ 安全 - 创建时直接设置权限
fs::create_dir(&path)?
    .with_permissions(Permissions::from_mode(0o700));
// 或者
OpenOptions::new()
    .create(true)
    .mode(0o700)  // Unix特定
    .open(&path)?;
```

### 🟡 发现4：路径字符串比较的陷阱

```rust
// ❌ 危险 - 字符串比较不可靠
if file == Path::new("/") { ... }  // 可被 /../ 绕过

// ✅ 安全 - 先规范化再比较
fn is_root(file: &Path) -> bool {
    matches!(fs::canonicalize(file), Ok(p) if p == Path::new("/"))
}
```

### 🟡 发现5：unwrap/expect的DoS风险

```rust
// ❌ 危险 - 任意输入可导致panic
let path = std::str::from_utf8(bytes)
    .expect("Could not parse...");

// 攻击者创建非UTF-8文件名 → 进程崩溃
```

**修复**：

```rust
// ✅ 安全 - 优雅错误处理
match std::str::from_utf8(bytes) {
    Ok(s) => process(s),
    Err(e) => return Err(ParseError::InvalidUtf8(e)),
}
```

**Clippy规则**：

```toml
[lints.clippy]
unwrap_used = "warn"
expect_used = "warn"
panic = "warn"
indexing_slicing = "warn"
```

## 二、Swift并发陷阱

**来源**：[Firebase iOS SDK #16081](https://github.com/firebase/firebase-ios-sdk/issues/16081)

### 🔴 发现6：asyncLet的任务完成竞态

**问题代码**：

```swift
// Firebase HTTPSCallable.call()中的崩溃
async let task1 = HTTPSCallable.call()  // 启动异步任务
async let task2 = anotherCall()        // 又一个异步任务
// ...
let results = await (task1, task2)     // 等待时序问题
```

**崩溃堆栈**：

```
swift_Concurrency_fatalError
asyncLet_finish_after_task_completion  // 任务完成后销毁时崩溃
HTTPSCallable.call()
```

**根因**：Swift并发中，`asyncLet`变量在作用域结束时必须被await，但有时任务完成时序不对导致崩溃。

### 🟡 发现7：Actor Isolation Violation

**来源**：[Postmortem Swift 6.0 Crash](https://tools.30tools.com/blogs/johalputt/postmortem-we-fixed-a-2026-ios-app-crash-with-swift-60-and-xcode-160-1gc7)

**问题代码**：

```swift
// ❌ 危险 - @preconcurrency掩盖了隔离违规
@preconcurrency
func syncWorkouts(completion: @escaping (Result<Void, Error>) -> Void) {
    backgroundQueue.async {
        let cache = UserWorkoutCache.shared  // 非Sendable跨Actor访问！
        cache.store(workout)
    }
}
```

**修复**：

```swift
// ✅ 安全 - 使用Actor代替共享类
actor UserWorkoutCache {
    func store(_ workout: Workout) { ... }
}

// ✅ 安全 - 使用async/await
func syncWorkouts() async throws {
    let cache = UserWorkoutCache.shared
    await cache.store(workout)  // 显式Actor跳转
}
```

## 三、跨语言设计智慧

### 3.1 安全边界的共同原则

| 问题 | Rust解法 | Swift解法 | Go解法 |
|------|----------|-----------|--------|
| **TOCTOU** | `create_new()` | `FileManager`原子操作 | `os.OpenFile()` |
| **类型截断** | 编译器警告 | N/A | 无警告 |
| **权限设置** | 创建时指定 | 创建时指定 | 创建时指定 |
| **路径比较** | `canonicalize` | `standardizingPath` | `filepath.Clean` |

### 3.2 信任边界跨越原则

> **Rule: Cross Before You Use**
> 一旦跨越信任边界，每个库调用都可能是攻击者的代码

```rust
// ❌ 危险 - chroot后加载用户信息
chroot(new_root)?;           // 切换到攻击者控制的文件系统
let user = get_user_by_name(name)?;  // 加载攻击者的libnss_*.so

// ✅ 安全 - 跨越前解析
let user = get_user_by_name(name)?;  // 在安全侧解析
chroot(new_root)?;
```

### 3.3 Bug-for-Bug兼容性的价值

> **Hyrum's Law**: 可观测的行为都会被依赖

```bash
# kill -1 在GNU和uutils中有不同语义
GNU: kill -1 → 请求信号1的PID
uutils: kill -1 → 发送给PID -1（所有可见进程）
# 一个typo变成系统级kill开关
```

**教训**：重实现成熟工具时，行为兼容性是安全特性

## 五、模式积累

### 5.1 新增审查模式

**Pattern: 双重Syscall检查**
```
触发条件：代码对同一路径执行两个操作
检查项：
  1. 两个操作之间是否可能修改文件系统？
  2. 第二个操作是否会跟随symlink？
  3. 是否可以使用原子操作替代？
```

**Pattern: 类型边界守卫**
```
触发条件：char/Unicode到字节的转换
检查项：
  1. 是否有显式的#[allow(trivial_casts)]？
  2. 是否有输入验证（ASCII范围）？
  3. 是否可以使用bytes()迭代器替代？
```

**Pattern: 信任边界标记**
```
触发条件：跨越信任边界（chroot、sandbox、权限提升）
检查项：
  1. 边界前的数据是否已解析完成？
  2. 边界后的库调用是否可控？
  3. 是否有NSS/动态库加载风险？
```

### 5.2 新增反模式

```
🚫 反模式：路径字符串比较
   let p = Path::new("/")
   
✅ 正模式：规范化后再比较
   let p = fs::canonicalize(path)?
   
🚫 反模式：创建后设置权限
   create_dir(path); set_permissions(path, mode)
   
✅ 正模式：创建时设置权限
   OpenOptions::new().mode(0o700).create()
```

## 六、关键教训

1. **Rust的borrow checker不保护TOCTOU**：它只在内存安全层面有效，文件系统状态在外部

2. **编译器警告是最后防线**：Ghost Bits漏洞需要显式忽略警告才能利用

3. **Swift 6.0的严格并发检查**：@preconcurrency是技术债，不是解决方案

4. **跨语言智慧**：TOCTOU是所有语言的共同问题，但解决API不同
