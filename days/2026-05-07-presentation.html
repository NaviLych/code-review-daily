核心线索：谁来保证资源的结束？
好设计让结束和开始一样明确；坏设计让结束成为希望而非保证。

Swift 样本A：Continuation 泄漏

问题代码 — 只在成功路径 resume，失败路径遗漏

func fetchDataAsync(from url: URL) async throws -> Data {
    try await withCheckedThrowingContinuation { continuation in
        let manager = NetworkManager()
        manager.delegate = self
        manager.fetchData(from: url)
        
        // 成功路径 — 有 resume
        func didReceiveData(_ data: Data) {
            continuation.resume(returning: data)
        }
        // ❌ 失败路径 — 忘记 resume！
        func didFailWithError(_ error: Error) {
            // continuation 从未被 resume → 泄漏
        }
    }
}

🔴 四层审查发现

❌ 失败路径遗漏 — didFailWithError 不 resume

❌ 任务取消 — 父 Task cancel 时无人 resume

❌ 超时 — 回调永不触发则永久泄漏

❌ 保留环 — self→manager→delegate=self

Swift 样本A：修复方案

✅ 所有路径都 resume continuation

// ✅ 所有路径都 resume
func fetchDataAsync(from url: URL) async throws -> Data {
    try await withCheckedThrowingContinuation { continuation in
        let manager = NetworkManager()
        manager.delegate = self  // weak!
        manager.fetchData(from: url)
        
        func didReceiveData(_ data: Data) {
            continuation.resume(returning: data)
        }
        func didFailWithError(_ error: Error) {
            continuation.resume(throwing: error) // ✅
        }
    }
}

// ✅ delegate 用 weak
protocol NetworkManagerDelegate: AnyObject {
    func didReceiveData(_ data: Data)
    func didFailWithError(_ error: Error)
}
class NetworkManager {
    weak var delegate: NetworkManagerDelegate?  // ✅
}

✅✅ 更优：带超时保护

func fetchWithTimeout(
    from url: URL, 
    timeout: TimeInterval = 30
) async throws -> Data {
    try await withThrowingTaskGroup(of: Data.self) { group in
        group.addTask {
            let (data, _) = try await 
                URLSession.shared.data(from: url)
            return data
        }
        group.addTask {
            try await Task.sleep(
                nanoseconds: UInt64(timeout * 1_000_000_000)
            )
            throw URLError(.timedOut)
        }
        let result = try await group.next()!
        group.cancelAll()  // 取消另一个
        return result
    }
}
continuation 的契约是恰好 resume 一次——编译器信任你，但你的代码必须在所有路径上遵守契约。

Go 样本B：结构化并发典范

errgroup + WithContext 实现 Dashboard 数据聚合

func fetchDashboard(ctx context.Context, userID string) (*Dashboard, error) {
    g, gctx := errgroup.WithContext(ctx)

    var (
        profile       *Profile
        orders        []*Order
        notifications []*Notification
    )

    g.Go(func() error {
        var err error
        profile, err = getProfile(gctx, userID)  // ✅ 使用 gctx 而非 ctx
        return err
    })
    g.Go(func() error {
        var err error
        orders, err = getOrders(gctx, userID)
        return err
    })
    g.Go(func() error {
        var err error
        notifications, err = getNotifications(gctx, userID)
        return err
    })

    if err := g.Wait(); err != nil {
        return nil, fmt.Errorf("fetch dashboard for %s: %w", userID, err)
    }
    return &Dashboard{Profile: profile, Orders: orders, Notifications: notifications}, nil
}

Go 样本B：审查分析与进阶

✅ 亮点

✅ 错误传播：任一 error → gctx 取消 → 其他退出

✅ 并发安全：各 goroutine 写不同变量

✅ context 取消：使用 gctx 传播信号

⚠️ 限制缺失：无并发上限可能资源耗尽

🤖 AI 隐瞒弱点

1. 忘记用 gctx 而用 ctx

2. 不包装 error，丢失上下文

3. 无限并发，打爆下游

带并发限制的进阶版

func enrichProducts(ctx context.Context, 
    products []Product) ([]EnrichedProduct, error) {
    results := make([]EnrichedProduct, len(products))
    g, gctx := errgroup.WithContext(ctx)
    g.SetLimit(20)  // 最多 20 个并发

    for i, p := range products {
        i, p := i, p  // Go < 1.22 捕获循环变量
        g.Go(func() error {
            enriched, err := enrichProduct(gctx, p)
            if err != nil {
                return fmt.Errorf(
                    "enrich product %s: %w", p.ID, err)
            }
            results[i] = enriched  // ✅ 安全
            return nil
        })
    }
    if err := g.Wait(); err != nil {
        return nil, err
    }
    return results, nil
}

Rust 样本C：Rc 循环引用泄漏

❌ 循环引用：a → b → a，引用计数永不为零

use std::rc::Rc;
use std::cell::RefCell;

#[derive(Debug)]
enum List {
    Cons(i32, RefCell<Rc<List>>),
    Nil,
}

fn main() {
    let a = Rc::new(Cons(5, 
        RefCell::new(Rc::new(Nil))));
    // a rc = 1

    let b = Rc::new(Cons(10, 
        RefCell::new(Rc::clone(&a))));
    // a rc = 2

    // ❌ 创建循环引用：a → b → a
    if let Some(link) = a.tail() {
        *link.borrow_mut() = Rc::clone(&b);
    }
    // a 和 b 的引用计数永远不为 0
    // → 内存泄漏！
}

✅ 用 Weak 打破循环

use std::rc::{Rc, Weak};
use std::cell::RefCell;

struct Node {
    value: i32,
    parent: RefCell<Weak<Node>>,    // ✅ Weak
    children: RefCell<Vec<Rc<Node>>>, // ✅ Strong
}

fn main() {
    let leaf = Rc::new(Node {
        value: 3,
        parent: RefCell::new(Weak::new()),
        children: RefCell::new(vec![]),
    });
    let branch = Rc::new(Node {
        value: 5,
        parent: RefCell::new(Weak::new()),
        children: RefCell::new(vec![Rc::clone(&leaf)]),
    });
    *leaf.parent.borrow_mut() = 
        Rc::downgrade(&branch); // ✅ 不增引用计数
    
    // branch strong = 1, leaf strong = 2
    // branch 离开作用域时正常释放
}

RAII：确保资源释放

// ✅ 用 RAII 包装 FFI 资源
struct CBuffer {
    data: *mut u8,
    len: usize,
}
impl CBuffer {
    fn new(len: usize) -> Self {
        let data = unsafe { 
            libc::malloc(len) as *mut u8 
        };
        assert!(!data.is_null(), "Allocation failed");
        CBuffer { data, len }
    }
}
impl Drop for CBuffer {
    fn drop(&mut self) {
        unsafe { 
            libc::free(self.data as *mut libc::c_void) 
        };
    }
}

// ✅ ManuallyDrop 替代 mem::forget
fn transfer_ownership() {
    let v = vec![65, 122];
    let mut v = ManuallyDrop::new(v);
    let (ptr, len, cap) = 
        (v.as_mut_ptr(), v.len(), v.capacity());
    let s = unsafe { 
        String::from_raw_parts(ptr, len, cap) 
    };
    // s 离开作用域时正常释放
}

💡 核心洞察：异步生命周期

❌ 坏代码的共同特征

  • 只有 happy path，忘记 error/cancel/timeout
  • 资源的开始有明确代码，结束靠"希望"
  • 保留环 / 循环引用无人打破
  • 局部变量可能在异步操作完成前被释放

✅ 好代码的共同特征

  • 所有路径都保证资源释放
  • 结构化并发：任务有明确生命周期边界
  • 弱引用建模"非必须存活"关系
  • 取消信号能级联传播
语言机制资源开始资源结束失败路径
Swift continuation withCheckedContinuation resume (恰好一次) 所有路径必须 resume
Go errgroup g.Go(func) g.Wait() ctx 取消 + error 返回
Rust ownership Rc::new() / Arc::new() 引用计数归零时 Drop Weak::upgrade() 返回 None
好设计让结束和开始一样明确；坏设计让结束成为希望而非保证。

🧩 新增审查模式

异步桥接遗漏路径 ⭐⭐⭐⭐⭐

将 callback/delegate 桥接到 async/await 时，只有 happy path 的 resume，缺少 error/cancel/timeout 路径

  • ☐ continuation 在所有路径上恰好 resume 一次？
  • ☐ 处理了 Task 取消？
  • ☐ 有超时保护？
  • ☐ delegate 无保留环？

结构化并发模式 ✅

使用 errgroup / TaskGroup / JoinSet 管理并发任务，任务有明确边界，错误能传播、取消能级联

  • ☐ 用 WithContext / gctx 传播取消？
  • ☐ 并发有限制（SetLimit / semaphore）？
  • ☐ error 包含足够上下文？
  • ☐ 共享变量写入安全？

所有权循环陷阱 ⭐⭐⭐⭐

使用 Rc/Arc 构建图/树结构时，节点间双向引用缺少 Weak 打破循环

  • ☐ 是否存在循环引用可能？
  • ☐ 父→子 Strong，子→父 Weak？
  • ☐ Debug/Display 会导致无限递归？
  • ☐ RefCell/Mutex borrow 会 panic/deadlock？
