## 样本A：Swift async/await 与 Delegate 桥接的 Continuation 泄漏

**来源**：CodeStudy博客《Fixing Swift Task Continuation Misuse》+ Swift GitHub Issue #81771  
**背景**：Swift 5.5 引入 async/await 后，与旧版 delegate 模式 API（URLSession、CoreLocation等）桥接时，极易出现 task continuation 泄漏

### 原始代码（坏设计）

```swift
// ❌ 只在成功路径 resume continuation，失败路径遗漏
func fetchDataAsync(from url: URL) async throws -> Data {
    try await withCheckedThrowingContinuation { continuation in
        let manager = NetworkManager()
        manager.delegate = self
        manager.fetchData(from: url)
        
        // 成功路径 — 有 resume
        func didReceiveData(_ data: Data) {
            continuation.resume(returning: data)
        }
        // ❌ 失败路径 — 忘记 resume！
        func didFailWithError(_ error: Error) {
            // continuation 从未被 resume → 泄漏
        }
    }
}
```

### Step 2：四层审查

**第1轮：数据流**
- 输入：URL → NetworkManager 发起请求
- 中间：delegate 回调 → continuation 桥接
- 输出：Data 或 Error
- **问题**：失败路径的数据流断裂——error 产生后无法流向 continuation

**第2轮：边界条件**
- ❌ **失败路径遗漏**：`didFailWithError` 不 resume → continuation 永远挂起
- ❌ **任务取消**：父 Task 被 cancel 时，continuation 也无人 resume
- ❌ **超时**：如果 delegate 回调永不触发（如网络不可达），continuation 永久泄漏
- ❌ **保留环**：`self` → `manager` → `delegate=self` → 保留环，可能导致 delegate 方法永不调用

**第3轮：必要性**
- `withCheckedThrowingContinuation` 是必要的——这是桥接 callback 到 async 的标准方式
- 但 manager 的生命周期管理不足——`manager` 是局部变量，可能被提前释放

**反向审：AI 最可能隐瞒的3个弱点**
1. **失败路径遗漏**：AI 生成代码时，往往只写 happy path，忘记 error path
2. **Task 取消处理缺失**：AI 不了解 Swift Concurrency 的取消语义
3. **保留环隐蔽**：delegate 强引用在 Swift 中是经典陷阱，AI 容易忽略

### 修复后代码（好设计）

```swift
// ✅ 所有路径都 resume continuation
func fetchDataAsync(from url: URL) async throws -> Data {
    try await withCheckedThrowingContinuation { continuation in
        let manager = NetworkManager()
        manager.delegate = self  // delegate 必须是 weak 的！
        manager.fetchData(from: url)
        
        func didReceiveData(_ data: Data) {
            continuation.resume(returning: data)
        }
        
        func didFailWithError(_ error: Error) {
            continuation.resume(throwing: error)  // ✅ 失败也 resume
        }
    }
}

// ✅ delegate 协议声明为 AnyObject，属性用 weak
protocol NetworkManagerDelegate: AnyObject {
    func didReceiveData(_ data: Data)
    func didFailWithError(_ error: Error)
}

class NetworkManager {
    weak var delegate: NetworkManagerDelegate?  // ✅ weak 避免保留环
}
```

### 更优方案：使用 withTaskCancellationHandler

```swift
// ✅✅ 同时处理取消和超时
func fetchDataAsync(from url: URL) async throws -> Data {
    try await withCheckedThrowingContinuation { continuation in
        let task = URLSession.shared.dataTask(with: url) { data, _, error in
            if let error = error {
                continuation.resume(throwing: error)
            } else if let data = data {
                continuation.resume(returning: data)
            }
        }
        
        // ✅ 处理 Task 取消
        task.resume()
    }
}

// ✅✅ 更完整的版本：带取消和超时
func fetchWithTimeout(from url: URL, timeout: TimeInterval = 30) async throws -> Data {
    try await withThrowingTaskGroup(of: Data.self) { group in
        group.addTask {
            let (data, _) = try await URLSession.shared.data(from: url)
            return data
        }
        
        group.addTask {
            try await Task.sleep(nanoseconds: UInt64(timeout * 1_000_000_000))
            throw URLError(.timedOut)
        }
        
        let result = try await group.next()!  // 第一个完成的
        group.cancelAll()  // 取消另一个
        return result
    }
}
```

### 架构评估

| 维度 | 评分 | 说明 |
|------|------|------|
| 可读性 | ⭐⭐⭐ | continuation 桥接本身不直观，需要注释 |
| 设计模式 | ⭐⭐⭐⭐ | withCheckedThrowingContinuation 是官方推荐桥接方式 |
| 架构 | ⭐⭐ | delegate + async 混用本身是架构债务，应逐步迁移到纯 async |
| 扩展性 | ⭐⭐ | 每个桥接点都需要手动保证所有路径 resume |

**核心教训**：continuation 的契约是**恰好 resume 一次**。这是一条编译器无法完全检查的运行时不变量（`withCheckedThrowingContinuation` 只在 debug 模式下检查），类似于 Rust 中 unsafe 代码的安全不变量——**编译器信任你，但你的代码必须在所有路径上遵守契约**。

## 样本B：Go errgroup 结构化并发（好设计）

**来源**：Go Patterns (go-patterns.dev) + Atharva Pandey 博客  
**背景**：Go 1.20+ 的 `golang.org/x/sync/errgroup` 包，展示结构化并发的最佳实践

### 经典场景：Dashboard 数据聚合

```go
// ✅ 好设计：errgroup + WithContext 实现结构化并发
func fetchDashboard(ctx context.Context, userID string) (*Dashboard, error) {
    g, gctx := errgroup.WithContext(ctx)

    var (
        profile       *Profile
        orders        []*Order
        notifications []*Notification
    )

    g.Go(func() error {
        var err error
        profile, err = getProfile(gctx, userID)  // ✅ 使用 gctx 而非 ctx
        return err
    })

    g.Go(func() error {
        var err error
        orders, err = getOrders(gctx, userID)
        return err
    })

    g.Go(func() error {
        var err error
        notifications, err = getNotifications(gctx, userID)
        return err
    })

    if err := g.Wait(); err != nil {
        return nil, fmt.Errorf("fetch dashboard for %s: %w", userID, err)
    }

    return &Dashboard{
        Profile:       profile,
        Orders:        orders,
        Notifications: notifications,
    }, nil
}
```

### Step 2：四层审查

**第1轮：数据流**
- 输入：ctx + userID
- 中间：3个并发 goroutine 各自获取数据，写入各自的变量（无共享写入）
- 输出：组装的 Dashboard 或首个 error
- **亮点**：每个 goroutine 写不同的变量 → 无竞态条件

**第2轮：边界条件**
- ✅ **错误传播**：任一 goroutine 返回 error → gctx 被取消 → 其他 goroutine 可提前退出
- ✅ **并发安全**：profile/orders/notifications 分别由不同 goroutine 写入，无数据竞争
- ✅ **context 取消**：使用 gctx 传播取消信号
- ⚠️ **限制缺失**：如果 items 很多，没有并发限制 → 可能导致资源耗尽

**第3轮：必要性**
- `errgroup.WithContext` 是必要的——提供了取消传播
- `fmt.Errorf("fetch dashboard for %s: %w", ...)` 是必要的——7个调用可能失败，裸 error 无法定位
- 每个变量声明在 group 外是必要的——Wait 后才能安全读取

**反向审：AI 最可能隐瞒的3个弱点**
1. **忘记用 gctx 而用 ctx**：AI 可能照抄参数名而不理解 WithContext 返回的新 context
2. **不包装 error**：直接 `return err` 而非 `fmt.Errorf("...: %w", err)`，丢失上下文
3. **无限并发**：对 slice 做 fan-out 时不设 SetLimit，可能打爆下游服务

### 带并发限制的进阶版本

```go
// ✅ SetLimit 控制并发数
func enrichProducts(ctx context.Context, products []Product) ([]EnrichedProduct, error) {
    results := make([]EnrichedProduct, len(products))
    g, gctx := errgroup.WithContext(ctx)
    g.SetLimit(20)  // 最多 20 个并发

    for i, p := range products {
        i, p := i, p  // Go < 1.22 需要捕获循环变量
        g.Go(func() error {
            enriched, err := enrichProduct(gctx, p)
            if err != nil {
                return fmt.Errorf("enrich product %s: %w", p.ID, err)
            }
            results[i] = enriched  // ✅ 安全：每个 goroutine 写唯一索引
            return nil
        })
    }

    if err := g.Wait(); err != nil {
        return nil, err
    }
    return results, nil
}
```

### 架构评估

| 维度 | 评分 | 说明 |
|------|------|------|
| 可读性 | ⭐⭐⭐⭐⭐ | 意图清晰：并发获取、等待、组装 |
| 设计模式 | ⭐⭐⭐⭐⭐ | 结构化并发的典范——所有子任务的生命周期被 group 管理 |
| 架构 | ⭐⭐⭐⭐ | "all succeed or all cancel" 语义简洁有力 |
| 扩展性 | ⭐⭐⭐⭐ | SetLimit 支持限流，但无法收集所有错误（只返回第一个） |

**核心教训**：errgroup 体现了**结构化并发**的设计哲学——就像结构化编程消除了 goto 一样，结构化并发消除了"飘浮的 goroutine"。每个并发任务都有明确的生命周期边界。

## 样本C：Rust Rc 循环引用与 Weak 打破循环

**来源**：Rust Book (Brown University版) Ch15-6 + Rust Nomicon "Leaking"  
**背景**：Rust 所有权系统号称内存安全，但 Rc/Arc 循环引用是少数能绕过编译检查的"漏网之鱼"

### 循环引用泄漏代码

```rust
use std::rc::Rc;
use std::cell::RefCell;

#[derive(Debug)]
enum List {
    Cons(i32, RefCell<Rc<List>>),
    Nil,
}

impl List {
    fn tail(&self) -> Option<&RefCell<Rc<List>>> {
        match self {
            Cons(_, item) => Some(item),
            Nil => None,
        }
    }
}

fn main() {
    let a = Rc::new(Cons(5, RefCell::new(Rc::new(Nil))));
    println!("a initial rc count = {}", Rc::strong_count(&a));  // 1

    let b = Rc::new(Cons(10, RefCell::new(Rc::clone(&a))));
    println!("a rc count after b creation = {}", Rc::strong_count(&a));  // 2

    // ❌ 创建循环引用：a → b → a
    if let Some(link) = a.tail() {
        *link.borrow_mut() = Rc::clone(&b);
    }
    println!("b rc count after changing a = {}", Rc::strong_count(&b));  // 2
    println!("a rc count after changing a = {}", Rc::strong_count(&a));  // 2
    // a 和 b 的引用计数永远不为 0 → 内存泄漏！
}
```

### Step 2：四层审查

**第1轮：数据流**
- 输入：两个 Rc<List> 节点
- 中间：通过 RefCell 可变引用修改连接关系
- 输出：本应释放的内存永远不会被释放
- **问题**：a → b（通过 RefCell 修改）→ a 形成环，引用计数永远不为 0

**第2轮：边界条件**
- ❌ **内存泄漏**：循环引用导致 Rc 永远不释放
- ❌ **栈溢出**：如果尝试打印这个循环结构（Debug trait 会无限递归）
- ⚠️ **RefCell 运行时检查**：borrow_mut() 在已有 borrow 时会 panic
- ⚠️ **线程安全**：Rc 不是 Send/Sync，多线程需要 Arc + Mutex

**第3轮：必要性**
- `RefCell` 是必要的——需要在运行时修改不可变引用内部的值
- `Rc` 是必要的——需要多所有权（一个节点被多个父节点引用）
- 但**循环**不是必要的——这是设计错误，应该用 Weak 打破

**反向审：AI 最可能隐瞒的3个弱点**
1. **循环引用隐蔽**：AI 生成图/树结构时，默认使用 Rc 而不想到循环问题
2. **Debug trait 栈溢出**：#[derive(Debug)] 在循环结构上会导致无限递归
3. **RefCell panic**：AI 可能同时调用 borrow() 和 borrow_mut()，运行时 panic

### 修复：使用 Weak 打破循环

```rust
use std::rc::{Rc, Weak};
use std::cell::RefCell;

struct Node {
    value: i32,
    parent: RefCell<Weak<Node>>,    // ✅ Weak 引用父节点，不增加引用计数
    children: RefCell<Vec<Rc<Node>>>, // ✅ Strong 引用子节点
}

fn main() {
    let leaf = Rc::new(Node {
        value: 3,
        parent: RefCell::new(Weak::new()),
        children: RefCell::new(vec![]),
    });

    let branch = Rc::new(Node {
        value: 5,
        parent: RefCell::new(Weak::new()),
        children: RefCell::new(vec![Rc::clone(&leaf)]),
    });

    // leaf 的 parent 指向 branch，用 Weak 不增加引用计数
    *leaf.parent.borrow_mut() = Rc::downgrade(&branch);

    // branch 引用计数 = 1（只有 branch 变量持有）
    // leaf 引用计数 = 2（leaf 变量 + branch.children）
    println!("branch strong = {}", Rc::strong_count(&branch));  // 1
    println!("leaf strong = {}", Rc::strong_count(&leaf));      // 2

    // 从 leaf 访问 parent
    if let Some(parent) = leaf.parent.borrow().upgrade() {
        println!("leaf parent = {}", parent.value);  // 5
    }

    // branch 离开作用域时，其引用计数归零，正常释放
    // leaf 的 parent 变成 Weak 指向已释放的内存 → upgrade() 返回 None
}
```

### RAII 模式：确保资源释放

```rust
use std::mem::ManuallyDrop;
use std::ptr;

// ✅ 用 RAII 包装 FFI 资源
struct CBuffer {
    data: *mut u8,
    len: usize,
}

impl CBuffer {
    fn new(len: usize) -> Self {
        let data = unsafe { libc::malloc(len) as *mut u8 };
        assert!(!data.is_null(), "Allocation failed");
        CBuffer { data, len }
    }
}

impl Drop for CBuffer {
    fn drop(&mut self) {
        unsafe { libc::free(self.data as *mut libc::c_void) };
    }
}

// ✅ ManuallyDrop 替代 mem::forget（更安全的所有权转移）
fn transfer_ownership() {
    let v = vec![65, 122];
    let mut v = ManuallyDrop::new(v);  // ✅ 先禁用析构
    let (ptr, len, cap) = (v.as_mut_ptr(), v.len(), v.capacity());
    let s = unsafe { String::from_raw_parts(ptr, len, cap) };
    // s 离开作用域时正常释放，不会 double-free
}
```

### 架构评估

| 维度 | 评分 | 说明 |
|------|------|------|
| 可读性 | ⭐⭐⭐ | Weak/Strong 区分需要经验，但命名清晰 |
| 设计模式 | ⭐⭐⭐⭐⭐ | Weak 是观察者模式在所有权系统中的优雅实现 |
| 架构 | ⭐⭐⭐⭐ | 所有权树 + Weak 回指，是 DAG 的经典建模方式 |
| 扩展性 | ⭐⭐⭐ | 多线程需要 Arc + Mutex，API 会变复杂 |

**核心教训**：Rust 的所有权系统解决的是**单所有权 + 生命周期**问题，但图/树等需要多所有权的数据结构是它的盲区。Weak 是 Rust 给出的答案——**弱引用不是妥协，而是对"非必须存活"关系的精确建模**。

## 跨语言对比：异步生命周期管理

### 核心问题：谁负责资源的开始和结束？

| 语言 | 机制 | 资源开始 | 资源结束 | 失败路径 |
|------|------|----------|----------|----------|
| **Swift** | continuation | `withCheckedContinuation` | `resume` (恰好一次) | 必须在所有路径 resume |
| **Go** | errgroup | `g.Go(func() error {...})` | `g.Wait()` | context 取消 + error 返回 |
| **Rust** | ownership | `Rc::new()` / `Arc::new()` | 引用计数归零时 Drop | Weak::upgrade() 返回 None |

### 跨语言智慧映射

| 概念 | Swift | Go | Rust |
|------|-------|----|------|
| 弱引用 | `weak var delegate` | N/A (GC 处理) | `Weak<T>` / `Arc::downgrade` |
| 取消传播 | `Task.cancel()` + `withTaskCancellationHandler` | `context.Context` | `tokio::sync::CancellationToken` |
| 资源释放保证 | `defer` / `deinit` | `defer` | `Drop` trait (RAII) |
| 结构化并发 | `TaskGroup` / `withThrowingTaskGroup` | `errgroup.WithContext` | `tokio::task::JoinSet` |
| 错误聚合 | 只抛第一个 | 只返回第一个 error | `JoinError` 包含多个 |

### 深层规律

1. **结构化并发的共同趋势**：三个语言都在走向"并发任务有明确生命周期边界"的方向
   - Swift: `TaskGroup` → 子任务随 group 生命周期
   - Go: `errgroup` → goroutine 随 Wait 结束
   - Rust: `JoinSet` → 任务可被集体 abort

2. **弱引用的普遍性**：当"持有引用"≠"持有所有权"时，需要弱引用
   - Swift: `weak var` 防止保留环
   - Rust: `Weak<T>` 打破 Rc 循环
   - Go: 无需（GC 处理循环引用）
   - Java: `WeakReference` / `SoftReference`

3. **"恰好一次"语义的普遍挑战**：
   - Swift continuation: 必须恰好 resume 一次
   - Go channel: 必须恰好 close 一次（且由发送方关闭）
   - Rust Drop: 必须恰好执行一次（mem::forget 是安全但危险的逃逸阀）

## 今日模式积累

### 新增审查模式

#### 异步桥接遗漏路径 ⭐⭐⭐⭐⭐

**识别特征**：
- 将 callback/delegate 模式桥接到 async/await 时
- withCheckedThrowingContinuation / withCheckedContinuation 内
- 只有 happy path 的 resume，缺少 error/cancel/timeout 路径

**审查要点**：
- [ ] continuation 在所有代码路径上是否恰好 resume 一次？
- [ ] 是否处理了 Task 取消？
- [ ] 是否有超时保护？
- [ ] delegate 是否有保留环风险？

#### 结构化并发模式 ✅

**识别特征**：
- 使用 errgroup / TaskGroup / JoinSet 管理并发任务
- 任务有明确的开始和结束边界
- 错误能传播、取消能级联

**审查要点**：
- [ ] 是否使用了 WithContext / gctx 传播取消？
- [ ] 是否有并发限制（SetLimit / semaphore）？
- [ ] error 是否包含足够的上下文信息？
- [ ] 共享变量的写入是否安全？

#### 所有权循环陷阱 ⭐⭐⭐⭐

**识别特征**：
- 使用 Rc/Arc 构建图/树结构
- 节点之间有双向引用
- 缺少 Weak 来打破循环

**审查要点**：
- [ ] 是否存在循环引用的可能？
- [ ] 父→子用 Strong，子→父用 Weak？
- [ ] Debug/Display 是否会导致无限递归？
- [ ] RefCell/Mutex 的 borrow 是否会 panic/deadlock？
