# AI代码审查模式库

> 记录AI生成代码的常见问题模式，供审查时快速识别

---

## 一、性能问题模式

### 1.1 重复计算陷阱 ⭐⭐⭐⭐⭐

**识别特征**：
- 循环内部调用高开销函数（toLowerCase, JSON.parse等）
- filter后立即sort，形成双重遍历
- 每次渲染重新计算而非缓存

**典型代码**：
```javascript
// ❌ AI常犯：每次渲染都计算
const filtered = data.filter(item => expensiveOperation(item));
const sorted = [...filtered].sort(comparator);

// ✅ 正确：使用useMemo缓存
const processed = useMemo(() => {
    return data.filter(item => expensiveOperation(item))
               .sort(comparator);
}, [data]);
```

**审查要点**：
- [ ] 是否有useMemo/useCallback包裹？
- [ ] 依赖数组是否正确？
- [ ] 是否有防抖优化输入响应？

---

### 1.2 不必要的数组拷贝

**识别特征**：
- `[...array]`后紧跟sort
- spread操作符用于非必要场景
- 大量小对象spread创建GC压力

**典型代码**：
```javascript
// ❌ AI常犯：sort是就地算法，拷贝多余
const sorted = [...unsorted].sort((a,b) => a-b);

// ✅ 正确：直接排序
unsorted.sort((a,b) => a-b);
```

---

### 1.3 内存泄漏模式

**识别特征**：
- useEffect无return清理函数
- 事件监听器未移除
- WebSocket/定时器未关闭

**典型代码**：
```javascript
// ❌ AI常犯：缺少清理
useEffect(() => {
    const ws = new WebSocket(url);
    ws.onmessage = handler;
}, [url]);

// ✅ 正确：清理函数
useEffect(() => {
    const ws = new WebSocket(url);
    ws.onmessage = handler;
    return () => ws.close();
}, [url]);
```

## 二、逻辑错误模式

### 2.1 假设未验证 ⭐⭐⭐⭐⭐

**识别特征**：
- AI声称"基于X假设，Y成立"
- 使用外部库常量但未查证
- 依赖"看起来合理"的行为

**典型案例**（Claude Code生产Bug）：
```python
# ❌ AI假设drop_params会删除参数名和值
response = llm.chat(
    fallbacks=[{"model": "...", "reasoning_effort": "disable"}],
    drop_params=True  # 实际上只删除不支持的参数名，不删除不支持的参数值
)
```

**审查要点**：
- [ ] 是否验证了外部库的实际行为？
- [ ] 是否检查了关键常量的实际值？
- [ ] 是否在文档中明确标注了假设？

---

### 2.2 条件判断错误 ⭐⭐⭐⭐

**识别特征**：
- 索引从1开始 vs 从0开始的混淆
- 边界条件判断反向（< vs <=）
- 逻辑运算符错误（&& vs ||）

**典型代码**：
```javascript
// ❌ AI常犯：边界条件错误
if (index > array.length) {  // 应该是 >=
    return array[index - 1];
}

// ✅ 正确
if (index >= array.length) {
    return array[array.length - 1];
}
```

---

### 2.3 数学知识错误 ⭐⭐⭐

**识别特征**：
- 公式推导错误
- 运算顺序错误
- 统计量计算错误（方差、协方差等）

**典型代码**：
```python
# ❌ AI常犯：样本方差用n而非n-1
variance = sum((x - mean)**2 for x in data) / len(data)

# ✅ 正确：样本方差
variance = sum((x - mean)**2 for x in data) / (len(data) - 1)
```

---

### 2.4 Wrong Variable Return ⭐⭐

**识别特征**：
- 计算正确但返回了错误的变量
- 多个相似变量名导致混淆
- 条件分支返回不一致

**典型代码**：
```python
# ❌ AI常犯：结果存错变量
max_product = max(a*b for a,b in zip(list1, list2))
min_product = min(a*b for a,b in zip(list1, list2))
return max_product  # 题目要求返回最小，乘法却返回了最大

# ✅ 正确
return min_product
```

## 三、数据结构问题模式

### 3.1 不适当的数据结构选择

**识别特征**：
- 需要保持顺序时使用了set
- 需要去重时使用了list导致O(n²)
- 缺少对应数据结构的特性考虑

**典型代码**：
```javascript
// ❌ AI常犯：set丢失顺序
const duplicates = [...new Set(items)];  // 顺序丢失！

// ✅ 正确：保持顺序去重
const seen = new Set();
const unique = items.filter(item => {
    if (seen.has(item.id)) return false;
    seen.add(item.id);
    return true;
});
```

---

### 3.2 API返回处理错误

**识别特征**：
- 假设API返回可变类型
- 未处理Promise/Stream的异步特性
- 缺少错误处理

**典型代码**：
```javascript
// ❌ AI常犯：未处理API返回特性
const result = api.streamData();  // 返回不可变流
result.push(additionalData);  // 失败！

// ✅ 正确：使用正确方法
const result = api.streamData().toList();
result.push(additionalData);
```

## 四、安全问题模式

### 4.1 SQL注入漏洞 ⭐⭐⭐⭐⭐

**识别特征**：
- 字符串拼接构建SQL
- 用户输入直接进入查询
- 缺少输入验证

**典型代码**：
```python
# ❌ AI常犯：SQL注入风险
query = f"SELECT * FROM users WHERE name = '{username}'"
cursor.execute(query)

# ✅ 正确：参数化查询
query = "SELECT * FROM users WHERE name = %s"
cursor.execute(query, (username,))
```

---

### 4.2 硬编码秘密

**识别特征**：
- API密钥、密码写在代码中
- 数据库连接字符串明文
- 环境变量未外部化

**典型代码**：
```python
# ❌ AI常犯：硬编码密钥
API_KEY = "sk-xxxx-secret-key-here"

# ✅ 正确：环境变量
API_KEY = os.environ.get("API_KEY")
```

---

### 4.3 权限校验缺失

**识别特征**：
- 前端隐藏入口误以为后端受保护
- 信任客户端输入
- 缺少服务端权限验证

**典型代码**：
```javascript

{/* <button onClick={handleAdmin}>Admin</button> */}
// 后端API仍然开放！
app.post('/api/admin', async (req, res) => {

```

## 五、异步和并发问题模式

### 5.1 缺少async/await

**识别特征**：
- fetch调用后未await
- Promise链不完整
- 错误处理缺失

**典型代码**：
```javascript
// ❌ AI常犯：遗漏await
function getData() {
    const result = fetch('/api/data');  // 返回Promise而非数据
    return result;  // 返回类型错误
}

// ✅ 正确
async function getData() {
    const response = await fetch('/api/data');
    return response.json();
}
```

---

### 5.2 竞态条件

**识别特征**：
- useEffect中直接使用state闭包
- 依赖外部状态但不加入依赖数组
- 缺少取消/中止机制

**典型代码**：
```javascript
// ❌ AI常犯：闭包持有旧state
useEffect(() => {
    fetchData().then(data => setData(data));  // data是旧值
}, []);

// ✅ 正确：使用ref或正确的依赖
useEffect(() => {
    let cancelled = false;
    fetchData().then(data => {
        if (!cancelled) setData(data);
    });
    return () => { cancelled = true; };
}, []);
```

## 六、Java并发安全模式 ⭐⭐⭐⭐⭐

> AI生成Java并发代码的高危模式，全部具备"测试通过、上线炸裂"特征

### 6.1 synchronized集合迭代删除 (CONC-001)

**识别特征**：
- `Collections.synchronizedList/Map/Set()` + for-each + remove
- 对synchronized包装器的复合操作（迭代+修改）

**典型代码**：
```java
// ❌ AI常犯：synchronizedList不保护迭代
private List<T> items = Collections.synchronizedList(new ArrayList<>());
for (T item : items) {
    if (shouldRemove(item)) items.remove(item); // ConcurrentModificationException
}

// ✅ 正确：使用ConcurrentLinkedQueue
private ConcurrentLinkedQueue<T> items = new ConcurrentLinkedQueue<>();
items.removeIf(this::shouldRemove);
```

**审查要点**：
- [ ] synchronized*()包装器的所有迭代操作是否原子？
- [ ] 是否应该替换为java.util.concurrent集合？

---

### 6.2 Virtual Thread synchronized pinning (CONC-002)

**识别特征**：
- `synchronized`方法/块 + Virtual Thread环境
- synchronized内含IO/网络/数据库操作

**典型代码**：
```java
// ❌ AI常犯：synchronized在Virtual Thread中pin住载体线程
public synchronized void transfer(Account from, Account to, BigDecimal amount) {
    from.debit(amount);  // DB操作
    to.credit(amount);   // DB操作
    auditLog.record();   // 网络调用
}

// ✅ 正确：ReentrantLock + tryLock超时
private final ReentrantLock lock = new ReentrantLock();
public void transfer(...) throws InterruptedException {
    if (lock.tryLock(5, TimeUnit.SECONDS)) {
        try { ... } finally { lock.unlock(); }
    }
}
```

**性能影响**：synchronized ~50 TPS → ReentrantLock ~500 TPS（10倍）

---

### 6.3 双重检查锁定缺少volatile (CONC-003)

**识别特征**：
- `if(x==null) synchronized { if(x==null) x = new ... }` 无volatile
- 延迟初始化模式

**典型代码**：
```java
// ❌ AI常犯：JMM允许指令重排序，返回半构造对象
private static Resource resource;
public static Resource getInstance() {
    if (resource == null) {
        synchronized (ResourceFactory.class) {
            if (resource == null) resource = new Resource(); // 可能看到半构造对象
        }
    }
    return resource;
}

// ✅ 正确：静态内部类Holder模式
private static class Holder { static final Resource INSTANCE = new Resource(); }
public static Resource getInstance() { return Holder.INSTANCE; }
```

---

### 6.4 价值类对象作锁 (CONC-004)

**识别特征**：
- `synchronized(Boolean/Integer/String)` 作为锁对象
- `private static final Boolean lock = Boolean.FALSE`

**典型代码**：
```java
// ❌ AI常犯：Boolean.FALSE在整个JVM中共享
private static final Boolean lock = Boolean.FALSE;
synchronized (lock) { ... }  // 与所有使用Boolean.FALSE的代码竞争同一锁

// ✅ 正确：专用Object实例
private final Object lock = new Object();
synchronized (lock) { ... }
```

**危险范围**：Boolean、Integer(-128~127缓存)、String常量池、List.of()、java.time类型

---

### 6.5 Structured Concurrency范围泄漏 (CONC-005)

**识别特征**：
- `scope.fork()` 无 `scope.join()`
- try-with-resources关闭scope时子任务未完成

**典型代码**：
```java
// ❌ AI常犯：漏掉join，僵尸线程泄漏
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    scope.fork(() -> process(order));
    // 缺少 scope.join()
}

// ✅ 正确：join + throwIfFailed
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    var tasks = orders.stream().map(o -> scope.fork(() -> process(o))).toList();
    scope.join();
    scope.throwIfFailed();
    return tasks.stream().map(Subtask::get).toList();
}
```

---

### 6.6 CompletableFuture异常吞噬 (CONC-006)

**识别特征**：
- CompletableFuture链式调用无 whenComplete/handle/orTimeout
- 异步操作无超时控制

**典型代码**：
```java
// ❌ AI常犯：异常静默丢失
return CompletableFuture.supplyAsync(() -> fetch(id))
    .thenCompose(this::validate)
    .thenApply(this::buildResult);
// 任何步骤失败 → 调用方永远收不到结果

// ✅ 正确：超时 + 日志 + 降级
return CompletableFuture.supplyAsync(() -> fetch(id))
    .thenCompose(this::validate)
    .thenApply(this::buildResult)
    .orTimeout(5, TimeUnit.SECONDS)
    .whenComplete((r, ex) -> { if (ex != null) log.error(...); })
    .handle((r, ex) -> ex != null ? fallback(id) : r);
```

---

### 6.7 锁内Thread.sleep (CONC-007)

**识别特征**：
- `synchronized { Thread.sleep() }` 轮询等待
- 持有锁时sleep不释放monitor

**典型代码**：
```java
// ❌ AI常犯：sleep不释放锁，其他线程无法进入
synchronized (monitor) {
    while (!ready()) Thread.sleep(200);  // 死锁风险
    process();
}

// ✅ 正确：wait释放锁，允许其他线程修改状态
synchronized (monitor) {
    while (!ready()) monitor.wait(200);
    process();
}
```

## 七、Spring Boot/Java后端事务模式

### 7.1 事务内外部调用陷阱 ⭐⭐⭐⭐⭐

**识别特征**：
- @Transactional方法内调用外部API（HTTP/RPC/MQ）
- 数据库锁持有时间覆盖了外部调用时间
- 外部调用失败导致事务回滚但锁已持有

**典型案例**（TossPayment支付确认）：
```java
// ❌ 事务内外部调用：锁持有覆盖了网络调用时间
@Transactional
public PaymentResponse confirmPayment(User user, PaymentConfirmRequest request) {
    Payment payment = repository.findByOrderIdForUpdate(request.getOrderId()); // 加悲观锁
    // ... 校验 ...
    Map<String, Object> response = tossPaymentClient.confirmPayment(request); // 外部API调用！
    payment.confirm(request.getPaymentKey(), method);
    return PaymentResponse.from(payment);
}

// ✅ 改进：先调外部API，再开事务更新（最短锁持有时间）
public PaymentResponse confirmPayment(User user, PaymentConfirmRequest request) {
    Payment payment = repository.findByOrderId(request.getOrderId()).orElseThrow(...);
    validate(user, payment, request);                        // 无事务校验
    TossConfirmResponse response = tossClient.confirm(request); // 外部调用（无锁）
    return updatePaymentStatus(request, response);           // 单独事务+锁
}
```

**审查要点**：
- [ ] @Transactional方法内是否有外部API/RPC调用？
- [ ] 数据库锁持有时间是否覆盖了网络调用时间？
- [ ] 外部调用失败时的回滚策略是否合理？

---

### 7.2 AI重构隐性规则丢失 ⭐⭐⭐⭐⭐

**识别特征**：
- AI将大方法拆分时，某些看似"计算逻辑"的代码实为"业务规则"
- filter/map操作被"优化"到其他层
- 业务约束只存在于代码中，无注释、无文档

**典型案例**（账单重复计算事故）：
```java
// 原代码
transactions = transactions.stream()
    .filter(t -> t.getBillId() == null)  // 看似简单null过滤，实际是"流水不能重复出账"
    .collect(Collectors.toList());

// AI重构后 —— filter被"优化"掉
List<Transaction> transactions = queryBillData(merchantId, startDate, endDate);
BigDecimal totalAmount = calculateBillAmount(transactions); // 未过滤，已出账流水重复计算
```

**防御策略**：
```java
// ✅ 每个filter/条件判断加上业务规则注释
/**
 * [业务规则] 结算协议4.2条：同一笔流水只能归入一期账单。
 * billId不为null表示该流水已被归入历史账单，当期不得重复计算。
 */
transactions = transactions.stream()
    .filter(t -> t.getBillId() == null)
    .collect(Collectors.toList());
```

**审查要点**：
- [ ] 每个filter/条件判断是否有业务规则注释？
- [ ] AI重构时是否逐条对照规则清单？
- [ ] 隐性规则是否已文档化？

### 7.3 @Transactional 静默失败五连 ⭐⭐⭐⭐⭐

**识别特征**：
- @Transactional注解存在但事务实际不生效
- 无编译错误、无运行时异常、数据静默出错
- 银行支付场景下表现为资金无声丢失

**五种模式及典型代码**：

```java
// 模式1：自调用绕过代理
public void placeOrder(Order order) {
    saveOrder(order);  // this.saveOrder() — 代理不拦截
}
@Transactional
public void saveOrder(Order order) { ... }  // 注解装饰性的

// 模式2：Checked异常默认提交
@Transactional  // ← 缺少 rollbackFor
public void transfer(Long fromId, Long toId, BigDecimal amount) throws IOException {
    from.debit(amount);
    accountRepository.save(from);  // 已持久化
    complianceClient.check(from);  // 抛IOException → 事务提交！资金丢失
}

// 模式3：private/final方法
@Transactional
private void persistPayment(Payment p) { ... }  // CGLIB无法override

// 模式4：REQUIRES_NEW连接池死锁
@Transactional  // 持有conn#1
public void createOrder(Order order) {
    orderRepository.save(order);
    auditService.logAudit(...);  // REQUIRES_NEW需要conn#2 → 池耗尽 → 死锁
}

// 模式5：readOnly=true静默丢弃写入
@Transactional(readOnly = true)
public class ProductService {
    public void updatePrice(Long id, BigDecimal price) {
        p.setPrice(price);  // Hibernate不flush — 修改静默丢失
    }
}
```

**统一本质**：所有模式都是**绕过了代理**——this调用、private无法拦截、checked异常绕过回滚逻辑、REQUIRES_NEW绕过当前事务上下文、readOnly绕过dirty checking。

**审查要点**：
- [ ] 是否有this.xxx()调用@Transactional方法？
- [ ] 是否显式声明rollbackFor=Exception.class？
- [ ] @Transactional方法是否为public且非final？
- [ ] REQUIRES_NEW是否用@TransactionalEventListener(AFTER_COMMIT)解耦？
- [ ] 类级readOnly=true上的写方法是否显式@Override？
- [ ] 连接池容量 ≥ 并发量 × (1 + REQUIRES_NEW方法数)？

## 八、废弃API使用模式 ⭐⭐⭐

### 8.1 Spring Security废弃API ⭐⭐⭐⭐

**识别特征**：
- 使用`withDefaultPasswordEncoder()`（已废弃）
- 继承`WebSecurityConfigurerAdapter`（Spring Boot 3已移除）
- 使用`authorizeRequests()`而非`authorizeHttpRequests()`

**典型代码**：
```java
// ❌ AI常犯：使用已废弃的API
@Bean
public UserDetailsService userDetailsService() {
    UserDetails user = User.withDefaultPasswordEncoder()  // ⚠️ 已废弃!
        .username("admin")
        .password("password")
        .roles("USER")
        .build();
    return new InMemoryUserDetailsManager(user);
}

// ❌ Spring Boot 3+ 无法编译
@Configuration
@EnableWebSecurity
public class SecurityConfig extends WebSecurityConfigurerAdapter {  // ⚠️ 废弃!
    @Override
    protected void configure(HttpSecurity http) throws Exception {  // ⚠️ 废弃!
        http.authorizeRequests()  // ⚠️ 废弃!
            .antMatchers("/api/public/**").permitAll()  // ⚠️ 废弃!
            .anyRequest().authenticated();
    }
}

// ✅ 正确：使用新API
@Configuration
@EnableWebSecurity
public class SecurityConfig {
    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        return http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/public/**").permitAll()
                .anyRequest().authenticated()
            )
            .build();
    }

    @Bean
    public UserDetailsService userDetailsService(PasswordEncoder passwordEncoder) {
        UserDetails user = User.builder()
            .username("admin")
            .password(passwordEncoder.encode("password"))  // 使用注入的encoder
            .roles("USER")
            .build();
        return new InMemoryUserDetailsManager(user);
    }
}
```

**审查要点**：
- [ ] 是否使用`withDefaultPasswordEncoder()`？
- [ ] 是否继承`WebSecurityConfigurerAdapter`？
- [ ] 是否使用`authorizeRequests()`/`antMatchers()`？

### 8.2 Java Stream废弃API ⭐⭐⭐

**识别特征**：
- 使用`Collectors.toList()`（Java 16+已废弃）
- 应直接使用`.toList()`

**典型代码**：
```java
// ⚠️ AI生成的代码（产生警告）
List<String> names = users.stream()
    .map(User::getName)
    .filter(name -> !name.isEmpty())
    .collect(Collectors.toList());  // ⚠️ Java 16+ 废弃

// ✅ 正确：Java 16+ 更简洁
List<String> names = users.stream()
    .map(User::getName)
    .filter(name -> !name.isEmpty())
    .toList();
```

**审查要点**：
- [ ] 是否使用`Collectors.toList()`？改为`.toList()`
- [ ] 是否使用`Collectors.toSet()`？改为`.toSet()`
- [ ] 是否使用`Collectors.toUnmodifiableList()`？改为`.toList()`

## 九、Swift并发陷阱模式 ⭐⭐⭐⭐

### 9.1 串行执行而非并行 ⭐⭐⭐⭐

**识别特征**：
- 多个无依赖的async调用顺序await
- 总耗时 = t1 + t2 + t3而非max(t1, t2, t3)

**典型代码**：
```swift
// ❌ 串行执行：总耗时 = t1 + t2 + t3
let user = await getUser()           // 先等
let address = await getAddress(of: user)  // 再等
let payment = await getPayment(of: user) // 最后等

// ✅ 并行执行：总耗时 = max(t1, t2, t3)
async let user = getUser()
async let address = getAddress(of: user)
async let payment = getPayment(of: user)

let (fetchedUser, fetchedAddress, fetchedPayment) = try await (user, address, payment)
```

**跨语言对比**：JavaScript的`Promise.all()`、Java的`CompletableFuture.allOf()`异曲同工

**审查要点**：
- [ ] 多个async调用是否可以并行？
- [ ] 是否使用`async let`或`TaskGroup`并行化？

---

### 9.2 Task隐式捕获self导致内存泄漏 ⭐⭐⭐⭐⭐

**识别特征**：
- Task内访问self但未使用`[weak self]`
- Task永不结束（如监听无限序列）
- ViewController释放后整个对象树无法释放

**典型代码**：
```swift
// ❌ Task隐式捕获self，永不释放
@MainActor
class ViewModel {
    func listenToNotifications() {
        Task {
            // ⚠️ self被隐式捕获，且永不释放
            let notifications = NotificationCenter.default.notifications(
                named: UIDevice.orientationDidChangeNotification
            )
            for await notification in notifications {
                self.handle(notification)  // Task持有self，强引用
            }
        }
    }
}

// ✅ 正确：weak self + 内部unwrap
@MainActor
class ViewModel {
    func listenToNotifications() {
        Task { [weak self] in
            guard let self else { return }

            let notifications = NotificationCenter.default.notifications(
                named: UIDevice.orientationDidChangeNotification
            )

            for await notification in notifications {
                self.handle(notification)
            }
            // ✅ 循环内部unwrap，确保Task可以正常结束
        }
    }
}
```

**关键点**：`weak self`必须在`for`循环**内部**unwrap，而非外部

**审查要点**：
- [ ] Task是否永不结束？
- [ ] Task内是否访问self？
- [ ] 是否使用`[weak self]`？

---

### 9.3 滥用Task.detached ⭐⭐⭐

**识别特征**：
- 使用`Task.detached`而非普通`Task`
- 脱离父任务的actor上下文
- 需要额外的await访问`@MainActor`标记的属性

**典型代码**：
```swift
// ❌ 滥用Task.detached
@MainActor
class ViewModel {
    func listenToNotifications() {
        Task.detached { [weak self] in  // ⚠️ 脱离@MainActor上下文
            let notifications = await NotificationCenter.default.notifications(
                named: UIDevice.orientationDidChangeNotification
            )

            for await notification in notifications {
                guard let self else { return }
                await self.handle(notification)  // 需要额外的await
            }
        }
    }
}

// ✅ 正确：优先使用普通Task
@MainActor
class ViewModel {
    func listenToNotifications() {
        Task { [weak self] in  // 自动继承@MainActor上下文
            guard let self else { return }
            let notifications = NotificationCenter.default.notifications(
                named: UIDevice.orientationDidChangeNotification
            )
            for await notification in notifications {
                self.handle(notification)  // 无需额外await
            }
        }
    }
}
```

**审查要点**：
- [ ] 是否确实需要`Task.detached`？
- [ ] 能否用普通`Task`替代？

## 十、并发上下文传播失败 ⭐⭐⭐⭐⭐

### 10.1 Java ScopedValue不传播到ExecutorService ⭐⭐⭐⭐⭐

**识别特征**：
- 使用`ScopedValue.where().run()`绑定值
- 在run()内使用`ExecutorService.submit()`
- 子线程中调用`ScopedValue.get()`抛出`NoSuchElementException`

**典型代码**：
```java
// ❌ ScopedValue绑定不传播到ExecutorService
static final ScopedValue<String> REQUEST_ID = ScopedValue.newInstance();

void handleRequest(String id) {
    ScopedValue.where(REQUEST_ID, id).run(() -> {
        executor.submit(() -> {  // ⚠️ 线程来自ExecutorService
            String reqId = REQUEST_ID.get(); // NoSuchElementException!
            processAsync(reqId);
        });
    });
}

// ✅ 正确：使用StructuredTaskScope继承绑定
void handleRequest(String id) throws Exception {
    ScopedValue.where(REQUEST_ID, id).call(() -> {
        try (var scope = StructuredTaskScope.open(Joiner.allSuccessfulOrThrow())) {
            scope.fork(() -> {
                String reqId = REQUEST_ID.get(); // ✅ 正确继承
                processAsync(reqId);
                return null;
            });
            scope.join();
        }
        return null;
    });
}
```

**审查要点**：
- [ ] ScopedValue绑定是否传播到了子线程？
- [ ] 是否使用StructuredTaskScope而非ExecutorService？

---

### 10.2 Swift Task-local在detached Task中丢失 ⭐⭐⭐⭐

**识别特征**：
- 使用`@TaskLocal`标记的值
- 在`Task.detached`中访问
- 值丢失或无法正确访问

**典型代码**：
```swift
// ❌ Task.local在detached中丢失
@TaskLocal static var userID: String?

func processRequest() async {
    $userID.withValue("user123") {
        // 普通Task可以访问
        Task {
            print(userID) // ✅ "user123"
        }

        // detached Task丢失
        Task.detached {
            print(userID) // ⚠️ nil
        }
    }
}

// ✅ 正确：避免detached或手动传递
func processRequest() async {
    $userID.withValue("user123") {
        Task {
            // 使用普通Task
            await performWork()
        }
    }
}

@MainActor
func performWork() async {
    // 可以访问Task-local
    print(userID) // ✅ "user123"
}
```

**审查要点**：
- [ ] 是否在`Task.detached`中访问`@TaskLocal`？
- [ ] 能否用普通`Task`替代？

### 10.3 Java ScopedValue.where()结果被丢弃 ⭐⭐⭐

**识别特征**：
- 调用`ScopedValue.where()`但未调用`.run()`或`.call()`
- Carrier结果被丢弃
- 绑定从未激活

**典型代码**：
```java
// ⚠️ Carrier结果被丢弃，绑定从未激活
static final ScopedValue<String> THEME = ScopedValue.newInstance();

ScopedValue.where(THEME, "DARK");  // ❌ 未调用run/call

// 下一行抛出NoSuchElementException
String currentTheme = THEME.get();

// ✅ 正确消费Carrier
ScopedValue.where(THEME, "DARK").run(this::renderUI);
```

**审查要点**：
- [ ] `ScopedValue.where()`后是否调用了`.run()`或`.call()`？
