# AI代码审查模式库

> 记录AI生成代码的常见问题模式，供审查时快速识别

---

## 一、性能问题模式

### 1.1 重复计算陷阱 ⭐⭐⭐⭐⭐

**识别特征**：
- 循环内部调用高开销函数（toLowerCase, JSON.parse等）
- filter后立即sort，形成双重遍历
- 每次渲染重新计算而非缓存

**典型代码**：
```javascript
// ❌ AI常犯：每次渲染都计算
const filtered = data.filter(item => expensiveOperation(item));
const sorted = [...filtered].sort(comparator);

// ✅ 正确：使用useMemo缓存
const processed = useMemo(() => {
    return data.filter(item => expensiveOperation(item))
               .sort(comparator);
}, [data]);
```

**审查要点**：
- [ ] 是否有useMemo/useCallback包裹？
- [ ] 依赖数组是否正确？
- [ ] 是否有防抖优化输入响应？

---

### 1.2 不必要的数组拷贝

**识别特征**：
- `[...array]`后紧跟sort
- spread操作符用于非必要场景
- 大量小对象spread创建GC压力

**典型代码**：
```javascript
// ❌ AI常犯：sort是就地算法，拷贝多余
const sorted = [...unsorted].sort((a,b) => a-b);

// ✅ 正确：直接排序
unsorted.sort((a,b) => a-b);
```

---

### 1.3 内存泄漏模式

**识别特征**：
- useEffect无return清理函数
- 事件监听器未移除
- WebSocket/定时器未关闭

**典型代码**：
```javascript
// ❌ AI常犯：缺少清理
useEffect(() => {
    const ws = new WebSocket(url);
    ws.onmessage = handler;
}, [url]);

// ✅ 正确：清理函数
useEffect(() => {
    const ws = new WebSocket(url);
    ws.onmessage = handler;
    return () => ws.close();
}, [url]);
```

## 二、逻辑错误模式

### 2.1 假设未验证 ⭐⭐⭐⭐⭐

**识别特征**：
- AI声称"基于X假设，Y成立"
- 使用外部库常量但未查证
- 依赖"看起来合理"的行为

**典型案例**（Claude Code生产Bug）：
```python
# ❌ AI假设drop_params会删除参数名和值
response = llm.chat(
    fallbacks=[{"model": "...", "reasoning_effort": "disable"}],
    drop_params=True  # 实际上只删除不支持的参数名，不删除不支持的参数值
)
```

**审查要点**：
- [ ] 是否验证了外部库的实际行为？
- [ ] 是否检查了关键常量的实际值？
- [ ] 是否在文档中明确标注了假设？

---

### 2.2 条件判断错误 ⭐⭐⭐⭐

**识别特征**：
- 索引从1开始 vs 从0开始的混淆
- 边界条件判断反向（< vs <=）
- 逻辑运算符错误（&& vs ||）

**典型代码**：
```javascript
// ❌ AI常犯：边界条件错误
if (index > array.length) {  // 应该是 >=
    return array[index - 1];
}

// ✅ 正确
if (index >= array.length) {
    return array[array.length - 1];
}
```

---

### 2.3 数学知识错误 ⭐⭐⭐

**识别特征**：
- 公式推导错误
- 运算顺序错误
- 统计量计算错误（方差、协方差等）

**典型代码**：
```python
# ❌ AI常犯：样本方差用n而非n-1
variance = sum((x - mean)**2 for x in data) / len(data)

# ✅ 正确：样本方差
variance = sum((x - mean)**2 for x in data) / (len(data) - 1)
```

---

### 2.4 Wrong Variable Return ⭐⭐

**识别特征**：
- 计算正确但返回了错误的变量
- 多个相似变量名导致混淆
- 条件分支返回不一致

**典型代码**：
```python
# ❌ AI常犯：结果存错变量
max_product = max(a*b for a,b in zip(list1, list2))
min_product = min(a*b for a,b in zip(list1, list2))
return max_product  # 题目要求返回最小，乘法却返回了最大

# ✅ 正确
return min_product
```

## 三、数据结构问题模式

### 3.1 不适当的数据结构选择

**识别特征**：
- 需要保持顺序时使用了set
- 需要去重时使用了list导致O(n²)
- 缺少对应数据结构的特性考虑

**典型代码**：
```javascript
// ❌ AI常犯：set丢失顺序
const duplicates = [...new Set(items)];  // 顺序丢失！

// ✅ 正确：保持顺序去重
const seen = new Set();
const unique = items.filter(item => {
    if (seen.has(item.id)) return false;
    seen.add(item.id);
    return true;
});
```

---

### 3.2 API返回处理错误

**识别特征**：
- 假设API返回可变类型
- 未处理Promise/Stream的异步特性
- 缺少错误处理

**典型代码**：
```javascript
// ❌ AI常犯：未处理API返回特性
const result = api.streamData();  // 返回不可变流
result.push(additionalData);  // 失败！

// ✅ 正确：使用正确方法
const result = api.streamData().toList();
result.push(additionalData);
```

## 四、安全问题模式

### 4.1 SQL注入漏洞 ⭐⭐⭐⭐⭐

**识别特征**：
- 字符串拼接构建SQL
- 用户输入直接进入查询
- 缺少输入验证

**典型代码**：
```python
# ❌ AI常犯：SQL注入风险
query = f"SELECT * FROM users WHERE name = '{username}'"
cursor.execute(query)

# ✅ 正确：参数化查询
query = "SELECT * FROM users WHERE name = %s"
cursor.execute(query, (username,))
```

```python
# ❌ AI常犯：硬编码密钥
API_KEY = "sk-xxxx-secret-key-here"

API_KEY = os.environ.get("API_KEY")
```

### 4.3 权限校验缺失

## 五、异步和并发问题模式

### 5.1 缺少async/await

**识别特征**：
- fetch调用后未await
- Promise链不完整
- 错误处理缺失

**典型代码**：
```javascript
// ❌ AI常犯：遗漏await
function getData() {
    const result = fetch('/api/data');  // 返回Promise而非数据
    return result;  // 返回类型错误
}

// ✅ 正确
async function getData() {
    const response = await fetch('/api/data');
    return response.json();
}
```

---

### 5.2 竞态条件

**识别特征**：
- useEffect中直接使用state闭包
- 依赖外部状态但不加入依赖数组
- 缺少取消/中止机制

**典型代码**：
```javascript
// ❌ AI常犯：闭包持有旧state
useEffect(() => {
    fetchData().then(data => setData(data));  // data是旧值
}, []);

// ✅ 正确：使用ref或正确的依赖
useEffect(() => {
    let cancelled = false;
    fetchData().then(data => {
        if (!cancelled) setData(data);
    });
    return () => { cancelled = true; };
}, []);
```

## 六、Java并发安全模式 ⭐⭐⭐⭐⭐

> AI生成Java并发代码的高危模式，全部具备"测试通过、上线炸裂"特征

### 6.1 synchronized集合迭代删除 (CONC-001)

**识别特征**：
- `Collections.synchronizedList/Map/Set()` + for-each + remove
- 对synchronized包装器的复合操作（迭代+修改）

**典型代码**：
```java
// ❌ AI常犯：synchronizedList不保护迭代
private List<T> items = Collections.synchronizedList(new ArrayList<>());
for (T item : items) {
    if (shouldRemove(item)) items.remove(item); // ConcurrentModificationException
}

// ✅ 正确：使用ConcurrentLinkedQueue
private ConcurrentLinkedQueue<T> items = new ConcurrentLinkedQueue<>();
items.removeIf(this::shouldRemove);
```

**审查要点**：
- [ ] synchronized*()包装器的所有迭代操作是否原子？
- [ ] 是否应该替换为java.util.concurrent集合？

---

### 6.2 Virtual Thread synchronized pinning (CONC-002)

**识别特征**：
- `synchronized`方法/块 + Virtual Thread环境
- synchronized内含IO/网络/数据库操作

**典型代码**：
```java
// ❌ AI常犯：synchronized在Virtual Thread中pin住载体线程
public synchronized void transfer(Account from, Account to, BigDecimal amount) {
    from.debit(amount);  // DB操作
    to.credit(amount);   // DB操作
    auditLog.record();   // 网络调用
}

// ✅ 正确：ReentrantLock + tryLock超时
private final ReentrantLock lock = new ReentrantLock();
public void transfer(...) throws InterruptedException {
    if (lock.tryLock(5, TimeUnit.SECONDS)) {
        try { ... } finally { lock.unlock(); }
    }
}
```

**性能影响**：synchronized ~50 TPS → ReentrantLock ~500 TPS（10倍）

---

### 6.3 双重检查锁定缺少volatile (CONC-003)

**识别特征**：
- `if(x==null) synchronized { if(x==null) x = new ... }` 无volatile
- 延迟初始化模式

**典型代码**：
```java
// ❌ AI常犯：JMM允许指令重排序，返回半构造对象
private static Resource resource;
public static Resource getInstance() {
    if (resource == null) {
        synchronized (ResourceFactory.class) {
            if (resource == null) resource = new Resource(); // 可能看到半构造对象
        }
    }
    return resource;
}

// ✅ 正确：静态内部类Holder模式
private static class Holder { static final Resource INSTANCE = new Resource(); }
public static Resource getInstance() { return Holder.INSTANCE; }
```

---

### 6.4 价值类对象作锁 (CONC-004)

**识别特征**：
- `synchronized(Boolean/Integer/String)` 作为锁对象
- `private static final Boolean lock = Boolean.FALSE`

**典型代码**：
```java
// ❌ AI常犯：Boolean.FALSE在整个JVM中共享
private static final Boolean lock = Boolean.FALSE;
synchronized (lock) { ... }  // 与所有使用Boolean.FALSE的代码竞争同一锁

// ✅ 正确：专用Object实例
private final Object lock = new Object();
synchronized (lock) { ... }
```

**危险范围**：Boolean、Integer(-128~127缓存)、String常量池、List.of()、java.time类型

---

### 6.5 Structured Concurrency范围泄漏 (CONC-005)

**识别特征**：
- `scope.fork()` 无 `scope.join()`
- try-with-resources关闭scope时子任务未完成

**典型代码**：
```java
// ❌ AI常犯：漏掉join，僵尸线程泄漏
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    scope.fork(() -> process(order));
    // 缺少 scope.join()
}

// ✅ 正确：join + throwIfFailed
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    var tasks = orders.stream().map(o -> scope.fork(() -> process(o))).toList();
    scope.join();
    scope.throwIfFailed();
    return tasks.stream().map(Subtask::get).toList();
}
```

---

### 6.6 CompletableFuture异常吞噬 (CONC-006)

**识别特征**：
- CompletableFuture链式调用无 whenComplete/handle/orTimeout
- 异步操作无超时控制

**典型代码**：
```java
// ❌ AI常犯：异常静默丢失
return CompletableFuture.supplyAsync(() -> fetch(id))
    .thenCompose(this::validate)
    .thenApply(this::buildResult);
// 任何步骤失败 → 调用方永远收不到结果

// ✅ 正确：超时 + 日志 + 降级
return CompletableFuture.supplyAsync(() -> fetch(id))
    .thenCompose(this::validate)
    .thenApply(this::buildResult)
    .orTimeout(5, TimeUnit.SECONDS)
    .whenComplete((r, ex) -> { if (ex != null) log.error(...); })
    .handle((r, ex) -> ex != null ? fallback(id) : r);
```

---

### 6.7 锁内Thread.sleep (CONC-007)

**识别特征**：
- `synchronized { Thread.sleep() }` 轮询等待
- 持有锁时sleep不释放monitor

**典型代码**：
```java
// ❌ AI常犯：sleep不释放锁，其他线程无法进入
synchronized (monitor) {
    while (!ready()) Thread.sleep(200);  // 死锁风险
    process();
}

// ✅ 正确：wait释放锁，允许其他线程修改状态
synchronized (monitor) {
    while (!ready()) monitor.wait(200);
    process();
}
```

### 5.3 事务内外部调用陷阱 ⭐⭐⭐⭐⭐

**识别特征**：
- @Transactional方法内调用外部API（HTTP/RPC/MQ）
- 数据库锁持有时间覆盖了外部调用时间
- 外部调用失败导致事务回滚但锁已持有

**典型案例**（TossPayment支付确认）：
```java
// ❌ 事务内外部调用：锁持有覆盖了网络调用时间
@Transactional
public PaymentResponse confirmPayment(User user, PaymentConfirmRequest request) {
    Payment payment = repository.findByOrderIdForUpdate(request.getOrderId()); // 加悲观锁

    Map<String, Object> response = tossPaymentClient.confirmPayment(request); // 外部API调用！
    payment.confirm(request.getPaymentKey(), method);

}

// ✅ 改进：先调外部API，再开事务更新（最短锁持有时间）
public PaymentResponse confirmPayment(User user, PaymentConfirmRequest request) {

}
```

### 5.4 AI重构隐性规则丢失 ⭐⭐⭐⭐⭐

### 5.5 @Transactional 静默失败五连 ⭐⭐⭐⭐⭐

**识别特征**：
- @Transactional注解存在但事务实际不生效
- 无编译错误、无运行时异常、数据静默出错
- 银行支付场景下表现为资金无声丢失

**五种模式及典型代码**：

```java
// 模式1：自调用绕过代理
public void placeOrder(Order order) {
    saveOrder(order);  // this.saveOrder() — 代理不拦截
}
@Transactional
public void saveOrder(Order order) { ... }  // 注解装饰性的

// 模式2：Checked异常默认提交
@Transactional  // ← 缺少 rollbackFor
public void transfer(Long fromId, Long toId, BigDecimal amount) throws IOException {
    from.debit(amount);
    accountRepository.save(from);  // 已持久化
    complianceClient.check(from);  // 抛IOException → 事务提交！资金丢失
}

// 模式3：private/final方法
@Transactional
private void persistPayment(Payment p) { ... }  // CGLIB无法override

// 模式4：REQUIRES_NEW连接池死锁
@Transactional  // 持有conn#1
public void createOrder(Order order) {
    orderRepository.save(order);
    auditService.logAudit(...);  // REQUIRES_NEW需要conn#2 → 池耗尽 → 死锁
}

// 模式5：readOnly=true静默丢弃写入
@Transactional(readOnly = true)
public class ProductService {
    public void updatePrice(Long id, BigDecimal price) {
        p.setPrice(price);  // Hibernate不flush — 修改静默丢失
    }
}
```

**统一本质**：所有模式都是**绕过了代理**——this调用、private无法拦截、checked异常绕过回滚逻辑、REQUIRES_NEW绕过当前事务上下文、readOnly绕过dirty checking。

**审查要点**：
- [ ] 是否有this.xxx()调用@Transactional方法？
- [ ] 是否显式声明rollbackFor=Exception.class？
- [ ] @Transactional方法是否为public且非final？
- [ ] REQUIRES_NEW是否用@TransactionalEventListener(AFTER_COMMIT)解耦？
- [ ] 类级readOnly=true上的写方法是否显式@Override？
- [ ] 连接池容量 ≥ 并发量 × (1 + REQUIRES_NEW方法数)？

### 5.6 Virtual Thread + synchronized 载体线程Pin ⭐⭐⭐⭐⭐

**识别特征**：
- Java 21+项目使用Virtual Thread但仍用synchronized
- 高并发下性能骤降（10x+退化）
- JProfiler显示载体线程全部blocked

**典型代码**：
```java
// ❌ AI常犯：synchronized pin住载体线程
public synchronized void transfer(Account from, Account to, BigDecimal amount) {
    from.withdraw(amount);   // 包含DB操作，耗时长
    to.deposit(amount);
    auditLog.record(...);    // 可能包含远程调用
}

// ✅ 正确：ReentrantLock + timeout
private final ReentrantLock transferLock = new ReentrantLock();
public void transfer(Account from, Account to, BigDecimal amount) {
    if (transferLock.tryLock(5, TimeUnit.SECONDS)) {
        try { ... } finally { transferLock.unlock(); }
    } else {
        throw new TransferTimeoutException("无法获取转账锁");
    }
}
```

**审查要点**：
- [ ] Virtual Thread项目中是否使用synchronized？→ 替换为ReentrantLock
- [ ] 锁是否有超时机制？→ 防止无限等待
- [ ] 是否在finally中释放锁？→ 防止死锁

### 5.7 Collections.synchronized* 假线程安全 ⭐⭐⭐⭐

**识别特征**：
- 使用Collections.synchronizedList/Map等包装器
- 在迭代过程中修改集合
- ConcurrentModificationException（甚至在单线程下！）

**典型代码**：
```java
// ❌ AI常犯：synchronized wrapper不保护迭代
private List<User> activeUsers = Collections.synchronizedList(new ArrayList<>());
for (User user : activeUsers) {
    if (user.isInactive()) {
        activeUsers.remove(user);  // ConcurrentModificationException!
    }
}

// ✅ 正确：使用并发集合
private ConcurrentLinkedQueue<User> activeUsers = new ConcurrentLinkedQueue<>();
activeUsers.removeIf(User::isInactive);  // 安全

// 或需要索引访问时
private CopyOnWriteArrayList<User> activeUsers = new CopyOnWriteArrayList<>();
```

**审查要点**：
- [ ] 是否有Collections.synchronized*()？→ 假定已损坏
- [ ] 迭代中是否有remove/add？→ 用ConcurrentHashMap.removeIf
- [ ] 读多写少？→ CopyOnWriteArrayList；写多？→ ConcurrentLinkedQueue

### 5.8 Double-Checked Locking 反模式 ⭐⭐⭐

**识别特征**：
- volatile + synchronized双重检查
- 看似正确但容易在修改时引入bug
- Java有更安全的替代方案

**典型代码**：
```java
// ❌ AI常犯：double-checked locking
private volatile Connection connection;
public Connection getConnection() {
    if (connection == null) {
        synchronized (this) {
            if (connection == null) {
                connection = createConnection();
            }
        }
    }
    return connection;
}

// ✅ 正确：holder pattern（利用JVM类加载保证线程安全）
private static class ConnectionHolder {
    static final Connection INSTANCE = createConnection();
}
public Connection getConnection() {
    return ConnectionHolder.INSTANCE;
}
```

**审查要点**：
- [ ] 是否有double-checked locking？→ 用holder pattern替代
- [ ] 懒初始化的"懒"是否必要？→ 大多数场景eager init即可
- [ ] 共享单例Connection？→ 应使用连接池（HikariCP）

### 5.9 Virtual Thread synchronized Pinning ⭐⭐⭐⭐⭐

**识别特征**：
- synchronized方法/块中包含IO操作（DB、网络调用）
- Java 21+ Virtual Thread环境下运行
- 性能急剧下降但CPU利用率低

**典型代码**：
```java
// ❌ AI常犯：synchronized + IO = pin住载体线程
public synchronized TransferResult transfer(Long fromId, Long toId, BigDecimal amount) {
    Account from = accountRepository.findById(fromId).orElseThrow();  // DB查询
    notificationService.notify();  // 网络调用
    return TransferResult.success();
}
// synchronized → pin载体线程 → ForkJoinPool耗尽 → 所有VT排队
// 实测：synchronized ~50 TPS vs ReentrantLock ~500 TPS

// ✅ 正确：ReentrantLock + tryLock超时 + 细粒度锁
private final ConcurrentHashMap<Long, ReentrantLock> accountLocks = new ConcurrentHashMap<>();
public TransferResult transfer(Long fromId, Long toId, BigDecimal amount) {
    Long first = Math.min(fromId, toId);
    Long second = Math.max(fromId, toId);
    ReentrantLock lock1 = accountLocks.computeIfAbsent(first, k -> new ReentrantLock());
    ReentrantLock lock2 = accountLocks.computeIfAbsent(second, k -> new ReentrantLock());
    if (!lock1.tryLock(5, TimeUnit.SECONDS)) throw new TransferTimeoutException();
    try {
        if (!lock2.tryLock(5, TimeUnit.SECONDS)) throw new TransferTimeoutException();
        try { return doTransfer(fromId, toId, amount); }
        finally { lock2.unlock(); }
    } finally { lock1.unlock(); }
}
```

**审查要点**：
- [ ] Virtual Thread环境下是否用了synchronized？→ 必须改ReentrantLock
- [ ] 锁内是否有IO/网络操作？→ 移出锁范围
- [ ] 多把锁获取顺序是否一致？→ 按ID排序防死锁
- [ ] 是否有超时机制？→ tryLock(timeout)

### 5.10 价值类对象作锁 ⭐⭐⭐⭐⭐

**识别特征**：
- synchronized(Boolean/Integer/String)
- 锁对象是JVM缓存的值类型
- 死锁堆栈中两个线程无逻辑关联

**典型代码**：
```java
// ❌ AI常犯：用Boolean/Integer作为锁对象
private static final Boolean settlementLock = Boolean.FALSE;

// Boolean.FALSE全局唯一！所有第三方库竞争同一个monitor

private static final Integer retryLock = Integer.valueOf(0);

// Integer缓存(-128~127)范围内共享同一对象

// ✅ 正确：专用Object实例
private final Object settlementLock = new Object();
```

### 5.11 StructuredTaskScope 缺少 join() ⭐⭐⭐⭐⭐

**识别特征**：
- scope.fork() 后无 scope.join()
- try-with-resources关闭scope时子任务未完成
- ArrayList等多线程共享非线程安全集合

**典型代码**：
```java
// ❌ AI常犯：漏掉join + 非线程安全集合
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    List<PaymentResult> results = new ArrayList<>();
    for (PaymentOrder order : orders) {
        scope.fork(() -> {
            results.add(processPayment(order));  // ❌ ArrayList非线程安全
            return null;
        });
    }
    // ❌ 没有scope.join()！关闭时子任务仍在运行→僵尸线程→OOM
}

// ✅ 正确：join + throwIfFailed + 安全收集
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    List<Subtask<PaymentResult>> tasks = orders.stream()
        .map(order -> scope.fork(() -> processPayment(order)))
        .toList();
    scope.join();            // ✅ 等待所有任务完成
    scope.throwIfFailed();   // ✅ 任何失败则抛异常
    List<PaymentResult> results = tasks.stream()
        .map(Subtask::get).toList();  // ✅ 安全收集
}
```

**审查要点**：
- [ ] StructuredTaskScope是否在关闭前调了join()？
- [ ] fork子任务中是否用了非线程安全集合？→ 用Subtask引用收集
- [ ] 是否需要ShutdownOnFailure还是ShutdownOnSuccess？

### 5.12 CompletableFuture 异常吞噬 ⭐⭐⭐⭐

**识别特征**：
- 链式异步调用无异常处理
- 无超时控制，可能永远pending
- 调用方无法感知失败

**典型代码**：
```java
// ❌ AI常犯：异步链无异常处理
CompletableFuture
    .supplyAsync(() -> accountClient.query())
    .thenCompose(account -> tradeClient.query())
    .thenCompose(detail -> riskClient.queryScore());
// 任何一步失败→异常被静默吞噬，调用方永远收不到结果

// ✅ 正确：超时 + 日志 + 降级
CompletableFuture
    .supplyAsync(() -> accountClient.query())
    .thenCompose(account -> tradeClient.query())
    .thenCompose(detail -> riskClient.queryScore())
    .orTimeout(5, TimeUnit.SECONDS)     // ✅ 超时控制
    .whenComplete((result, ex) -> {      // ✅ 日志记录

    })
    .handle((result, ex) -> {           // ✅ 降级处理
        if (ex != null) return TransactionDetail.fallback();
        return result;
    });
```

- [ ] 降级策略是否合理？

### 5.13 锁内 Thread.sleep ⭐⭐⭐⭐

**识别特征**：
- synchronized块内调用Thread.sleep()
- 轮询等待某个条件满足
- sleep不释放monitor锁，其他线程无法进入同步块

**典型代码**：
```java
// ❌ AI常犯：锁内sleep → 死锁
synchronized (monitor) {
    while (!isConfirmed()) {
        Thread.sleep(200);  // sleep不释放锁！
        // 如果更新状态的代码也需要这个锁 → 永远死锁
    }
}

// ✅ 正确：wait/notify模式
synchronized (monitor) {
    while (!isConfirmed()) {
        monitor.wait(200);  // wait释放锁，允许其他线程进入
    }
}
// 更新状态的代码：
synchronized (monitor) {
    updateStatus();
    monitor.notifyAll();  // 唤醒等待线程
}
```

**审查要点**：
- [ ] synchronized块内是否有Thread.sleep()？→ 必须改wait()
- [ ] 条件检查是否在while循环中（防止虚假唤醒）？
- [ ] wait/notify是否配对使用？
